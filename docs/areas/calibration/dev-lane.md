# Calibration: the Aperture lane and backfilled tickets

Dev work, Aperture built by Claude Code under the maintainer's supervision, is calibrated apart from the rest of life. Its minutes are his attention minutes, and its estimates are Claude's read of them, so the gap measures how well Claude prices his time, not how well he prices his own. Followup F128; decided 2026-11-15 and 2026-11-16. The plan and decision log live in the lane's archived `localNotes/` (`calibration-dev-lane`).

"Backfill" here is this import. It is not the one-time retro estimate on a done task with no baseline ([integrity](integrity.md) → _Retro estimate, once_), which scores like any other point.

## The import path

- **`backfill_tasks {tasks: [{id, actualMin, estimateMin?, completedDay}]}`** (MCP) / `backfillTasks` (API) closes open tickets: each is taken through `complete_task`'s chain in one pure step (`planBackfill`): started, so the lock freezes on what it said then; the estimate if given; the actual; the done gate. Then `completedAt` is set to noon of `completedDay` in the user's zone, `startedAt` is clamped so it never follows it, and the task is marked. Noon sits inside the app day whatever the day-start hour and away from a DST edge.
- **One consistent read, one batch put.** Sixty `complete_task` chains each re-read the task list, which would not fit the MCP Lambda's 15 s timeout (`cdk/src/lib/app-stack.ts`).
- **All-or-nothing on validation.** One bad row refuses the whole batch, naming it (`Row 3 (<id>): …`), and writes nothing: an unknown id, an id listed twice, `actualMin` under 1, `estimateMin` under 1 or missing on a task with none, a `completedDay` that isn't a date or is after today, a cancelled task, or a done one not yet marked. 1 to 100 rows.
- **Plain tasks only.** A parent, a part, an errand, a Roll rep, a recurring occurrence or a task with a calendar event carries side effects (a rollup, a check-off, a sitting, a series, a block) the batch keeps out of its path. Those close through `complete_task`, then take the mark with `update_task {backfilled: true}`.
- **A rerun is safe.** A task already done and backfilled comes back `skipped`, unchanged. If the batch put dies part-way, the rows it wrote are done and marked, and a rerun finishes the rest.
- **The mark alone.** `update_task {backfilled: true | false}` (`setTaskBackfilled`) sets or clears it on a done task that is a calibration point and not a parent, applied after any status change in the same call. The completion day never moves. `complete_task` is unchanged.

**Who writes it.** The backfill of the shipped dev tickets is prod data: the hub drafts the table for the maintainer's one skim, and the write happens only on his explicit yes, from a session started after the deploy (a running session can keep a stale MCP tool list).

## Dev estimates: the plan table's "You" minutes

A dev ticket's estimate is the plan table's **You** minutes for that lane: what the lane will cost the maintainer in attention (decisions, Mac steps, phone checks, reading), never Claude's build time (decided 2026-11-16). Its actual is his real attention minutes: his number at merge until pulse tracking supplies it.

- **The kickoff carries it.** The hub's kickoff file names the lane's Aperture ticket and its `You: <n> min`, and the plan row for the lane writes `you` as `<n> min` ([SESSION-BOARD](../../ops/SESSION-BOARD.md) → _Plan_).
- **Both writes ride asks the hub already sends**, never a separate ping ([HUB](../../ops/HUB.md) → _The hub's duties_ → _Dev tickets_): the kickoff relay asks for the one `update_task {id, estimateMin: n}`, made before work starts so the lock freezes on it as `planned`; the merge line asks for the `complete_task {id, actualMin}` with his number. Each is a prod MCP write, so each needs his in-the-moment yes (CLAUDE.md → _Aperture MCP connector_).
