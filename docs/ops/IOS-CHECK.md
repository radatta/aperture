# iOS check — the devcheck on the Mac's iOS Simulator

Headless Chromium can't show what only an iPhone does: the soft keyboard covering a field, zoom on focus, the Home Screen app's relaunch, the first launch after a deploy running the old build. The **iOS check** runs those rows on a real **iOS 27 Simulator on the user's Mac**, unattended. The devcheck sends a `sim` job through the Mac mailroom (MAILROOM.md). The mailroom's installed runner drives the sim with fixed recipes: boot, launch the Home Screen web app, sign in from Keychain, tap, read and screenshot. The result comes back through the shared folder. The sim never takes the Mac's focus, cursor or keyboard. Proven in the 2026-11-04 trial (`/workspace/localNotes/archive/mac-sim/trial/findings.md`).

```
container: devcheck step (entry 'ios') → ctx.ios.run(plan)
  plan = data: [{op:"launch"},{op:"tap",…},{op:"expect",…}]   ─ .hostjobs/inbox/<id>.json (job "sim") ─▶ Mac runner
  waits ≤ 90 s for the pickup (results/<id>/ appears), then for result.json while progress.json moves     │
  ◀── results/<id>/{progress.json, shots/NN-<name>.png, result.json}                    jobs/sim.sh: validate the
  pass → rows proven · fail → row fails · unavailable → rows "needs you: <reason>"      whole plan → Device Hub →
                                                                                        boot → ops (AXe + simctl)
```

Analogy: the container hands the Mac a checklist ("open the app, tap the box labelled Reflection, is it above the keyboard?"). The Mac's clerk knows how to do each line safely and answers only what it saw.

## The op language

A job's `params`: `{sha: <40 hex: the build under test>, timeoutSec: 60–600, shutdown: bool, steps: [1–80 ops]}`. No device, URL, path or credential is a parameter: the sim name, the dev origin (through the Home Screen icon), the Cognito host pattern, the Keychain item and the test user's email are constants in `jobs/sim.sh`. They are slot A's (`dev`): a devcheck on slot B (`devb`, CI-BOT.md → _Dev slots_) never queues a sim job, and its iOS rows read needs-you `SIM_SLOT_A_ONLY` (`scripts/src/devcheck/ios.ts`). `SIM_JQ` validates the whole plan before any `simctl`/`axe` call; `scripts/src/mailroom/sim.ts → validateSimParams` mirrors it in the same order, and `tools/mailroom/testdata/jobs.jsonl` drives both.

A plan that doesn't open with `launch` carries on from the previous job's screen (the devcheck's later steps); it still gets the readiness checks, and if they had to boot the sim (it was off, or rebooted to re-arm the keyboard prefs) or quit the app (to pin the keyboard prefs, _Keyboard_) there is nothing to carry on from: `SIM_UNAVAILABLE/NOT_LAUNCHED`. Each job allows 400 point reads (`TIMEOUT/PROBES`) and its `timeoutSec` (`TIMEOUT`).

Refused at validation (`rejected`, a harness bug): `BAD_PARAM`, `TOO_MANY_OPS`, `BAD_OP` (an unknown op or argument, a point off the `SIM_W`×`SIM_H` screen, an `as` (or a `keys` `in`) used before it's defined, an `as` defined twice, a kill not followed by launch, a signIn before any launch, shutdown not last, over 20 shots) and `DENIED_TAP`. `TAP_DENY` lists the app's write buttons (`Save`, `Save log`, `Mark done`, `Start`, `Focus`, `Delete`, `Export JSON`, `send` — the capture bar's return key, …). A label is denied when it equals an entry or is an entry followed by a space, on the op's label at validation and again on the element actually matched (`DENIED`), since a label prefix could land on one. A belt — the boundary is the test user's own partition.

## Device profile

Every fixed point a recipe uses — the landmarks (Home's capture bar, the Sign in card), the Cognito form, the keyboard's keys, space bar and accessory bar, the nav row, the build stamp, the app switcher — lives in one block at the top of `jobs/sim.sh`, measured on one device type (`SIM_DEVICE_TYPE`). A sim of any other type is `SIM_UNAVAILABLE/PROFILE_MISMATCH` (needs you), never a run of mis-aimed taps. Changing the device: create the sim, add dev to its Home Screen by hand, measure the points in a Mac session (`/workspace/localNotes/archive/mac-sim/trial/remeasure.md` is the procedure), replace the block, and update the fixture tape (`gen-jobs.py`'s point rules) — a fixture that probes a point the runner no longer uses fails, so the two can't drift.

## Reading the page

AXe's full accessibility tree holds no web content (AXe issue 65): only native chrome such as SpringBoard icons. So `tap --label` can't target page elements. **`describe-ui --point X,Y` does see web content**, about 1 s per read: static text puts its text in `AXValue` (label empty), controls carry their `aria-label` in `AXLabel`, toggles their state in `AXValue` (`"1"`/`"0"`), buttons `enabled`. An empty field reports its placeholder as its value. No DOM ids come through. Coordinates are points (`SIM_W`×`SIM_H`; screenshots are 3×).

## Keyboard

The sim boots as if a hardware keyboard were attached: a focused field shows only the accessory bar. Simulator.app's `ConnectHardwareKeyboard` pref does nothing under Device Hub. What works (trial T11–T12): two **in-guest** prefs, `com.apple.keyboard.preferences` `HardwareKeyboardLastSeen` and `AutomaticMinimizationEnabled`, both `false`, **written before boot** (a live write doesn't apply). Any HID typing (`axe type`/`axe key`) flips both back to 1 and hides the keyboard, so test text is typed by tapping the on-screen keys, found and confirmed with `--point`. `launch` re-arms and reboots whenever the prefs read anything but `0/0`; a sign-in (which types through HID) ends with a re-arm and reboot.

These prefs are undocumented, so an Xcode or iOS update can break the recipe for every branch at once. **No soft keyboard where one is due is `SIM_UNAVAILABLE/KEYBOARD_SETUP` — needs you, never a fail**; its note carries both prefs and the Xcode version, and every result records `device.xcode`, so a break lines up with the update. **After updating Xcode or the sim runtime**, run `pnpm mailroom sim-probe` and one devcheck with the iOS scenario; if keyboard rows say `KEYBOARD_SETUP`, re-trial the recipe (findings T11–T12) before trusting them. The trade-off: an app bug that stops a field taking focus would also read as `KEYBOARD_SETUP`; the row's screenshot tells which (`shots/NN-fail.png`). A dropped tap on the field no longer does: `tap` retaps a field that brought no keyboard (job …054323Z…-done-form-e8e2 read as `KEYBOARD_SETUP` before that).

**Everything that changes what a key does or when it lands is pinned**, in the same domain, read back at every readiness check (one `defaults export`). Pinned off: autocorrect, auto-capitalisation, spell check, predictions and the suggestion bar, inline completion, the "." shortcut, smart quotes and dashes, slide to type, and the hardware keyboard's own autocorrect, capitalisation and "." shortcut (`KeyboardAutocorrection` `KeyboardAutocapitalization` `KeyboardCheckSpelling` `KeyboardPrediction` `KeyboardShowPredictionBar` `KeyboardInlineCompletion` `KeyboardPeriodShortcut` `SmartQuotesEnabled` `SmartDashesEnabled` `KeyboardContinuousPathEnabled` `HWKeyboardAutocorrection` `HWKeyboardAutocapitalization` `HWKeyboardPeriodShortcut`). Pinned on: the slide-to-type, gesture and inline-completion tips, marked seen (`DidShowContinuousPathIntroduction` `DidShowGestureKeyboardIntroduction` `DidShowInlineCompletionEducationTip`).

- **If one isn't pinned:** the runner writes them all, quits the web app (it reads them at its next launch; no reboot needed) and reads them again. Still not pinned is `KEYBOARD_SETUP` naming the keys, and `launch`'s note says `keyboard prefs pinned (N were off)`.
- **Why:** Rahul asked for it to be "as deterministic as possible" after job …233129Z…-done-form-80c5 typed "cdcgac" three times and kept "Cdc".
- **Evidence for the keys:** pest-plugin-simulator PR 32 (iOS 26.5) and WebDriverAgent. Seen to reach the web app on 2026-11-08, when typed text stopped being capitalised and the suggestion bar went.

**Not pinned:**

- **The keyboard layout** (`KeyboardsCurrentAndNext`, `en_US` QWERTY). Every key's spot is read before it is tapped, so a different layout is a `MISS`, never a wrong letter.
- **The keyboard's height.** With no suggestion bar it sits about 20 pt lower. `blur` and `aboveKeyboard` read the accessory bar where it is.
- **Dictation and emoji keys.** They are never tapped.
- **Whether `KeyboardContinuousPathEnabled` really stops slide to type.** Taps never slide, so it can't change a run.
- **`simctl erase`.** It drops them all, and the next readiness check writes them back.

## Sign-in and the password

The web app's refresh token lasts 30 days, so the runner signs in when `launch` lands on the Sign in card (≤ monthly, plus a ~14 s reboot). The app has no Sign out control. To sign the sim out by hand, delete the icon and re-add it: that landed on the Sign in card (P12), though the deleted icon came back once by the next run (P13) and stayed gone after a reboot the time after (P14), so check for one icon; two is `WEBCLIP_MISSING`. The password's only path: `security find-generic-password -s aperture-devcheck-dev -a <email> -w | tr -d '\n' | axe type --stdin`, the Keychain read time-capped like every tool (a Keychain access prompt nobody answers would otherwise hang the drain). Never argv, env, a file, a log, a result, a note or a screenshot. It is typed only while the sheet's **native** address bar — role `AXGenericElement`, id `URL`, label `Address`, owned by another process than the page (its `pid` differs from the Sign in button's) — reads dev's own Cognito host, `aperture-dev-618015769091.auth.us-west-1.amazoncognito.com`; checked before the email and again just before the password. The second check also requires the same bar pid as the first and a pid other than the form's, so a whole page drawn at another origin (one pid for both) fails. A page can't fake the process. Measured (mac-sim re-measure, P12): the value starts with U+200E, which the check strips; the id is `URL`; the bar's pid differs from both pages' and is unchanged with the password field focused. Web content never showed an `AXUniqueId`, but no element read was known to have a DOM id, so the id alone isn't trusted. Anything else is `SIGNIN_FAILED/COGNITO_HOST`, the password never read. Between those checks, point reads on the form drop their values (labels only: a typed password lives in `AXValue`); the address reads keep theirs, which is the host. **Focus is proven before the password moves.** Accessibility marks no focus between fields (P12: every key identical between Email focused and Password focused), and a dropped tap would type the password into Email, in clear. So after tapping the field the runner presses one harmless key (`axe key 27 --duration 0.2`, x; a bare `axe key` exits 0 and did nothing in the re-measure): Password must read one bullet with Email unchanged, and delete must return it to its placeholder. Anything else retaps once, then is `SIGNIN_FAILED/FORM_CHANGED`, the password never read. The bullet is U+2022, still masked at about 1 s and 4 s (P14). The keyboard's previous/next arrows also show focus through `enabled` (read by `--point` only, same process as the address bar), measured but not used: the key proves where characters land, and a second fixed-point read would only add a way to fail. A dropped tap on Aperture's Sign in is also retried once, and any failure after that first tap terminates the app, so no filled form survives for a later plan to read. iOS 27 masks a filled password field as bullets but leaks its length (trial T9b), so no read lands inside the password field after typing (the submit search skips its frame), and no screenshot is taken during sign-in. The fixtures plant the password in point reads and fail if it reaches anything the runner writes.

An unavailable step turns off the run's later iOS steps (they don't wait on a sleeping Mac again), except `KEYBOARD_SETUP`: that one is the step's alone, so the rest of the scenario still runs (`needsYou(…, {stepOnly})`, scenario.ts).

**A point read that hangs** (8 s; other axe calls 30 s) answers nothing, which isn't "not there": every recipe that reads turns it into `AX_TIMEOUT` (needs you), never a `MISS`, a `KEYBOARD_SETUP`, an `AUTH_REJECTED` or a blur with no keyboard. Launch and the post-reboot check say `AX_TIMEOUT` only when no pass read cleanly. A dropped tap on the Home Screen icon is tapped again at polls 3, 6 and 10 of launch's wait, and a dropped submit on the Cognito form once more (only on that form's own button) before `AUTH_REJECTED`. Deletes (`erase … in`) and closing taps (`tap … closes`) are read back too (job …230610Z…-done-form-4385: six deletes left a Z and the Cancel tap left the modal open, so the next job's launch found it over Home and failed `LANDMARK`). Home presses and the switcher kill are read back too (`launch`, `kill` above); their misses are fails that block, because a read-back op that fails blocks, but their notes say iOS dropped the input: rerun the step, don't debug the app.

A result also carries `device {name, udid, runtime, axe, xcode}`, `booted` (warm · cold · rebooted · off), `signedIn` (already · fresh · false), `buildsSeen`, per-op `steps` with notes, `reads` and `shots`; the result dir also keeps the job as `plan.json`.

**iOS not run is never quiet.** When any iOS step came back unavailable, the devcheck report's status line says `iOS NOT RUN (<reason>): <n> iPhone rows untested`, `report.json` carries an `ios` block, and `pnpm mailroom open-pr` puts `> ⚠ **iPhone checks did not run** (<reason>): …` (plus "Mac asleep?" when it was `MAC_UNREACHABLE`/`MAC_STALLED`) as the PR body's **first line** when the head commit's newest devcheck had it (`open-pr.ts → iosBanner`). The hub's `[pr-open]` message and an autonomous `CC done` task repeat it.

## The build guard

Dev is redeployed often, and an iOS step doesn't hold the dev lock for its own sake. Every job carries the expected `sha`; `readBuild` reads the **running** build from the Settings stamp, and results are credited to it. `expectBuild` relaunches once when a service worker still runs the previous build — that is the two-launch refresh row. The devcheck's own end-of-run check (`DEV_CHANGED_MID_RUN`) unproves every row if dev's served build moved.

## Runtime

The scenario's last job ends with `shutdown`, so the sim is off for the rest of the run, and `finish` sends nothing when the last job's result says `booted: off`; a later scenario's sim step must open with `launch`, or it reads `NOT_LAUNCHED`. Trial timings: cold boot 2.7 s, first app launch after a boot 11 s, warm relaunch 8 s, ~1 s per point read. The iOS scenario costs ≈ 6 min (one clean run, 374 s; +0.8 min on the monthly sign-in), so every one of its steps is **slow** (DEV-CHECK.md → _Slow tier_): a full run takes it when the branch touches what the rows can see (`APP` in `scenarios/ios-standalone.ts`: keyboard lift, the fields it covers, the shell and insets, auth, the service worker's config) or the iOS harness, or `--feature ios-standalone`; `--tier all` always does; otherwise its rows read `deferred`. (The user's call, 2026-11-05: first replacing "every full run", then narrowing `app/**`, which would have rerun it on all 13 app PRs of a day, about 3 h, against 6 of them and about 1.5 h.) So an iOS-only bug in another app file waits for `--tier all` or naming the scenario.

**Nothing heavy runs on the Mac while a sim job does:** no build, test suite or mailroom fixture suite (its stubs skip the sim but still load the CPU). Under load the sim's reads slow about threefold and keys drop, which reads as a failed row (_Failures_ → the Mac under load). So the Mac-side steps that prove a runner change go one at a time, before the devcheck, never beside it (_Proving the Mac side_).

How long these jobs take on a given Mac, and what the machine goes through meanwhile, is the sim bench's job (SIM-BENCH.md).

## Proving the Mac side (a PR that changes `jobs/sim.sh`)

Mac bash is outside lint and typecheck, so its proof is the fixtures plus a real run: on the Mac, the fixture suite from GitHub's tarball at the sha under `/bin/bash` 3.2, (cases run in shards, `MAILROOM_FIXTURE_JOBS`: MAILROOM.md → _Tests_), then `install.sh --ref <sha>` (MAILROOM.md → _Install_), then from the container `pnpm mailroom sim-probe` (add `--sign-in` if it reports signed out; give the Bash call a 300 s timeout) and a full devcheck, each step finished before the next starts (nothing heavy beside a sim job: _Runtime_). The fixtures stub `axe`, `xcrun`, `open`, `pgrep`, `caffeinate` and `xcodebuild` as exported shell functions answering from a per-case tape (MAILROOM.md → _Tests_).

## Security

The sim job extends the mailroom's model (MAILROOM.md → _Security_). At worst a compromised container can make the Mac boot the dedicated sim and run allowlisted ops inside the Aperture web app as the dev test user, ≤ 10 min per job and 5 jobs per drain, and read that sim's screenshots — the same blast radius the devcheck's own API token gives it. Nothing on the Mac's screen, files or other Keychain items; `jobs/sim.sh` makes no network call itself (statically checked: no `curl`, `openurl` or `osascript`), runs every tool by name with a time cap (`sim_cap`), and opens no URL from a job.

**AXe under the dependency rule (B):** HID injection and accessibility reads over Apple's private Simulator automation channels, with version-specific edges already bitten (issues 65, 71, 76). One Mac-side binary, not a repo dependency. Rolling our own means an XCUITest runner target (Swift, an Xcode host project, code signing) on the same private APIs: strictly more to own.
