# iOS check — the devcheck on the Mac's iOS Simulator

Headless Chromium can't show what only an iPhone does: the soft keyboard covering a field, zoom on focus, the Home Screen app's relaunch, the first launch after a deploy running the old build. The **iOS check** runs those rows on a real **iOS 27 Simulator on the user's Mac**, unattended. The devcheck sends a `sim` job through the Mac mailroom (MAILROOM.md). The mailroom's installed runner drives the sim with fixed recipes: boot, launch the Home Screen web app, sign in from Keychain, tap, read and screenshot. The result comes back through the shared folder. The sim never takes the Mac's focus, cursor or keyboard. Proven in the 2026-11-04 trial (mac-sim branch, `localNotes/trial/findings.md`).

```
container: devcheck step (entry 'ios') → ctx.ios.run(plan)
  plan = data: [{op:"launch"},{op:"tap",…},{op:"expect",…}]   ─ .hostjobs/inbox/<id>.json (job "sim") ─▶ Mac runner
  waits ≤ 90 s for the pickup (results/<id>/ appears), then for result.json while progress.json moves     │
  ◀── results/<id>/{progress.json, shots/NN-<name>.png, result.json}                    jobs/sim.sh: validate the
  pass → rows proven · fail → row fails · unavailable → rows "needs you: <reason>"      whole plan → Device Hub →
                                                                                        boot → ops (AXe + simctl)
```

Analogy: the container hands the Mac a checklist ("open the app, tap the box labelled Reflection, is it above the keyboard?"). The Mac's clerk knows how to do each line safely and answers only what it saw.

## The op language

A job's `params`: `{sha: <40 hex: the build under test>, timeoutSec: 60–600, shutdown: bool, steps: [1–80 ops]}`. No device, URL, path or credential is a parameter: the sim name, the dev origin (through the Home Screen icon), the Cognito host pattern, the Keychain item and the test user's email are constants in `jobs/sim.sh`. `SIM_JQ` validates the whole plan before any `simctl`/`axe` call; `scripts/src/mailroom/sim.ts → validateSimParams` mirrors it in the same order, and `tools/mailroom/testdata/jobs.jsonl` drives both.

| op            | params                                                                                                                     | what the runner does                                                                                                                                                                                                                                                                         |
| ------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `launch`      | —                                                                                                                          | Readiness (AXe version, the device, Device Hub, boot, keyboard prefs `0/0` — else write them and reboot), home button, find the on-screen Aperture icon (on another page → `gesture scroll-left`), tap it, wait ≤ 40 s for the landmark: Home's capture bar (signed in) or the Sign in card. |
| `signIn`      | —                                                                                                                          | No-op when signed in. | `kill`        | `method`: `terminate` · `switcher` · `reboot`                                                                              | `simctl terminate <udid> com.apple.webapp` · double home in one `axe batch`, swipe the card up, tap the background · shutdown + boot. Refused at validation (`rejected`, a harness bug): `BAD_PARAM`, `TOO_MANY_OPS`, `BAD_OP` (an unknown op or argument, an `as` used before it's defined or defined twice, a kill not followed by launch, shutdown not last, over 20 shots) and `DENIED_TAP`. `TAP_DENY` lists the app's write buttons (`Save`, `Save log`, `Mark done`, `Start`, `Delete`, `Export JSON`, …); the runner checks it again on the element actually matched (`DENIED`), since a label prefix could land on one. A belt — the boundary is the test user's own partition.

## Device profile

Every fixed point a recipe uses — the landmarks (Home's capture bar, the Sign in card), the Cognito form, the keyboard's keys, space bar and accessory bar, the nav row, the build stamp, the app switcher — lives in one block at the top of `jobs/sim.sh`, measured on one device type (`SIM_DEVICE_TYPE`). A sim of any other type is `SIM_UNAVAILABLE/PROFILE_MISMATCH` (needs you), never a run of mis-aimed taps. Changing the device: create the sim, add dev to its Home Screen by hand, measure the points in a Mac session (the mac-sim branch's `localNotes/trial/remeasure.md` is the procedure), replace the block, and update the fixture tape (`gen-jobs.py`'s point rules) — a fixture that probes a point the runner no longer uses fails, so the two can't drift.

## Reading the page

AXe's full accessibility tree holds no web content (AXe issue 65): only native chrome such as SpringBoard icons. So `tap --label` can't target page elements. **`describe-ui --point X,Y` does see web content**, about 1 s per read: static text puts its text in `AXValue` (label empty), controls carry their `aria-label` in `AXLabel`, toggles their state in `AXValue` (`"1"`/`"0"`), buttons `enabled`. An empty field reports its placeholder as its value. No DOM ids come through. Coordinates are points (`SIM_W`×`SIM_H`; screenshots are 3×).

## Keyboard

The sim boots as if a hardware keyboard were attached: a focused field shows only the accessory bar. Simulator.app's `ConnectHardwareKeyboard` pref does nothing under Device Hub. What works (trial T11–T12): two **in-guest** prefs, `com.apple.keyboard.preferences` `HardwareKeyboardLastSeen` and `AutomaticMinimizationEnabled`, both `false`, **written before boot** (a live write doesn't apply). Any HID typing (`axe type`/`axe key`) flips both back to 1 and hides the keyboard, so test text is typed by tapping the on-screen keys, found and confirmed with `--point`. `launch` re-arms and reboots whenever the prefs read anything but `0/0`; a sign-in (which types through HID) ends with a re-arm and reboot.

These prefs are undocumented, so an Xcode or iOS update can break the recipe for every branch at once. **No soft keyboard where one is due is `SIM_UNAVAILABLE/KEYBOARD_SETUP` — needs you, never a fail**; its note carries both prefs and the Xcode version, and every result records `device.xcode`, so a break lines up with the update. **After updating Xcode or the sim runtime**, run `pnpm mailroom sim-probe` and one devcheck with the iOS scenario; if keyboard rows say `KEYBOARD_SETUP`, re-trial the recipe (findings T11–T12) before trusting them. The trade-off: an app bug that stops a field taking focus would also read as `KEYBOARD_SETUP`; the row's screenshot tells which.

## Sign-in and the password

The web app's refresh token lasts 7 days, so the runner signs in when `launch` lands on the Sign in card (≤ weekly, plus a ~14 s reboot). The password's only path: `security find-generic-password -s aperture-devcheck-dev -w | tr -d '\n' | axe type --stdin`. Never argv, env, a file, a log, a result, a note or a screenshot. It is typed only after the sheet's address bar matched `^aperture-dev-[0-9]{12}\.auth\.us-west-1\.amazoncognito\.com$`; anything else is `SIGNIN_FAILED/COGNITO_HOST` with nothing typed. From the Sign in tap to Home every point read drops its value (labels only: a typed password lives in `AXValue`). iOS 27 masks a filled password field as bullets but leaks its length (trial T9b), so the password field is never read after typing, and no screenshot is taken during sign-in. The fixtures plant the password in point reads and fail if it reaches anything the runner writes.

| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `pass`                                        | —                                                                                                                                                                                                                                                                                                                           | the step passes; its rows are proven on dev                                      |
| `fail`                                        | `ASSERT` + `MISS` · `OFF_SCREEN` · `NOT_IN_APP` · `BELOW_KEYBOARD` · `VALUE` · `ENABLED` · `WIDTH` · `STALE_BUILD` · `LANDMARK` · `DENIED`                                                                                                                                                                                  | the step fails: a bug (or a plan that needs new coordinates)                     |
| `error`                                       | `SIM_UNAVAILABLE` + `AXE_MISSING` · `AXE_VERSION(x)` · `SIM_MISSING` · `SIM_AMBIGUOUS` · `DEVICE_HUB` · `BOOT_FAILED` · `AX_TIMEOUT` · `WEBCLIP_MISSING` · `KEYBOARD_SETUP` · `AXE_FAILED` · `TERMINATE` · `RESULT_DIR`; `PASSWORD_MISSING`; `SIGNIN_FAILED` + `COGNITO_HOST` · `FORM_CHANGED` · `AUTH_REJECTED`; `TIMEOUT` | **needs you**: the step's rows say `iOS this run: <reason>`; the run stays green |
| `rejected`                                    | a validation code                                                                                                                                                                                                                                                                                                           | a harness bug: the step throws                                                   |
| no pickup in 90 s                             | `MAC_UNREACHABLE` (the job is withdrawn, so it can't run stale on wake)                                                                                                                                                                                                                                                     | needs you; later iOS steps in the run don't wait again                           |
| no heartbeat 5 min / past `timeoutSec` + 60 s | `MAC_STALLED`                                                                                                                                                                                                                                                                                                               | needs you                                                                        |

A result also carries `device {name, udid, runtime, axe, xcode}`, `booted` (warm · cold · rebooted · off), `signedIn` (already · fresh · false), `buildsSeen`, per-op `steps` with notes, `reads` and `shots`.

**iOS not run is never quiet.** When any iOS step came back unavailable, the devcheck report's status line says `iOS NOT RUN (<reason>): <n> iPhone rows untested`, `report.json` carries an `ios` block, and `pnpm mailroom open-pr` puts `> ⚠ **iPhone checks did not run** (<reason>, Mac asleep?): …` as the PR body's **first line** when the head commit's newest devcheck had it (`open-pr.ts → iosBanner`). The hub's `[pr-open]` message and an autonomous `CC done` task repeat it.

## The build guard

Dev is redeployed often, and an iOS step doesn't hold the dev lock for its own sake. Every job carries the expected `sha`; `readBuild` reads the **running** build from the Settings stamp, and results are credited to it. `expectBuild` relaunches once when a service worker still runs the previous build — that is the two-launch refresh row. The devcheck's own end-of-run check (`DEV_CHANGED_MID_RUN`) unproves every row if dev's served build moved.

## Runtime

Trial timings: cold boot 2.7 s, first app launch after a boot 11 s, warm relaunch 8 s, ~1 s per point read. The iOS scenario costs ≈ 3.5 min (+0.8 min on the weekly sign-in), so every one of its steps is **slow** (DEV-CHECK.md → _Slow tier_): a full run takes it when the branch touches `app/**` or the iOS harness, or `--feature ios-standalone`; `--tier all` always does; otherwise its rows read `deferred`. (The user's call, 2026-11-05, replacing "every full run".)

## Failures

| Symptom                                                | Cause                                                         | Fix                                                                                                   |
| ------------------------------------------------------ | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| every iOS row `needs you: MAC_UNREACHABLE`             | Mac asleep, lid shut, or the mailroom isn't installed         | wake the Mac and rerun; `pnpm mailroom probe` checks the mailroom                                     |
| `SIM_UNAVAILABLE/AXE_VERSION(x)`                       | Homebrew upgraded AXe                                         | `brew pin axe`, or re-trial and bump `SIM_AXE_VERSION`                                                |
| `SIM_UNAVAILABLE/KEYBOARD_SETUP` on every keyboard row | an Xcode/iOS update changed the keyboard prefs                | _Keyboard_ above: re-trial T11–T12                                                                    |
| `SIGNIN_FAILED/AUTH_REJECTED`                          | the devcheck password was rotated; the Keychain copy is stale | recopy it into `aperture-devcheck-dev` (Setup)                                                        |
| `PASSWORD_MISSING`                                     | no Keychain item, or launchd can't read it                    | re-add with `-T /usr/bin/security`                                                                    |
| `SIM_UNAVAILABLE/WEBCLIP_MISSING`                      | the sim was reset or the icon removed                         | add dev to the Home Screen again (Setup)                                                              |
| a `MISS` right after an app change                     | the plan's coordinates moved                                  | update the scenario's `near`/`scan` from the step's screenshot; scenario-only reruns need no redeploy |
| the sim stays booted after a crashed devcheck          | cleanup didn't run                                            | `pnpm mailroom sim-shutdown`                                                                          |

## Proving the Mac side (a PR that changes `jobs/sim.sh`)

Mac bash is outside lint and typecheck, so its proof is the fixtures plus a real run: on the Mac, the fixture suite from GitHub's tarball at the sha under `/bin/bash` 3.2, then `install.sh --ref <sha>` (MAILROOM.md → _Install_), then from the container `pnpm mailroom sim-probe` (add `--sign-in` if it reports signed out; give the Bash call a 300 s timeout) and a full devcheck. The fixtures stub `axe`, `xcrun`, `open`, `pgrep`, `caffeinate` and `xcodebuild` as exported shell functions answering from a per-case tape (MAILROOM.md → _Tests_).

## Security

The sim job extends the mailroom's model (MAILROOM.md → _Security_). At worst a compromised container can make the Mac boot the dedicated sim and run allowlisted ops inside the Aperture web app as the dev test user, ≤ 10 min per job and 5 jobs per drain, and read that sim's screenshots — the same blast radius the devcheck's own API token gives it. Nothing on the Mac's screen, files or other Keychain items; `jobs/sim.sh` makes no network call itself (statically checked: no `curl`, `openurl` or `osascript`), runs every tool by name with a time cap (`sim_cap`), and opens no URL from a job.

**AXe under the dependency rule (B):** HID injection and accessibility reads over Apple's private Simulator automation channels, with version-specific edges already bitten (issues 65, 71, 76). One Mac-side binary, not a repo dependency. Rolling our own means an XCUITest runner target (Swift, an Xcode host project, code signing) on the same private APIs: strictly more to own.
