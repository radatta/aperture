# iOS check — the devcheck on the Mac's iOS Simulator

Headless Chromium can't show what only an iPhone does: the soft keyboard covering a field, zoom on focus, the Home Screen app's relaunch, the first launch after a deploy running the old build. The **iOS check** runs those rows on a real **iOS 27 Simulator on the user's Mac**, unattended. The devcheck sends a `sim` job through the Mac mailroom (MAILROOM.md). The mailroom's installed runner drives the sim with fixed recipes: boot, launch the Home Screen web app, sign in from Keychain, tap, read and screenshot. The result comes back through the shared folder. The sim never takes the Mac's focus, cursor or keyboard. Proven in the 2026-11-04 trial (`/workspace/localNotes/archive/mac-sim/trial/findings.md`).

```
container: devcheck step (entry 'ios') → ctx.ios.run(plan)
  plan = data: [{op:"launch"},{op:"tap",…},{op:"expect",…}]   ─ .hostjobs/inbox/<id>.json (job "sim") ─▶ Mac runner
  waits ≤ 90 s for the pickup (results/<id>/ appears), then for result.json while progress.json moves     │
  ◀── results/<id>/{progress.json, shots/NN-<name>.png, result.json}                    jobs/sim.sh: validate the
  pass → rows proven · fail → row fails · unavailable → rows "needs you: <reason>"      whole plan → Device Hub →
                                                                                        boot → ops (AXe + simctl)
```

Analogy: the container hands the Mac a checklist ("open the app, tap the box labelled Reflection, is it above the keyboard?"). The Mac's clerk knows how to do each line safely and answers only what it saw.

## The op language

A job's `params`: `{sha: <40 hex: the build under test>, timeoutSec: 60–600, shutdown: bool, steps: [1–80 ops]}`. No device, URL, path or credential is a parameter: the sim name, the dev origin (through the Home Screen icon), the Cognito host pattern, the Keychain item and the test user's email are constants in `jobs/sim.sh`. They are slot A's (`dev`): a devcheck on slot B (`devb`, CI-BOT.md → _Dev slots_) never queues a sim job, and its iOS rows read needs-you `SIM_SLOT_A_ONLY` (`scripts/src/devcheck/ios.ts`). `SIM_JQ` validates the whole plan before any `simctl`/`axe` call; `scripts/src/mailroom/sim.ts → validateSimParams` mirrors it in the same order, and `tools/mailroom/testdata/jobs.jsonl` drives both.

A plan that doesn't open with `launch` carries on from the previous job's screen (the devcheck's later steps); it still gets the readiness checks, and if they had to boot the sim (it was off, or rebooted to re-arm the keyboard prefs) or quit the app (to pin the keyboard prefs, _Keyboard_) there is nothing to carry on from: `SIM_UNAVAILABLE/NOT_LAUNCHED`. Each job allows 400 point reads (`TIMEOUT/PROBES`) and its `timeoutSec` (`TIMEOUT`).

Refused at validation (`rejected`, a harness bug): `BAD_PARAM`, `TOO_MANY_OPS`, `BAD_OP` (an unknown op or argument, a point off the `SIM_W`×`SIM_H` screen, an `as` (or a `keys` `in`) used before it's defined, an `as` defined twice, a kill not followed by launch, a signIn before any launch, shutdown not last, over 20 shots) and `DENIED_TAP`. `TAP_DENY` lists the app's write buttons (`Save`, `Save log`, `Mark done`, `Start`, `Focus`, `Delete`, `Export JSON`, `send` — the capture bar's return key, …). A label is denied when it equals an entry or is an entry followed by a space, on the op's label at validation and again on the element actually matched (`DENIED`), since a label prefix could land on one. A belt — the boundary is the test user's own partition.

## Device profile

Every fixed point a recipe uses — the landmarks (Home's capture bar, the Sign in card), the Cognito form, the keyboard's keys, space bar and accessory bar, the nav row, the build stamp, the app switcher — lives in one block at the top of `jobs/sim.sh`, measured on one device type (`SIM_DEVICE_TYPE`). A sim of any other type is `SIM_UNAVAILABLE/PROFILE_MISMATCH` (needs you), never a run of mis-aimed taps. Changing the device: create the sim, add dev to its Home Screen by hand, measure the points in a Mac session (`/workspace/localNotes/archive/mac-sim/trial/remeasure.md` is the procedure), replace the block, and update the fixture tape (`gen-jobs.py`'s point rules) — a fixture that probes a point the runner no longer uses fails, so the two can't drift.

## Reading the page

AXe's full accessibility tree holds no web content (AXe issue 65): only native chrome such as SpringBoard icons. So `tap --label` can't target page elements. **`describe-ui --point X,Y` does see web content**, about 1 s per read: static text puts its text in `AXValue` (label empty), controls carry their `aria-label` in `AXLabel`, toggles their state in `AXValue` (`"1"`/`"0"`), buttons `enabled`. An empty field reports its placeholder as its value. No DOM ids come through. Coordinates are points (`SIM_W`×`SIM_H`; screenshots are 3×).

## Probe check

Every probe above is a point, and a UI change that moves what it points at — or puts another control beside it — breaks the row with nothing to catch it before a Simulator run (2026-11-12: private-log's 🔒 pill sat on the capture bar's probe). The **probe check** replays every iOS plan the scenarios send (recorded by `devcheck/ios-plans.ts`, as the sim bench's) against the stub app in headless Chromium from `~/pw`, and reads each point the runner would, in its order (`sim_points`, a scan's `hint` first) and with its match (`sim_match`). `pnpm ios-probe` runs it (`--scenario a,b`, `--engine webkit`, `--shots <dir>`); `pnpm devcheck:local` runs it after its scenarios (LOCAL-CHECK.md). It isn't in `pnpm test` or CI: 0 Actions minutes. Code: `scripts/src/ios-probe/`.

- **Calibrated, not guessed** (2026-11-12, against jobs …180905Z…-capture-be55 and …181031Z…-done-form-ab97; archive `localNotes/archive/ios-probe-check/calib/`). At 440×956 with insets 59/34 (CSS for `--safe-top` and `.pb-safe`), keyboard down matched AXe's frames to 0–3 pt. Keyboard up is a viewport resize, applied when focus sits in a fixed layer (the dock, a modal): at 440×550 with no bottom inset the capture bar, the Log toggle and Save log land on their frames exactly, and the Done form within 7 pt. Chromium and Playwright WebKit agreed to the pixel. Not modelled: a page field's keyboard (iOS scrolls the field, 45 pt for Search tasks) — so probes there are scans. `pnpm ios-probe --calibrate` repeats this comparison against the newest green run of each job (after an Xcode, runtime or `AXE_VERSION` change: _Keyboard_).
- **Reading**: a field's name is its label, its placeholder the value while empty; a toggle is an `AXCheckBox` valued `1`/`0`; a `<label>`'s text reads as its control (as on iOS); static text is an unlabelled value.
- **Fails**, with the runner's own semantics (`nav`'s tab points, `keys`/`erase` read-backs with the frame-centre second look, `expect` storing what it re-read, `closes`): `MISS`, `PRESENT`, `VALUE`/`LABEL`/`ENABLED`, `TYPED`/`ERASED`, `STILL_THERE`, `DENIED`, `OFF_SCREEN`, `UNMODELLED` (an op it can't place, the nav swipe included — never a skip), `NAV_UNCONFIRMED` only after the
  runner's whole read-back ladder (`nav` above; its 2 s waits as 7 settles — F198: one 300 ms settle missed a lazy
  route under load), with the runner's note on a late pass, a crashed job, a stale dev-data skip, no plans at all, and **`AMBIGUOUS`**: for a find whose point a later `keys … in`/`erase … in` reads back, another control within 8 pt (the calibration's error) of the points a step above or below the hit — the hit's column of a `near` grid, the scan's points either side. The dock settles vertically, so the find can take one of those and the read-back lands on the neighbour: the pill's mechanism, and the check fails on the pre-151 plan.
- **Warns**, counted on the head line: `FRAGILE` — a match only within 8 pt of a runner point, or a hit under 8 pt inside the element's top or bottom (aim the probe at the element's middle; the job carries on from where it lies); and a control beside a probe only an `expect` reads back — Save log sits under Focus in every column, so failing that would leave no probe for it.
- **Skips**, each with its reason (`SKIP` in `check.ts`): sign-in, kill/build/shutdown, `aboveKeyboard`, `sameWidthAs`, `shot`, waits (a settle here), an `absent` while a page field's keyboard is up, and ops needing dev data (`DEV_DATA`: category-suggest's chip). A plan not opening with `launch` starts on a fresh Home.
- **Dock probes are scans**: `scan: DOCK(x)` (`devcheck/ios.ts`, y 390→650; the mode row's toggles `DOCK(x, MODE_ROW)`, whose points land mid-toggle settled, settling and low), never a `near` — the dock's height follows the keyboard. The scan's role and label keep it off page content above the dock (Home's habit rows are toggles too). Keep `x` clear of the mode row's pills (`private`, `→ today`): x 300 is.

A first filter, not the proof: Chromium isn't Safari (fonts, AX text runs, the keyboard, scrolling, settle timing). A pass never proves an iOS row; a fail is almost always a plan to fix before the Simulator sees it.

## Probe job

The probe check's points on the real Simulator, without the full scenario's ~6 min: the `ios-probe` scenario (`scenarios/ios-probe.ts`) records every plan the scenarios send (`SOURCES`: ios-standalone, category-suggest — `ios-probe.test` fails when another scenario starts sending sim jobs), cuts each to its probes (`devcheck/probe-only.ts`, pure) and sends them as ordinary `sim` jobs, so the runner and `sim.sh` are unchanged and nothing needs a reinstall. The cut, per job:

- **Dropped:** `signIn`, `kill`, every `launch`, `shutdown`, and each **draft** — a `keys` through the `erase` that empties it (one with `in`: the latest open `keys` into that field; one without: the latest open `keys` of all) with everything between, which reads the draft — plus any read of a draft's text and any `expect` whose element (or `sameWidthAs`) went with it. Whole jobs it doesn't send (`NOT_PROBED`): relaunch (all kills), and capture-long — its points hold only after the full plan's kill, relaunch and 16 padding tasks, and cut it ran on a short page still filtered by done-form's search, where its Task tap failed on both dev runs that reached it (2026-11-12); ios-standalone and the headless check keep its points.
- **Kept:** `nav`, `find`, `tap` (`closes`, `hint`, `role` as sent), `absent`, the remaining `expect`s, `blur`, `scroll`, `wait`, `shot`, and a **filter** — a `keys` nothing erases (done-form's 6-letter search, read back), since the Done tap after it lands on whatever it filtered to. The setup titles its in-progress task with that text. Nothing erases it, so Tasks stays filtered to that task for the rest of the run.
- **Added:** `launch` at the head of the first job, which alone keeps the build guard (`readBuild`, `expectBuild`); `shutdown` after the last.

It never signs in: an app on the sign-in card reads `needs you: SIGNED_OUT` for the rest of the scenario — run ios-standalone (its launch signs in from the Keychain), then rerun. A `MISS` or any other assert fails the step, as in the full scenario (_Failures_); a low dock fails too — ios-standalone's known one needs its padded long page, which this job doesn't build. Each job has a 240 s timeout.

**Opt-in**: it runs on `--feature ios-probe` / `--scenario ios-probe`, or a change to its own two files, and is deferred (`ios-standalone runs in full this run`) whenever ios-standalone's slow steps run, since those read the same points (`probeSkip`, DEV-CHECK.md → _Slow tier_). Locally it is skipped: `pnpm ios-probe` is the local half. Mac time, measured on dev 2026-11-12 (sim step times): launch 64–220 s (a cold boot and the build guard's `readBuild`/`expectBuild` are most of it), capture 30–40 s, done-form 88–116 s (its search 17 s), review-chip ~35 s — about 4–5 min a run against the full scenario's ~6+.

## Keyboard

The sim boots as if a hardware keyboard were attached: a focused field shows only the accessory bar. Simulator.app's `ConnectHardwareKeyboard` pref does nothing under Device Hub. What works (trial T11–T12): two **in-guest** prefs, `com.apple.keyboard.preferences` `HardwareKeyboardLastSeen` and `AutomaticMinimizationEnabled`, both `false`, **written before boot** (a live write doesn't apply). Any HID typing (`axe type`/`axe key`) flips both back to 1 and hides the keyboard, so test text is typed by tapping the on-screen keys, found and confirmed with `--point`. `launch` re-arms and reboots whenever the prefs read anything but `0/0`; a sign-in (which types through HID) ends with a re-arm and reboot.

These prefs are undocumented, so an Xcode or iOS update can break the recipe for every branch at once. **No soft keyboard where one is due is `SIM_UNAVAILABLE/KEYBOARD_SETUP` — needs you, never a fail**; its note carries both prefs and the Xcode version, and every result records `device.xcode`, so a break lines up with the update. **After updating Xcode or the sim runtime**, run `pnpm mailroom sim-probe` and one devcheck with the iOS scenario; if keyboard rows say `KEYBOARD_SETUP`, re-trial the recipe (findings T11–T12) before trusting them. Then run `pnpm ios-probe --calibrate` (and after an `AXE_VERSION` bump): it compares the probe check's frames with the newest green run's AXe frames per job (listing a job with no green run) and is OK only with no frame 8+ pt away and both a keyboard-down and a keyboard-up frame compared — re-measure `KEYBOARD_VIEWPORT_H` and `SAFE` (`ios-probe/check.ts`) until it's OK, before trusting `pnpm ios-probe`. The trade-off: an app bug that stops a field taking focus would also read as `KEYBOARD_SETUP`; the row's screenshot tells which (`shots/NN-fail.png`). A dropped tap on the field no longer does: `tap` retaps a field that brought no keyboard (job …054323Z…-done-form-e8e2 read as `KEYBOARD_SETUP` before that).

**Everything that changes what a key does or when it lands is pinned**, in the same domain, read back at every readiness check (one `defaults export`). Pinned off: autocorrect, auto-capitalisation, spell check, predictions and the suggestion bar, inline completion, the "." shortcut, smart quotes and dashes, slide to type, and the hardware keyboard's own autocorrect, capitalisation and "." shortcut (`KeyboardAutocorrection` `KeyboardAutocapitalization` `KeyboardCheckSpelling` `KeyboardPrediction` `KeyboardShowPredictionBar` `KeyboardInlineCompletion` `KeyboardPeriodShortcut` `SmartQuotesEnabled` `SmartDashesEnabled` `KeyboardContinuousPathEnabled` `HWKeyboardAutocorrection` `HWKeyboardAutocapitalization` `HWKeyboardPeriodShortcut`). Pinned on: the slide-to-type, gesture and inline-completion tips, marked seen (`DidShowContinuousPathIntroduction` `DidShowGestureKeyboardIntroduction` `DidShowInlineCompletionEducationTip`).

- **If one isn't pinned:** the runner writes them all, quits the web app (it reads them at its next launch; no reboot needed) and reads them again. Still not pinned is `KEYBOARD_SETUP` naming the keys, and `launch`'s note says `keyboard prefs pinned (N were off)`.
- **Why:** the maintainer asked for typing to be as repeatable as it can be made, after job …233129Z…-done-form-80c5 typed "cdcgac" three times and kept "Cdc".
- **Evidence for the keys:** pest-plugin-simulator PR 32 (iOS 26.5) and WebDriverAgent. Seen to reach the web app on 2026-11-08, when typed text stopped being capitalised and the suggestion bar went.

**Not pinned:**

- **The keyboard layout** (`KeyboardsCurrentAndNext`, `en_US` QWERTY). Every key's spot is read before it is tapped, so a different layout is a `MISS`, never a wrong letter.
- **The keyboard's height.** With no suggestion bar it sits about 20 pt lower. `blur` and `aboveKeyboard` read the accessory bar where it is.
- **Dictation and emoji keys.** They are never tapped.
- **Whether `KeyboardContinuousPathEnabled` really stops slide to type.** Taps never slide, so it can't change a run.
- **`simctl erase`.** It drops them all, and the next readiness check writes them back.

## Sign-in and the password

The web app's refresh token lasts 30 days, so the runner signs in when `launch` lands on the Sign in card (≤ monthly, plus a ~14 s reboot). The app has no Sign out control. To sign the sim out by hand, delete the icon and re-add it: that landed on the Sign in card (P12), though the deleted icon came back once by the next run (P13) and stayed gone after a reboot the time after (P14), so check for one icon; two is `WEBCLIP_MISSING`. The password's only path: `security find-generic-password -s aperture-devcheck-dev -a <email> -w | tr -d '\n' | axe type --stdin`, the Keychain read time-capped like every tool (a Keychain access prompt nobody answers would otherwise hang the drain). Never argv, env, a file, a log, a result, a note or a screenshot. It is typed only while the sheet's **native** address bar — role `AXGenericElement`, id `URL`, label `Address`, owned by another process than the page (its `pid` differs from the Sign in button's) — reads dev's own Cognito host, `aperture-dev-<dev-account>.auth.us-west-1.amazoncognito.com`; checked before the email and again just before the password. The second check also requires the same bar pid as the first and a pid other than the form's, so a whole page drawn at another origin (one pid for both) fails. A page can't fake the process. Measured (mac-sim re-measure, P12): the value starts with U+200E, which the check strips; the id is `URL`; the bar's pid differs from both pages' and is unchanged with the password field focused. Web content never showed an `AXUniqueId`, but no element read was known to have a DOM id, so the id alone isn't trusted. Anything else is `SIGNIN_FAILED/COGNITO_HOST`, the password never read. Between those checks, point reads on the form drop their values (labels only: a typed password lives in `AXValue`); the address reads keep theirs, which is the host. **Focus is proven before the password moves.** Accessibility marks no focus between fields (P12: every key identical between Email focused and Password focused), and a dropped tap would type the password into Email, in clear. So after tapping the field the runner presses one harmless key (`axe key 27 --duration 0.2`, x; a bare `axe key` exits 0 and did nothing in the re-measure): Password must read one bullet with Email unchanged, and delete must return it to its placeholder. Anything else retaps once, then is `SIGNIN_FAILED/FORM_CHANGED`, the password never read. The bullet is U+2022, still masked at about 1 s and 4 s (P14). The keyboard's previous/next arrows also show focus through `enabled` (read by `--point` only, same process as the address bar), measured but not used: the key proves where characters land, and a second fixed-point read would only add a way to fail. A dropped tap on Aperture's Sign in is also retried once, and any failure after that first tap terminates the app, so no filled form survives for a later plan to read. iOS 27 masks a filled password field as bullets but leaks its length (trial T9b), so no read lands inside the password field after typing (the submit search skips its frame), and no screenshot is taken during sign-in. The fixtures plant the password in point reads and fail if it reaches anything the runner writes.

## The build guard

Dev is redeployed often, and an iOS step doesn't hold the dev lock for its own sake. Every job carries the expected `sha`; `readBuild` reads the **running** build from the Settings stamp, and results are credited to it. `expectBuild` relaunches once when a service worker still runs the previous build — that is the two-launch refresh row. The devcheck's own end-of-run check (`DEV_CHANGED_MID_RUN`) unproves every row if dev's served build moved.

## Runtime

The scenario's last job ends with `shutdown`, so the sim is off for the rest of the run, and `finish` sends nothing when the last job's result says `booted: off`; a later scenario's sim step must open with `launch`, or it reads `NOT_LAUNCHED`. Trial timings: cold boot 2.7 s, first app launch after a boot 11 s, warm relaunch 8 s, ~1 s per point read. The iOS scenario costs ≈ 6 min (one clean run, 374 s; +0.8 min on the monthly sign-in), so every one of its steps is **slow** (DEV-CHECK.md → _Slow tier_): a full run takes it when the branch touches what the rows can see (`APP` in `scenarios/ios-standalone.ts`: keyboard lift, the fields it covers, the shell and insets, auth, the service worker's config) or the iOS harness, or `--feature ios-standalone`; `--tier all` always does; otherwise its rows read `deferred`. (The user's call, 2026-11-05: first replacing "every full run", then narrowing `app/**`, which would have rerun it on all 13 app PRs of a day, about 3 h, against 6 of them and about 1.5 h.) So an iOS-only bug in another app file waits for `--tier all` or naming the scenario.

**Nothing heavy runs on the Mac while a sim job does:** no build, test suite or mailroom fixture suite (its stubs skip the sim but still load the CPU). Under load the sim's reads slow about threefold and keys drop, which reads as a failed row (_Failures_ → the Mac under load). So the Mac-side steps that prove a runner change go one at a time, before the devcheck, never beside it (_Proving the Mac side_).

How long these jobs take on a given Mac, and what the machine goes through meanwhile, is the sim bench's job (SIM-BENCH.md).

## Switcher kill

`kill switcher` is the user's own way out of an app, so the relaunch row keeps it beside `terminate` (which kills the
Home Screen app fine on the Mac) and `reboot`. Its steps, all in `jobs/sim.sh`:

- **Open** (`sim_switcher_open`): double home in one `axe batch`, then one tree read must show the switcher, neither the
  app nor the Home Screen; else pressed again (two presses in all). The only AXe-version-specific step (2.0.4: _Setup_);
  the batch's argv stays byte for byte, since ios-ci-probe's CI-side AXe routing keys on it (F209).
- **Card** (`sim_card`): a point read at `SIM_PT_CARD` must be Aperture's card (`AXGenericElement "Aperture"`, never
  Safari's), read until its frame holds still over two reads 0.5 s apart (four at most, else `moving`). No card: a
  fresh tree read, the background tapped only with the switcher in front, and the switcher opened again.
- **Swipe** (`sim_card_swipe`, `sim_card_rung`): up from the card's own frame, x mid its on-screen part, the start at the
  rung's share of its height (clear of the bottom edge), to `SIM_CARD_END_Y`. Then the process is checked now and up to
  six more times 0.5 s apart (`sim_web_gone`; only `pgrep`'s "no match" is gone, an error reads as alive). Alive: what's
  in front decides: the switcher takes the next rung, the app or the Home Screen (the swipe left it) is pressed again.
  A process that exits only after its polls, with the card gone or the ladder out, is the kill, noted `late`.
- **Leave** (`sim_switcher_leave`): the background tap, only with the process gone and the switcher still in front (it
  can close itself with the last card), so it never lands in a live app or on the Home Screen.

**The ladder**, rung by rung (`sim_card_rung`; AXe 1.8.0's `swipe` flags):

| rung    | start | duration | flags                                       | what it isolates                                         |
| ------- | ----- | -------- | ------------------------------------------- | -------------------------------------------------------- |
| `flick` | 70 %  | 0.3 s    | –                                           | aiming at the frame after it settles, and a 0.3 s flick  |
| `lead`  | 70 %  | 0.3 s    | `--pre-delay 1 --post-delay 0.5`            | only the lead-in: a lost first touch (AXe issue 71)      |
| `drag`  | 88 %  | 0.6 s    | `--delta 20 --pre-delay 1 --post-delay 0.5` | a slower, finer drag from lower on the card: by distance |

**The note** records the card and every swipe, pass or fail, so every relaunch result is a sample:
`; card 239,136 306x664 r2; s1 flick 339,600 alive>sw; s2 lead 339,600 gone@0.5` (`r<n>`: reads until it held still;
`frame?`: aimed at the read spot instead; `alive>sw|app|home`: what was in front after; `gone@<s>`; `late`: the card and

**Why (2026-11-17):** the old kill, one 0.2 s swipe from a fixed 340,560 to 340,40, then once more, passed 10 of 23

## Input-gap trial

AXe can report a tap done that iOS never got. AXe issue 71: on Xcode 27 with iOS 27, a new `axe` process can lose its first touch before the sim's input service is up, and the runner spawns one per tap. The runner's read-backs catch those drops and retry them. The trial measures which way of sending cuts them at the source, and where.

The first trial (2026-11-08) typed and erased words in the capture bar and found key drops rare: about 1 in 250, with no difference between variants. The drops that broke runs were element taps after a pause instead: the Home Screen icon (4 of 4 in one run), Capture (2 of 2), Cancel, the mode row's Task. So the default trial taps those, each after a pause. It keeps keys in, because the done-form's dropped keys then failed devchecks in five lanes (2026-11-08 to 11-15). The keys trial stays as `--keys`.

- **Variants (`via`):** without it, every op sends as `tap`, and the scenarios never set it.
  - On `launch` (its icon taps) and `tap`: `tap`, the plain `axe tap`; `hid`, `AXE_HID_STABILIZATION_MS=500` in that tap's environment; `batch`, one `axe batch` that sleeps 1 s and then taps.
  - A `tap` with `via` needs a read-back to count by: `closes`, `selects`, or a text field's role (the keyboard must come up). Anything else is `BAD_OP`.
  - On `keys` and `erase`, which need `in`: `tap`, `hid` and `batch` as above, plus `post` (`--post-delay 0.5`, a 0.1 s sleep after) and `batch15` (a 1.5 s lead).
    - `batch` and `batch15` read every key at its spot first. A key off its spot is `MISS`, and no tap is sent. Then one `axe batch` taps them all, 0.6 s apart: one HID session per word.
  - Retaps, retypes and extra deletes go the same way as the first.
- **Held still before the tap:** a trial `tap` re-reads its target's centre until two reads 1 s apart give the same frame, at most 3 reads. A dock still settling (PR 156: taps at y 374 and 402 on a dock that settles at 464) is a moving target, not a dropped tap. A target that never holds still, or leaves its centre, is tapped where it was last seen and its line is uncounted (`moving`); a read that hangs is tapped at find's spot, uncounted (`unread`). A field whose keyboard is already up before the tap is uncounted too (`kbup`): the keyboard couldn't show the tap landed. The deny check runs on the element about to be tapped, after these reads.
- **What gets counted:** each `via` tap or launch writes exactly one line to the job's `trial.jsonl` and its step note (`via batch, drops 1`), from its first read-back, or from its failure when it ends before one. Keys and erase write theirs at the read-back; one that fails before it leaves none, and the table names that step's failure (or `not run`, for a step the round never reached).
  - **icon:** still the Home Screen at a poll means 1; the web app in front at a poll, or at the end, means 0. Anything else (a stale tree, Spotlight) counts nothing. A relaunch's icon tap (an app left mid-typing) isn't counted: the first one landed.
  - **closes:** the element gone means 0. Still there with the same frame on both looks means 1.
  - **selects:** the toggle on means 0. Still off on both looks, same frame, means 1.
  - **field:** the keyboard up, at once or late, means 0. None twice, with the field still at its spot, means 1.
  - **keys:** the letters missing, at least 1 when the field reads wrong. Only from a read that is the field: `in`'s role and label (empty, its placeholder the value), or an unlabelled run whose text is the typed text with letters missing. A checkbox's `0` where the field was counts nothing.
  - **erase:** the letters left.
  - **Uncounted:** `drops` is `null`, and `un` says why: `moving`; `moved` (the frame changed between the tap and the look); `gone` (something else at the field's spot); `unread`; `kbup`; `already` (the toggle was on, so no tap); `notfield` (a keys or erase read that wasn't the field); or a tap's or launch's failure (`MISS`, `DENIED`, `AX_TIMEOUT`, `AXE_FAILED`, …), when it ended before a read-back. `sendMs` is `null` when no tap went out. A count that can't be read is never a zero.
  - The first line of `trial.jsonl` holds the Mac's `vm.loadavg` at the job's start and end.
  - The read-backs still retry, and fail as `ICON_TAP_DROPPED`, `TAP_DROPPED`, `TYPED` or `ERASED`. A trial hides nothing.
- **A round** (`sim-trial.ts` → `tapPlan`) is one sim job of 62 ops, timeout 600 s. It launches with the round's first variant, signs in and goes to Tasks. Then one cycle per variant:
  - its `launch` (the icon, counted);
  - `Bulk add` (`closes`);
  - in its dialog, the field tapped, found once settled, and the round's 6-letter word typed and erased with exactly 6 deletes;
  - `blur`, then `Cancel` (`closes`), tapped with the keyboard down because the keyboard lifts the dialog;
  - `Capture` (the field);
  - the mode row's `Task`, then `Log` (`selects`);
  - `blur`.
  - Every counted element tap follows a `wait` of 3 s or more plus its own reads: 5–6 s with no touch. The icon tap follows the home press and the icon's tree reads, as in a devcheck. The variant order rotates each round, so a change in load lands on every variant alike.
  - Bulk add, its field and Cancel need no dev data and make no writes: Cancel drops the draft.
  - Their spots come from the probe check against the stub app: Bulk add 318,212 102×34; Cancel 205,648 79×38 with the keyboard down; the field 40,422 360×210 down and 40,219 up. The smoke round is the proof on the Simulator.
- **Running it:** `pnpm mailroom sim-trial --tag <t>`. This needs no dev lock and no deploy.
  - Start on a fresh sim: `pnpm mailroom sim-shutdown`, then `pnpm mailroom sim-probe`, then about 3 minutes of settle. A boot's indexing load would otherwise land on round 0.
  - First a smoke round, `--tag smoke --round 0` (about 6 min). It proves the spots and the toggle read-back before the window is spent.
  - Then the full trial: 6 rounds, about 40 min with pickup and retaps. Ask the hub for 45. `--round N` reruns one round (same order and word) when a load spike spoiled it. A round that aborts mid-typing can make the next launch fail `LANDMARK`; rerun that round.
  - `--keys` runs the keys trial instead: 5 rounds (about 15 min), one word typed into the capture bar and erased per keys variant, all five of them.
  - `--icon` runs the icon trial instead (below): 6 rounds of 10 launches, about 22 min; hold 30.
  - It prints, per target and variant, the counted taps, the drops, the drop %, the ops retried, the median ms per tap and the uncounted or not-run steps. Totals per variant follow, element taps and keys apart, then each round's load. The files stay in `.hostjobs/results/<id>/`.
  - **Exit codes:**
    - 1: a round failed, or a step went uncounted, not run or unreadable. The table names it, and a closing line counts them by reason.
    - 2: a bad `--tag` or `--round`.
    - 3: the sim couldn't finish a round (a hung read; the other rounds still run), or the Mac never answered (the trial stops there).
    - A non-zero exit can leave the sim booted (`pnpm mailroom sim-shutdown`).
  - A `closes` 0 whose next step then fails `MISS` is uncounted (`unconfirmed`): the page wasn't where the read assumed.
  - `ms/tap` is wall time: it includes the key reads and a batch's lead sleep. Read it as the cost per tap, not the speed of the method.
- **Conditions:**
  - The container runs in a VM on the Mac, so other sessions' tests count as load. Get the hub to call a quiet window.
  - The booted sim alone loads the Mac (`loadavg` 12–18 seen with the container quiet), so a quiet run is a quiet container, not an idle Mac.
  - A round's reads slow about threefold under load, and a round can then run out of its 600 s; the steps it never reached show as not run.
  - The done-form's key drops came under devcheck load, which a quiet run doesn't reproduce.
  - A loaded run (the fixture suite in a loop, the load chosen on 2026-11-08) can follow, judged against the quiet run's rates.
- **The icon trial** (`--icon`, `sim-trial.ts` → `iconPlan`). The 11-16 trial found the drops on the Home Screen icon (4 of 9 first tries, and every icon tap in 2 of 6 rounds), and neither `hid` nor `batch` fixed them. So it measures the icon alone, and the cause.
  - A round is one job of 10 `launch` ops with `via: tap`, `wait 3` between, no sign-in (launch takes either landmark). `settle`, the wait after each home press, alternates 1 s and 3 s, the first flipped each round: 30 launches per arm in all.
  - **Attribution:** during a trial job the runner streams the sim's own log (`simctl spawn … log stream`, `dtuhidd` and any "No active service" line) and at the end gives each tap the "No active service, dropping event" lines inside its window, its send plus 1 s. That line is AXe issue 71's drop: the touch reached a HID service with no session. Only counts leave the job; the stream's text is deleted.
  - Each launch line gets `settle`, its `taps` (each `{d, hid, frontMs}`: 0 landed, 1 dropped, null unknown; the no-service count; for a landed one the time to the look that saw the app, an upper bound in about 1 s steps) and `hidOther` (no-service lines in the op outside its taps: a home press, the scroll). The header's `hid` says whether the counts can be trusted: `ok`, else `why` (`died`: the stream wasn't up at the end; `badline`: a line that isn't the stream's JSON, or a timestamp that won't parse; `loss`: the log said it dropped messages). A tap's `hid` is a number only when the capture is shown listening through its window: a line inside it, or lines on both sides (the stream can start late on a cold boot, and lose its buffered tail at the stop). Otherwise it's `null`, never 0.
  - **What a zero means:** a dropped tap is `no service` (a count of 1 or more: issue 71), `no such line` (0, from a capture that heard `dtuhidd` in that round: the tap reached iOS and did nothing), `unproven` (0 from a round whose capture never heard `dtuhidd`, which can't tell the two apart) or `unread` (no trusted count). The table's control column counts landed taps that logged no-service lines too: as often as on drops, and the line means nothing. Unproven and unread make the trial exit 1: the point is the cause.
  - The table adds every icon tap, the reset retaps too: sent, landed, dropped, unknown, the median `frontMs`, and the attribution per dropped tap; and each round's capture state.
  - **Before the first run on a Mac:** check the stream once by hand, with the sim booted: `xcrun simctl spawn booted log stream --level debug --style ndjson --timeout 10s --predicate 'process == "dtuhidd"' | head -5`. It must print JSON lines carrying `timestamp` and `eventMessage` (and `eventType`: a record whose type says `loss`, when the log dropped messages, makes that round's counts untrusted, `why: loss`).
  - **Results (2026-11-16):** 1.8.0 dropped 4 of 53 first icon taps and stuck in 2 of 6 rounds; 2.0.4 dropped 0 of 60, stuck in none, and taps in about 0.27 s against 1.25 s. Neither logged a "No active service" line, so the 1.8.0 drops didn't carry issue 71's log signature, yet 2.0.4's transport fixes them. On 2.0.4 a devcheck's keys, erase, blur, nav, finds and expects passed, but the app switcher kill doesn't (the setup row above).
  - **AXe 2.0.4 against 1.8.0:** run the icon trial on 1.8.0, back up 1.8.0's install, unpin it (`brew unpin axe`: a pinned formula ignores `brew upgrade`) and upgrade (Homebrew 6 won't load or link a formula from an untrusted tap: `brew trust --formula cameroncooke/axe/axe` first, the formula only, not the whole tap; the same for a rollback's `brew link axe`, which restores the 1.8.0 keg copied aside; an uninstall can also remove dependencies nothing else needs, `rav1e` on 2026-11-16); `axe --version` must say 2.0.4 (a newer latest is refused by the pins: roll back), then pin again, then `pnpm mailroom sim-probe --sign-in` (it exercises `type --stdin`), a smoke round, and the same icon trial. 2.0.4 becomes the only pin if it's clean; otherwise restore the copy.
- **When to rerun:** after an AXe bump (one with PR 73's connection priming) or a new Xcode. The results and the decision live in the PR that ran it.

## Security

The sim job extends the mailroom's model (MAILROOM.md → _Security_). At worst a compromised container can make the Mac boot the dedicated sim and run allowlisted ops inside the Aperture web app as the dev test user, ≤ 10 min per job and 5 jobs per drain, and read that sim's screenshots — the same blast radius the devcheck's own API token gives it. Nothing on the Mac's screen, files or other Keychain items; `jobs/sim.sh` makes no network call itself (statically checked: no `curl`, `openurl` or `osascript`), runs every tool by name with a time cap (`sim_cap`), and opens no URL from a job.

**AXe under the dependency rule (B):** HID injection and accessibility reads over Apple's private Simulator automation channels, with version-specific edges already bitten (issues 65, 71, 76). One Mac-side binary, not a repo dependency. Rolling our own means an XCUITest runner target (Swift, an Xcode host project, code signing) on the same private APIs: strictly more to own.
