# CI bot — Claude's GitHub identity

Claude pushes feature branches, deploys a pushed commit to dev and reads dev logs as a **GitHub App, `aperture-cc-bot`**, through `pnpm bot …`. It never opens or merges PRs: **the user opens every PR**, because a squash commit's author is the PR opener and `main` stays the user's (decided 2026-10-29; since 2026-11-01 the Mac mailroom opens it with a PR-only token of the user's — MAILROOM.md). `main` needs the user's code-owner approval or admin bypass, and the bot is not a bypass actor. The container's own GitHub token (a read-only PAT, COI-SANDBOX → _GitHub access_) stays as it is, for fetches and reads.

Built 2026-10-13 (ci-bot branch, part of "Zero-Touch PRs"). Its dev deploys (`pnpm bot deploy-dev`) stayed **off** until dev ran in its own AWS account (_Dev deploy blast radius_): the `dev-account` PR moved dev there, and the `dev-cutover` PR turned dispatch on and retired the user's `dev` push path (_Setup_ step 8). `DEV_DEPLOY_ISOLATED` is now the pause switch (the end of _Dev deploy blast radius_).

## Commands

Run from a worktree root (`pnpm bot` is a root script: `node scripts/src/bot/cli.ts`, plain Node type stripping, builtins only).

Tokens are minted per invocation (JWT → `GET /app/installations` → `POST …/access_tokens` narrowed to `aperture` and the row's permissions), held in memory, and reach `git`/`gh` through env only — a credential helper reading `$APERTURE_BOT_TOKEN`, or `GH_TOKEN`. Never argv, never a file. The JWT needs `Authorization: Bearer`; `gh api` sends `token …`, which GitHub rejects for a JWT (401 "could not be decoded"), so the CLI uses `fetch`.

Workflow changes: the App has no `workflows` permission, so GitHub refuses a bot push that touches `.github/workflows/` — the user pushes such a branch. `pnpm bot deploy-dev` dispatches **any** branch that changes `.github/` (workflows, `.github/actions/`, `CODEOWNERS`, `dependabot.yml` — the bot may push the rest) **on its own ref**, so its workflows are what run on dev. That is how a CI, deploy or Actions-version change gets tried before it reaches `main`, which deploys prod with no pause. **The `dev` environment admits `main` only, plus such a branch by name**, else its deploy job is refused (the CLI says so). The user admits it the first time Claude asks — folded into the same one-line handoff as their push for a workflows branch — with `cd /Users/rahuldatta/Coding/Personal/aperture && gh api -X POST repos/radatta/aperture/environments/dev/deployment-branch-policies -f name=<branch> -f type=branch`, and removes it at Cleanup, folded into the `git branch -D` handoff (or when the PR is abandoned), with `cd /Users/rahuldatta/Coding/Personal/aperture && gh api repos/radatta/aperture/environments/dev/deployment-branch-policies --jq '.branch_policies[] | select(.name=="<branch>") | .id' | xargs -I{} gh api -X DELETE repos/radatta/aperture/environments/dev/deployment-branch-policies/{} && gh api repos/radatta/aperture/environments/dev/deployment-branch-policies --jq '.branch_policies[].name'` (the listing at the end shows it went: the DELETE is silent when the name doesn't match). Not `**`: the `workflows` check doesn't stop the bot pointing a new branch at an existing commit whose YAML differs from main's (probed 2026-11-01: a bot push of a branch at main's pre-PR-78 commit was accepted), so an every-branch policy would let it dispatch any old commit's workflows — older timeouts, older checks — with the dev credentials. ## Dev deploys

`deploy-dev.yml` (dispatch only; on `ref: main`, or on the commit's own branch when it changes `.github/`): job `verify` checks the sha is 40-hex, on a pushed feature branch (not main/master/dev) and contains `origin/main`. Dispatched on main, it refuses a `.github/` change — main's YAML would run, so the change would silently go untested; dispatched on a branch, it requires that branch's head to be the sha. It then classifies the change with the checked-out ref's classifier against **what dev serves now** (`base`: the last successful dispatch's sha when newer than main's last deploy; empty → `origin/main`; unknown → `full`). Job `deploy` calls `deploy-stage.yml` with `ref: <sha>`, which checks it out and exports `APERTURE_BUILD_SHA`. No `check` job: the PR runs CI; dev is for trying things.

**Run-name contract** (with dev-e2e's devcheck): `deploy-dev <40-hex sha> <key>`, key `<branch>-<base36 ms>` (`-r` appended on the one retry after a `cancelled`). A dispatched run's `head_sha` and branch are main's on a main-ref dispatch and the feature's on a branch-ref one — so the devcheck's `pickDeployRun` must not filter by branch; it matches `^deploy-dev ([0-9a-f]{40}) (\S+)$` and the build marker reads `APERTURE_BUILD_SHA`, falling back to `GITHUB_SHA`.

**Whichever deploys last wins.** A merge to `main` deploys dev from main (deploy.yml) over a dispatched branch; a dispatch queued behind main's dev job deploys over main. `deploy-stage-dev` queues them, never runs both. A main deploy's mode comes from main's own diff, so a feature's infra can linger on dev until the next `full` deploy. The devcheck's build-marker check notices any change mid-run; re-run `deploy-dev`.

**Two lanes into the dev account** (built with `dev-account`): a `main` push is merged, reviewed code, so deploy.yml deploys it to dev in the **`dev-main`** GitHub environment (deployment branches: `main` only) as `aperture-github-dev-main`, through a second CDK bootstrap (qualifier `devmain`) whose execution role the freeze SCP exempts — shape-changing merges deploy, and prod follows, with no hand step. A bot dispatch stays in the **frozen lane** (as did the `dev` push, until `dev-cutover`): the `dev` environment, `aperture-github-deploy-dev`, the stock bootstrap. What keeps the bot lane out of it, all in the guardrails SCP: only the dev-main role (and break-glass) may assume a `devmain` bootstrap role (`OnlyMainAssumesItsLane`); nothing but break-glass may change or pass one, or any `aperture-github-*` role, bar the devmain deploy role passing its own exec role (`NoLaneTampering`); every stack call must name its role, since CloudFormation reuses a stack's stored role — after main's deploy, the exempt one — for a call that names none (`NameTheStackRole`); and nothing but break-glass and devmain's publishing role may write devmain's asset bucket, its version parameter or its `CDKToolkit-devmain` stack — the publishing role's own policy reaches only the bucket (`DevMainBootstrapIntact`); nothing in dev may create an S3 access point, a second address for a bucket (`NoCostSinks`) — cdk-assets skips a key that already exists, so a planted template or zip would otherwise deploy. The exempt lane is otherwise under every other SCP and the kill. Each lane has its own asset bucket, so dev carries no CDK provider function (the freeze denies the bot lane new provider code, and a provider's code location would move on every lane switch): dev owns its log groups and its site bucket has no auto-delete. The lanes' templates differ only in the `BootstrapVersion` parameter and the asset bucket (`cdk/src/config/lane.ts`). **Lockstep:** a CDK CLI bump that raises the required bootstrap version needs both dev bootstraps upgraded (`cdk bootstrap`, as break-glass, once with `--qualifier devmain --toolkit-stack-name CDKToolkit-devmain`). The bot's `Actions: write` can re-run an old main Deploy run, which redeploys that older merged commit through the exempt lane — reviewed code, so a nuisance, not an escalation. So can the bot lane make main's next dev deploy fail (and prod wait) without gaining anything — a stack policy, a cancelled update, a CloudFormation hook, a code-signing config, the devmain bucket's encryption setting; break-glass clears it. deploy-stage refuses lane `devmain` unless the run is a `main` push of its own commit, so a dispatch on `ref: main` can't carry branch code into it. The lane's first live run is a merge — GitHub admits `dev-main` only from `main`. **A stale branch:** `verify` refuses a branch that doesn't contain `origin/main`, so one behind a shape-changing merge is told to rebase before it reaches the freeze; a rebased branch whose shape differs from what dev runs now (another dispatch deployed a different shape between) fails in `Deploy stacks` with `explicit deny in a service control policy`, and deploy-stage's _Unstick a refused dev deploy_ step rolls it back — open the freeze for it (_Kill switch_ → _Opening the freeze_) or wait for main's next full deploy.

**What dev serves now** is judged by the dev-stack _job_ (`deploy-dev / deploy` in deploy.yml, `deploy / deploy` in deploy-dev.yml): the newest finished one decides. A main run finishes with prod, long after dev, so run times would mislead. A main deploy counts only when its `Deploy stacks` step ran: an app- or docs-only main merge leaves whatever infra a dispatch put on dev, so the base stays that dispatch (the cost: a few more `full` dispatches after such merges). A dev job still running, one that failed (a possibly half-applied stack), or a deciding job further back than the last 10 runs makes the base `unknown` → `full`. A `dev` push counts too — the path was retired at `dev-cutover`, but the admin bypass could recreate the branch, and every older `deploy.yml` deploys it: when one is the newest dev deploy, the base is `unknown`. A dispatch always publishes the frontend (a docs-only `none` becomes `app`), so the build marker always moves to the dispatched sha.

**The lock outlives the deploy:** `deploy-dev` renews it whenever less than 15 minutes remain while it waits, and once more on success, so the devcheck starts with a full 45 minutes. A run that finishes unsuccessfully releases it; a timeout or API error leaves it to expire, since the run may still be deploying.

## Dev lock

`refs/locks/dev` → an annotated tag on the feature sha (it must be pushed) whose message is `{"branch","sha","expiresAt"}`. Acquire = create the ref (a 422 means held). Holder = branch. TTL 45 minutes, `renew` to extend; an expired or unreadable lock is taken over by the next `acquire` (it re-reads the ref and deletes it only if it still points at the tag it judged expired). Residual races: two sessions taking over the same expired lock within that window can both believe they hold it, and a holder's `renew`/`release` (read, then PATCH or DELETE) can clobber a take-over that lands in between — the devcheck's build-marker check catches the result. GitHub's Git refs API has no compare-and-swap.

**Waiting for it:** another branch's lock means wait, never work around it — send the two messages the refusal prints, then `pnpm bot lock wait` in the background, which wakes the session when the lock frees or lapses; then `deploy-dev` takes it (`docs/ops/HUB.md` → _Lock etiquette_). Every lock read or change the bot makes also lands in the board's cache, so `board.sh status`, the SessionStart hook and the status line show the holder (`docs/ops/SESSION-BOARD.md` → _Dev lock line_).

Until dispatch was on, the user's `dev` push was guarded by the session board's local dev lease instead; session-comms removed it, so `refs/locks/dev` is the one lock.

## Dev logs

`fetch-dev-logs.yml` (dispatch only, `ref: main`) runs in the **`dev-logs`** environment, assumes `aperture-github-logs-dev` and runs `scripts/aws/fetch-dev-logs.mjs`: `filter-log-events` (or Logs Insights with `--query`) per group for one window, up to 20 000 events a group, into an artifact kept 3 days.

- **Dev only, three ways:** the allowlist (`scripts/src/bot/logs-spec.ts`: `bff`, `mcp`, `finance-sync` → `/aws/lambda/aperture-<x>-dev`), checked by the CLI and again on the runner; the role reads only those three groups (`cicd-stack.ts`); the environment admits only `main`'s YAML.
- **Why its own environment, not `dev`:** AWS trusts a job by its environment (`…:environment:<name>`). A job in `dev` could assume the dev **deploy** role too; `dev-logs` gives log reading its own subject that only the read-only role trusts. "Deployment branches: `main`" names which branch's workflow code may run there — not which logs it reads.
- **Window ≤ 6 h; loop guard ≤ 10 fetches an hour** per worktree (`localNotes/devlogs/fetches.jsonl`) — then the CLI stops and says so. Actions minutes are the budget; reading CloudWatch costs next to nothing (Insights bills per GB scanned; dev groups are tiny).
- Prod logs stay the user's to fetch.

**Retention:** prod's BFF and MCP groups were created by Lambda on first invoke and never expired. `logRetention` on both prod functions (`app-stack.ts`) sets 90 days through CDK's `Custom::LogRetention`, which tolerates the existing group. Dev, in its own account since `dev-account`, owns its two groups outright (14 days, deleted with the stack; _Dev deploys_ → _Two lanes_). Deprecated but supported in aws-cdk-lib 2.263; `logGroup` would try to create the group and fail (AlreadyExists) — moving to it needs a `cdk import`, a follow-up. finance-sync already owns its group (30 days).

### Dev deploy blast radius — decided 2026-10-13: isolate first; built 2026-10-30, moved to its own account 2026-10-31

The row above is the real exposure, and it predates the bot: the dev deploy role reached the account through the shared CDK bootstrap roles. What the bot changes is that nobody runs the deploy by hand any more. **The user's call: isolate dev first.** The stock bootstrap's **deploy role** may create, update and delete any stack (an `UpdateStack` without a `RoleARN` reuses a prod stack's admin execution role), its **lookup role** holds `ReadOnlyAccess` (every row of `aperture-prod`), and its **execution role** is admin.

PR 72 (`dev-bootstrap`) built a dev-only bootstrap inside the shared account. The cost analysis that followed (2026-10-30) changed the target: **the user's worst case for a rogue, buggy or prompt-injected agent is about $1 an incident, with $0 standing cost** — money over prod uptime, so a kill that stalls the pipeline is acceptable as a signal. In-account IAM couldn't bound money, so **dev moved to its own AWS account** (`dev-account`, INFRA §2–§3): prod is out of reach by construction — no dev credential exists in the management account — and the dev account's SCPs, which nothing in it can remove, take away the levers.

**What's capped, and how:**
- **Compute** — the dev account's Lambda concurrency quota: 10 today, AWS's reduced new-account quota, which it raises with use (Support case 179351213900245 asks for 30; Service Quotas refuses a request below the 1,000 default). Until then a devcheck's page-load burst gets 429s ([DEV-CHECK.md](DEV-CHECK.md) → _Known 429s_). Dev may not raise it itself (`servicequotas:Request*` denied); the freeze SCP keeps every function at its deployed memory (512 MB) — main's own deploy excepted (_Two lanes_) — and timeout (15 s; 300 s for finance sync), so a kill's in-flight tail is at most those, and denies new functions, Function URLs, permissions and async destinations. No reserved or provisioned concurrency, recursion-detection changes or event-source mappings.
- **Everything else AWS sells** — the allowlist SCP denies every service outside the ~14 dev uses (EC2, Bedrock, SageMaker, SNS…; of SSM only Parameter Store, of ACM only reads), every region but us-west-1 (closes Lambda@Edge), and the paid add-ons of the allowed ones (invalidations, real-time logs, log subscriptions, metric filters and anomaly detectors, KMS keys, exportable certs, S3 replication, acceleration, request metrics, Object Lock and any storage class but Standard, DynamoDB restores, backups, global tables and Contributor Insights).
- **Grants that would outlive a kill** — an SCP binds only the dev account's own principals, so the freeze denies whatever would let another account's principals, an unauthenticated caller, or a service act for dev: bucket policies, ACLs and lifecycle rules, a table resource policy, new roles and role trusts, new buckets and distributions, and the user pool (no self-sign-up, new clients or created users — monthly active users bill).
- **CDK's provider functions** (LogRetention, S3 auto-delete, the OIDC provider) have 15-minute timeouts, so the freeze also denies new code in them (`function:Aperture…`); the app's own functions (`aperture-…`) stay open to code updates — that is what a dev deploy is.
- **DynamoDB** — an on-demand ceiling on dev's table and GSI1 (100 read / 50 write units each), which the freeze keeps (no `UpdateTable`).
- **The deploy job** — 30 min (`deploy-stage.yml` `timeout-minutes`), in YAML the bot can't edit.
- **Logs and internet egress** — no AWS cap exists for either, so the kill switch bounds them in time.

#### Kill switch

```
dev account (ApertureDevGuard)                 management account (ApertureOrg, us-east-1)
aperture-kill-duration   ≥ 600,000 ms/min ×2 ┐
aperture-kill-duration-hour ≥ 600,000 ms/h   │
aperture-kill-duration-3h ≥ 300,000 ms/3 h   │
aperture-kill-invocations ≥ 3,000/min        ├─ ALARM ─▶ rule aperture-kill-forward ─▶ default bus ─▶ rule aperture-dev-kill
aperture-kill-log-bytes  ≥ 100 MB/min        ┘          (role aperture-kill-forwarder)                 ├─▶ Lambda aperture-dev-kill
                                                                                                         │     1. attach SCP aperture-dev-kill (deny-all)
dev budget > $3 actual (8–24 h lag) ─────────────────────▶ topic aperture-dev-budget-kill ─────────────┤     2. every dev function → concurrency 0
                                                                                                         │     3. bff + mcp Function URLs → AWS_IAM
                                                                                                         │     4. dev's CloudFront distributions → disabled
                                                                                                         └─▶ email (raw alarm; also a failed kill, via the Lambda's failure destination)
```

- **Why four moves:** the deny-all SCP stops every API call a dev principal makes (the runner, SDK loops, a schedule's role) — but some compute and egress happens without one. Lambda's own async queue (events queued before the kill retry for up to 6 h) and a public Function URL invoke as the service, so every function goes to concurrency 0; the URLs also switch to `AWS_IAM` (403, and the app goes dark — CloudFront's origin requests aren't signed) in case the throttle fails; and CloudFront serves its cache and reads S3 as a service principal, so the distribution is disabled. All four run through the dev account's break-glass role, which the kill SCP exempts.
- **Latency:** about 2–4 min from a spike (1-min alarm periods, then EventBridge and the Lambda); up to an hour for a slow drain the hourly alarm catches, and up to three for one the rolling three-hour alarm catches (a period under a day is evaluated every minute over a sliding window). Thresholds sit well above a full devcheck; re-tune them from a measured run. Five alarms: with prod's five, the free ten (the free tier is shared across the Organization).
- **Unkill** (user, Mac) — first find out what tripped it (`pnpm bot logs`, the alarm in the email), and redeploy main to dev if a branch is suspect. Wait until nothing will re-kill: if the kill emailed a failure, its retries finish first (about 3 min, ending in the failure email); and all five alarms must read `OK` — a per-minute trip also pushes the hourly and three-hour sums past theirs — `aws cloudwatch describe-alarms --profile aperture-dev --region us-west-1 --alarm-name-prefix aperture-kill- --query 'MetricAlarms[].[AlarmName,StateValue]' --output text`. Then detach the SCP and let the kill Lambda reverse moves 2–4 (only a direct invoke with this payload can — a trigger only ever kills): `cd /Users/rahuldatta/Coding/Personal/aperture && aws organizations detach-policy --policy-id <KillPolicyId output of ApertureOrg> --target-id <dev account id> && aws lambda invoke --region us-east-1 --function-name aperture-dev-kill --cli-binary-format raw-in-base64-out --payload '{"action":"restore"}' /dev/stdout` — `aws lambda invoke` exits 0 even when the function failed, so check the output has no `FunctionError`. A distribution takes a few minutes to re-enable. A dev stack whose first create failed (`ROLLBACK_COMPLETE`) blocks every later deploy in both lanes: the CDK CLI deletes it without naming a role, which `NameTheStackRole` denies — delete it as break-glass, `aws cloudformation delete-stack --profile aperture-dev --region us-west-1 --stack-name <stack>`. If the kill landed mid-deploy and left a dev stack in `UPDATE_ROLLBACK_FAILED`: the rollback runs as the stack's own role (the CDK execution role), which the SCPs bind — so detach the kill SCP first (and the freeze, if that deploy changed a function's shape), then `aws cloudformation continue-update-rollback --profile aperture-dev --region us-west-1 --stack-name <stack>`. **The budget's $3 kill fires once per month** (a Budgets notification fires once per threshold per period), so after an unkill that month only the alarms remain.
- **Drill** (after any change to either guard stack, and quarterly): `aws cloudwatch set-alarm-state --profile aperture-dev --region us-west-1 --alarm-name aperture-kill-duration --state-value ALARM --state-reason drill`; expect the email, the SCP on the account (`aws organizations list-policies-for-target --target-id <dev account id> --filter SERVICE_CONTROL_POLICY`), both URLs at `AWS_IAM`, `aws lambda get-function-concurrency --profile aperture-dev --region us-west-1 --function-name aperture-bff-dev` at 0, and the distribution disabled. The first drill also settles one open question: whether Lambda accepts a reservation of 0 below the 100-unreserved floor (the quota: _What's capped_ → Compute). **If it refuses, stop before merging `dev-account`:** moves 3–4 still close the URL and CloudFront paths, but not Lambda's async queue (events queued before a kill would run for up to 6 h), and every later kill would retry and email a failure. The planned fallback is a move that sets each function's async event age to 60 s with no retries (`PutFunctionEventInvokeConfig`, as break-glass). Then unkill and set the alarm back to `OK`.

**Opening the freeze** — a branch that changes a function's shape (an env var, memory, a new function or URL), the table, a schedule or a grant (a bucket policy, a new role — but not a changed policy on an existing role: an inline `iam:PutRolePolicy` passes the freeze, proven live 2026-11-01 by `attachment-s3-delete`, run 41353956072) fails its dev deploy with `explicit deny in a service control policy` (CloudFormation's own rollback is refused too — it re-applies the configuration as the same frozen role — so in the frozen lane deploy-stage's _Unstick a refused dev deploy_ step continues it with `cdk rollback --force`, skipping the resource the freeze refused both ways, so it never changed; without it the stack would stick in `UPDATE_ROLLBACK_FAILED` and block both lanes. A run cancelled or timed out mid-deploy skips the step; the next dev deploy fails at once on the stuck stack, and its own step unsticks it. Main's lane never skips: a failed rollback there is a real fault — break-glass `continue-update-rollback`, below) — and so can an `aws-cdk-lib` bump (a dependency PR included) that changes a bucket policy CDK manages, a role trust, or adds a Lambda permission, or adds a CDK provider function (dev's app stacks carry none; a test pins it). So do the user pool's clients and domain (`UpdateUserPoolClient`, `CreateUserPoolClient`, `UpdateUserPoolDomain` sit under the freeze's wildcards): a change to callback URLs — `CLAUDE_CONNECTOR_CALLBACK_URLS` included — scopes or token validity. A merge to `main` needs none of this — main deploys through the freeze-exempt lane (_Dev deploys_ → _Two lanes_); only a dispatch of such a change does. The user detaches the freeze, deploys, and reattaches: `cd /Users/rahuldatta/Coding/Personal/aperture && aws organizations detach-policy --policy-id <freeze id> --target-id <dev OU id>`, then the dispatch — **wait until its run has finished** (a freeze reattached mid-deploy refuses the rollback of a change that already applied, and the unstick step would then skip it, leaving the function in the branch's shape while the stack records the old one) — then `aws organizations attach-policy --policy-id <freeze id> --target-id <dev OU id>` (ids: `aws organizations list-policies --filter SERVICE_CONTROL_POLICY`); a dispatch then runs in the frozen lane, as always. **Read the branch's diff first** — while the freeze is open, that branch's code can change any of those. A stack delete in dev needs it open too (CloudFormation removes URL configs and permissions), and deleting `ApertureApp-dev` needs its site bucket emptied first (`aws s3 rm s3://<bucket> --recursive --profile aperture-dev` — dev has no auto-delete provider). Changing `ApertureDevGuard` or `ApertureCicdDev` is the same with all three standing SCPs detached (they deny the execution role CloudWatch/EventBridge writes, OIDC-provider changes and — `NoLaneTampering` — any change to a GitHub role), then a drill.

#### Worst case

Per incident, at the cap of 30 environments (the Support case's ask; the quota today: _What's capped_ → Compute), before the kill lands (~3 min):
- **A buggy or overreaching agent** (normal memory, modest logging, no deliberate egress flood): cents — well inside the $1 target.
- **A deliberately maximal one:** log ingest ~$13 and internet egress ~$38 in theory (at an assumed 5 MB/s of logs and 625 Mbps of egress per environment — real Lambdas manage a fraction), compute under $0.10, DynamoDB cents; plus up to ~$9 of S3 requests (and some egress) from the runner over a full 30-min job, which no alarm watches — per dispatch, and `dev-cutover` puts no rate cap on dispatches.
- **A deliberate slow drain** sitting under the per-minute thresholds (one environment kept busy, or the table held at its cap): above 10 environment-minutes an hour the hourly alarm trips within the hour — about $0.30–1 by then — and above ~1.7 an hour on average the rolling three-hour alarm trips within three hours (a few dollars by then). **Below that, only the budget catches it**, 8–24 h late: at the same assumed egress rate, just under it is under ~$1/h — still up to ~$20 over a day in theory, for an agent built to hide. Its threshold (300,000 ms per 3 h) sits ~17× above a measured busy dev session (17,707 ms over the 2026-11-01 window: deploys, two full devchecks, a phone test); a tighter one would start false-killing real agent sessions. **The $1 target does not hold against a deliberate flood** — AWS offers no cap on logs or egress, and a VPC without NAT would break Plaid, Google and Anthropic.
- **Persistent after the kill:** ~$0/hr — nothing runs (every function at 0), nothing serves (distributions disabled), and no other account holds a grant (the freeze). Left to delete by hand: S3 objects and SSM parameters (Advanced-tier parameters cost $0.05 a month each and no SCP key can refuse the tier — the dev budget's $1 email and $3 kill catch a pile within a day).
- **If the fast kill itself fails:** the dev budget fires 8–24 h later; the drill is what keeps that from happening.

`deploy-dev.yml` **refuses every dispatch** unless the repository variable `DEV_DEPLOY_ISOLATED` is `true`, which the user set during `dev-cutover` (_Setup_ step 8; the App has no Variables permission, so the bot can't). It is the user's pause switch: `cd /Users/rahuldatta/Coding/Personal/aperture && gh variable set DEV_DEPLOY_ISOLATED --body false` stops every dispatch, `--body true` resumes. `pnpm bot deploy-dev` reports a refused run and releases the lock. While paused, nothing reaches dev but a merge to `main`.
