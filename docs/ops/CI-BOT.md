# CI bot — Claude's GitHub identity

Claude pushes feature branches, deploys a pushed commit to dev and reads dev logs as a **GitHub App, `aperture-cc-bot`**, through `pnpm bot …`. It never opens or merges PRs: **the user opens every PR**, because a squash commit's author is the PR opener and `main` stays the user's (decided 2026-10-29; since 2026-11-01 the Mac mailroom opens it with a PR-only token of the user's — MAILROOM.md). `main` needs the user's code-owner approval or admin bypass, and the bot is not a bypass actor. The container's own GitHub token (a read-only PAT, COI-SANDBOX → _GitHub access_) stays as it is, for fetches and reads.

Built 2026-10-13 (ci-bot branch, part of "Zero-Touch PRs"). Its dev deploys (`pnpm bot deploy-dev`) stayed **off** until dev ran in its own AWS account (_Dev deploy blast radius_): the `dev-account` PR moved dev there, and the `dev-cutover` PR turned dispatch on and retired the user's `dev` push path (_Setup_ step 8). `DEV_DEPLOY_ISOLATED` is now the pause switch (the end of _Dev deploy blast radius_).

## Commands

Run from a worktree root (`pnpm bot` is a root script: `node scripts/src/bot/cli.ts`, plain Node type stripping, builtins only).

`-h` / `--help` anywhere on a command (or `pnpm bot help <command>`) prints that command's usage, exits 0, and runs nothing. An unknown flag, subcommand or extra argument exits 2, again before anything runs. Each command's allowed flags live in the CLI's `FLAGS` table; a new subcommand needs an entry, and a test fails without one. The same guard, `scripts/src/bot/help.ts`, also fronts `pnpm mailroom` and the board CLI (`scripts/src/board/cli.ts`).

## Dev deploys

`deploy-dev.yml` (dispatch only; on `ref: main`, or on the commit's own branch when it changes `.github/`): job `verify` checks the sha is 40-hex, on a pushed feature branch (not main/master/dev) and contains `origin/main`. Dispatched on main, it refuses a `.github/` change — main's YAML would run, so the change would silently go untested; dispatched on a branch, it requires that branch's head to be the sha. It then classifies the change with the checked-out ref's classifier against **what dev serves now** (`base`: the sha the newest deciding dev job put there — a dispatch's, or the one main's dev job deployed, never main's head, which a merge still in flight or one that never landed hasn't put there; empty → `origin/main`, only when no deploy is in reach; unknown → `full`). It then prints `If merged now: dev-main=<mode> prod=<mode>`: what a merge would deploy, from `scripts/src/deploy-base.ts` (INFRA §9), and the only real-API run of that script before main. The proof is the log lines above it (`prod: <sha> deployed full`, `base {…}`), since a broken walk also prints `full`, with a `::warning`. A second line, `If merged now: check=<plan>`, previews `scripts/src/checked-tree.ts` (INFRA §9 → _Tree-matched main checks_) for the open PR whose head is the sha: `skip`/`fixtures` only while the branch sits on main's head and its PR run is green, else `check` with the reason in the log — the only real-API run of the tree lookup before main. A third, `<slot> lock probe: … — read with the job token`, reads the slot's lock once as a merge's wait would (`scripts/src/main-dev-wait.ts --once`): the only runner run of that module before main, so a dev test of a change to it needs that line (a failed read is only a `::warning::`). Job `deploy` calls `deploy-stage.yml` with `ref: <sha>`, which checks it out and exports `APERTURE_BUILD_SHA`. No `check` job: the PR runs CI; dev is for trying things. No notify job (INFRA §9 → _No ntfy_): the bot reports every conclusion to the session that dispatched.

**Run-name contract** (with dev-e2e's devcheck): `deploy-dev <40-hex sha> <key>`, key `<branch>-<base36 ms>` (`-r` appended on the one retry after a `cancelled`). A dispatched run's `head_sha` and branch are main's on a main-ref dispatch and the feature's on a branch-ref one — so the devcheck's `pickDeployRun` must not filter by branch; it matches `^deploy-dev ([0-9a-f]{40}) (\S+)$` and the build marker reads `APERTURE_BUILD_SHA`, falling back to `GITHUB_SHA`.

**A merge waits for the lock** (`merge-waits-slot-a`, 2026-11). A merge to `main` deploys dev from main (deploy.yml), but once its `check` has passed (or was planned-skipped) its `wait-dev` job first waits while slot A's lock is held and live: it polls every 30 s, wakes at the holder's expiry, and lets the deploy go when the lock is released or lapses (`scripts/src/main-dev-wait.ts`). A red check fails the run at once, never waits. `wait-devb` does the same for slot B when the merge redeploys it (_Dev slots_), on its own, so a held devb never delays that run's dev or prod — but it keeps the run in progress, so the next merge's whole run queues behind it (up to ~70 min, with slot A free). A docs-only (`none`) merge touches no stack and doesn't wait. **Never a gate:** prod still follows dev, the deploy `if:`s never read the wait's result, and after 60 minutes of waiting (a lock renewed past its TTL) or ten failed reads in a row (~5 min) the deploy goes anyway, with a `::warning::` and the run's step summary saying a lane's branch may have been replaced mid-test. The job is read-only (`contents: read`); the other half is the bot's. From the moment main's `wait-<slot>` starts until its `deploy-<slot>` job completes (`scripts/src/bot/main-pending.ts`), `deploy-dev` and `lock acquire` refuse that slot to every branch but its live holder, naming the run, the holder it waits for and the wait (`MainPending`). They check before writing the lock and again after, releasing it on a hit: the wait's first read comes 20 s after it starts (`SETTLE_MS`, past the jobs API's lag), so either it reads the lane's lock or the lane sees it running. A run not yet at its wait (queued behind another, still checking) holds nothing up: its wait will read any lock written now, so a lane may take the slot first and main then waits for it — at most one holder's turn, and devb stays usable while merges cluster. The holder may redeploy a fix while main waits — rebased onto the waiting merge first (`deploy-dev` refuses a branch behind `origin/main`), so when that merge changes a frozen shape the freeze refuses the redeploy and the lane loses the slot to main: wait for main's run instead; when it releases, main deploys, then the next lane. `lock renew` never revives a lapsed lock (main's wait may already be deploying); `acquire` and `deploy-dev` re-take it, guarded. `lock wait` waits for both, and says when it gave up on main rather than a holder. **To hurry a merge** (a hotfix): ask the holder, through the hub, to `pnpm bot lock release`; never cancel the run — a cancelled run deploys nothing. Re-running a failed main Deploy: **Re-run all jobs**, so the wait runs again, and only while it is the newest main run (an older one would redeploy its older commit to dev; the next merge's run carries the change); _Re-run failed jobs_ skips a wait that already passed and deploys over whoever took the slot since. **Clustering:** a waiting run is running, never cancelled; merges behind it queue and collapse to the newest (GitHub keeps one pending run per group, INFRA §9), which classifies from what each stage last deployed, so nothing is lost but prod lags by up to the wait — and the ceiling is per run, so a lock renewed for hours holds each run up to an hour. **Residual:** a jobs API that shows a started wait more than 20 s late lets a lane's lock land unseen before main's deploy; the devcheck's build-marker check notices any change mid-run — re-run `deploy-dev`.

**Whichever deploys last wins**, otherwise: a dispatch queued behind main's dev job deploys over main. `deploy-stage-dev` queues them, never runs both. A main deploy's mode comes from its lane's own deployment history (`dev-main`, not the dispatches), so a feature's infra can linger on dev until the next `full` deploy. The devcheck's build-marker check notices any change mid-run; re-run `deploy-dev`.

**Two lanes into the dev account** (built with `dev-account`): a `main` push is merged, reviewed code, so deploy.yml deploys it to dev in the **`dev-main`** GitHub environment (deployment branches: `main` only) as `aperture-github-dev-main`, through a second CDK bootstrap (qualifier `devmain`) whose execution role the freeze SCP exempts — shape-changing merges deploy, and prod follows, with no hand step. A bot dispatch stays in the **frozen lane** (as did the `dev` push, until `dev-cutover`): the `dev` environment, `aperture-github-deploy-dev`, the stock bootstrap. What keeps the bot lane out of it, all in the guardrails SCP: only the dev-main role (and break-glass) may assume a `devmain` bootstrap role (`OnlyMainAssumesItsLane`); nothing but break-glass may change or pass one, or any `aperture-github-*` role, bar the devmain deploy role passing its own exec role (`NoLaneTampering`); every stack call must name its role, since CloudFormation reuses a stack's stored role — after main's deploy, the exempt one — for a call that names none (`NameTheStackRole`); and nothing but break-glass and devmain's publishing role may write devmain's asset bucket, its version parameter or its `CDKToolkit-devmain` stack — the publishing role's own policy reaches only the bucket (`DevMainBootstrapIntact`); nothing in dev may create an S3 access point, a second address for a bucket (`NoCostSinks`) — cdk-assets skips a key that already exists, so a planted template or zip would otherwise deploy. The exempt lane is otherwise under every other SCP and the kill. Each lane has its own asset bucket, so dev carries no CDK provider function (the freeze denies the bot lane new provider code, and a provider's code location would move on every lane switch): dev owns its log groups and its site bucket has no auto-delete. The lanes' templates differ only in the `BootstrapVersion` parameter and the asset bucket (`cdk/src/config/lane.ts`). **Lockstep:** a CDK CLI bump that raises the required bootstrap version needs both dev bootstraps upgraded (`cdk bootstrap`, as break-glass, once with `--qualifier devmain --toolkit-stack-name CDKToolkit-devmain`). The bot's `Actions: write` can re-run an old main Deploy run, which redeploys that older merged commit through the exempt lane — reviewed code, so a nuisance, not an escalation. So can the bot lane make main's next dev deploy fail (and prod wait) without gaining anything — a stack policy, a cancelled update, a CloudFormation hook, a code-signing config, the devmain bucket's encryption setting; break-glass clears it. deploy-stage refuses lane `devmain` unless the run is a `main` push of its own commit, so a dispatch on `ref: main` can't carry branch code into it. The lane's first live run is a merge — GitHub admits `dev-main` only from `main`. **A stale branch:** `verify` refuses a branch that doesn't contain `origin/main`, so one behind a shape-changing merge is told to rebase before it reaches the freeze; a rebased branch whose shape differs from what dev runs now (another dispatch deployed a different shape between) fails in `Deploy stacks` with `explicit deny in a service control policy`, and deploy-stage's _Unstick a refused dev deploy_ step rolls it back — open the freeze for it (_Kill switch_ → _Opening the freeze_) or wait for main's next full deploy.

**What dev serves now** is judged by the dev-stack _job_ (`deploy-dev / deploy` in deploy.yml, `deploy / deploy` in deploy-dev.yml): the newest finished one decides. A main run finishes with prod, long after dev, so run times would mislead. A main deploy counts only when its `Deploy stacks` step ran: an app- or docs-only main merge leaves whatever infra a dispatch put on dev, so the base stays that dispatch (the cost: a few more `full` dispatches after such merges). A dev job still running, one that failed (a possibly half-applied stack), or a deciding job further back than the last 50 runs (5 pages) makes the base `unknown` → `full`. A `dev` push counts too — the path was retired at `dev-cutover`, but the admin bypass could recreate the branch, and every older `deploy.yml` deploys it: when one is the newest dev deploy, the base is `unknown`. A dispatch always publishes the frontend (a docs-only `none` becomes `app`), so the build marker always moves to the dispatched sha.

**The lock outlives the deploy:** `deploy-dev` renews it whenever less than 15 minutes remain while it waits, and once more on success, so the devcheck starts with a full 45 minutes. A run that finishes unsuccessfully releases it; a timeout or API error leaves it to expire, since the run may still be deploying.

## Dev slots

Two dev stacks share the dev account (INFRA §2): **slot A**, `dev` (`ApertureData-dev` / `ApertureApp-dev`, `dev.aperture.rahuldatta.dev`), and **slot B**, `devb` (`-devb`, `devb.aperture.rahuldatta.dev`), so two branches can be on dev at once. One safety net covers both (the SCPs, the alarms, the budget and the kill are account-wide; the kill's URL list names both slots' functions, `cdk/src/config/devAccount.ts`), as do one pair of GitHub environments (`dev`, `dev-main`), one pair of deploy roles and the `*_DEV` secrets. Slots are told apart by job name: `deploy` / `deploy-b` in deploy-dev.yml, `deploy-dev` / `deploy-devb` in deploy.yml — `currentBase` and `deploy-base.ts --slot` read each slot's own records by it.

- **The lock picks the slot, never a flag.** Each slot has its own lock (`refs/locks/dev`, `refs/locks/devb`, _Dev lock_). `deploy-dev` keeps the slot this branch holds, else takes `dev`, else `devb`; both held → refused, naming both holders and `lock wait --any`. A branch whose diff against main touches iOS paths (every iOS-entry scenario's slowPaths, `scripts/src/devcheck/scenarios/ios-paths.ts`) takes `dev` only: held → refused with `lock wait` even when devb is free, and holding devb, or `lock acquire --slot devb`, is refused with the way back (`bot/ios-routing.ts`). A branch holds at most one. `pnpm devcheck` targets the slot its branch's lock is on (no lock: `dev`, as before slot B — DEV-CHECK.md → _Dev slots_). `lock acquire --slot devb` is the one explicit choice, for a test that must be on devb.
- **Main keeps devb's shape current.** A dispatch onto a slot is accepted only if that slot already runs main's shape (the freeze), and every dispatch brings the slot's code to its branch anyway. So deploy.yml's `deploy-devb` job deploys devb through the devmain lane — after `wait-devb` waits for devb's lock — only when a merge changed its shape since devb's last main deploy — `cdk/`, `pnpm-lock.yaml`, or `packages/shared/src/stage.ts` (the slot list cdk builds devb's table from; `deploy-base.ts` → `SHAPE_PATHS`, whose test pins every name cdk imports from shared) — in full, in parallel with `deploy-dev`, never gating prod; skipped otherwise. The job takes ~8–12 minutes, on ~1 merge in 5.
- **A slot B base:** like slot A's, a main job's base is the sha it deployed (`head_sha`); a devb never deployed is `unknown` → full.
- **`.github/` branches** dispatch on their own ref onto either slot; the `dev` environment admits them by name for both.
- **iOS is slot A's:** the sim's Home Screen app, Keychain item and sign-in host are dev's (`tools/mailroom/jobs/sim.sh`), so a devb run's iOS rows read needs-you (`SIM_SLOT_A_ONLY`, IOS-CHECK.md) — which is why `deploy-dev` sends a branch touching iOS paths to dev (above), and a devb run of one says how to move.
- **Not on devb:** `DEVICE_USER_ID` (no finance schedule), Google OAuth callbacks (no scenario uses Google), the claude.ai `aperture-dev` connector (slot A's; the devcheck signs in as `aperture-claude-devb` from the slot's env file).
- **Setup, once** (the `dev-slot-b` PR's dev test): the `devb` ACM cert in us-east-1 + its Netlify CNAMEs, `CERT_ARN_DEVB`; `ApertureCicdDev` redeployed with the three standing SCPs detached (the deploy roles' S3, smoke and DescribeStacks grants and the logs role now cover both slots); devb created by one freeze-open dispatch (born with the table's on-demand ceiling and TTL; with no domain yet, the health check skips the MCP OAuth façade checks and says so, since the façade runs only with `APP_URL`), then `ApertureOrg` redeployed — the kill's lists, and the guardrails' `kms:DescribeKey` / `kms:CreateGrant` exemption without which CloudFront refuses the cert (`InvalidViewerCertificate`; the attach reads ACM's key in us-east-1 under the deploying role) — then a second freeze-open dispatch for the alias, which runs the façade checks, then a drill (which kills both slots); the test user and `.secrets/devcheck.devb.env` by break-glass; `/aperture/devb/…` SSM operator values copied from `/aperture/dev/…`; Plaid Link once.

## Dev lock

Each slot's lock — `refs/locks/dev` (slot A) and `refs/locks/devb` (slot B) — works the same way: the ref → an annotated tag on the feature sha (it must be pushed) whose message is `{"branch","sha","expiresAt"}`. Acquire = create the ref (a 422 means held). Holder = branch. TTL 45 minutes, `renew` to extend; an expired or unreadable lock is taken over by the next `acquire` (it re-reads the ref and deletes it only if it still points at the tag it judged expired). Residual races: two sessions taking over the same expired lock within that window can both believe they hold it, and a holder's `renew`/`release` (read, then PATCH or DELETE) can clobber a take-over that lands in between — the devcheck's build-marker check catches the result. GitHub's Git refs API has no compare-and-swap.

A merge's slot deploy waits for that slot's lock too, and while it is pending the slot is refused to all but its holder (_Dev deploys_ → _A merge waits for the lock_).

**Waiting for it:** another branch's lock means wait, never work around it — send the two messages the refusal prints, then the wait the refusal names in the background — `pnpm bot lock wait --any` when both slots are held, plain `lock wait` when it named dev alone (an iOS-path branch, which `--any` would wake for a devb it can't take) — which wakes the session when the lock frees or lapses; then `deploy-dev` takes it (`docs/ops/HUB.md` → _Lock etiquette_). Every lock read or change the bot makes also lands in the board's cache (`devlock.json`, `devlock.devb.json`), so `board.sh status`, the SessionStart hook and the status line show the holder (`docs/ops/SESSION-BOARD.md` → _Dev lock line_).

Until dispatch was on, the user's `dev` push was guarded by the session board's local dev lease instead; session-comms removed it, so the two slot locks (`refs/locks/dev`, `refs/locks/devb`) are the only dev locks.

## Dev logs

`fetch-dev-logs.yml` (dispatch only, `ref: main`) runs in the **`dev-logs`** environment, assumes `aperture-github-logs-dev` and runs `scripts/aws/fetch-dev-logs.mjs`: `filter-log-events` (or Logs Insights with `--query`) per group for one window, up to 20 000 events a group, into an artifact kept 1 day (public with the repo — INFRA §9 → _Public repo_).

- **Why its own environment, not `dev`:** AWS trusts a job by its environment (`…:environment:<name>`). A job in `dev` could assume the dev **deploy** role too; `dev-logs` gives log reading its own subject that only the read-only role trusts. "Deployment branches: `main`" names which branch's workflow code may run there — not which logs it reads.
- **Window ≤ 6 h; loop guard ≤ 10 fetches an hour** per worktree (`localNotes/devlogs/fetches.jsonl`) — then the CLI stops and says so. The cap is a loop brake and keeps the public run list quiet (each fetch is a public run); reading CloudWatch costs next to nothing (Insights bills per GB scanned; dev groups are tiny).
- **No identifiers in the inputs:** a run's inputs and name are public, so the CLI scans `--filter`, `--query`, `--groups` and the run key first and refuses a personal identifier before spending a run; `--start`/`--end` go out as ISO (`IDENTIFIERS.md` → _The checks_).
- Prod logs stay the user's to fetch.

**Retention:** prod's BFF and MCP groups were created by Lambda on first invoke and never expired. `logRetention` on both prod functions (`app-stack.ts`) sets 90 days through CDK's `Custom::LogRetention`, which tolerates the existing group. Dev, in its own account since `dev-account`, owns its two groups outright (14 days, deleted with the stack; _Dev deploys_ → _Two lanes_). Deprecated but supported in aws-cdk-lib 2.263; `logGroup` would try to create the group and fail (AlreadyExists) — moving to it needs a `cdk import`, a follow-up. finance-sync already owns its group (30 days).

### Dev deploy blast radius — decided 2026-10-13: isolate first; built 2026-10-30, moved to its own account 2026-10-31

The row above is the real exposure, and it predates the bot: the dev deploy role reached the account through the shared CDK bootstrap roles. What the bot changes is that nobody runs the deploy by hand any more. **The user's call: isolate dev first.** The stock bootstrap's **deploy role** may create, update and delete any stack (an `UpdateStack` without a `RoleARN` reuses a prod stack's admin execution role), its **lookup role** holds `ReadOnlyAccess` (every row of `aperture-prod`), and its **execution role** is admin.

PR 72 (`dev-bootstrap`) built a dev-only bootstrap inside the shared account. The cost analysis that followed (2026-10-30) changed the target: **the user's worst case for a rogue, buggy or prompt-injected agent is about $1 an incident, with $0 standing cost** — money over prod uptime, so a kill that stalls the pipeline is acceptable as a signal. In-account IAM couldn't bound money, so **dev moved to its own AWS account** (`dev-account`, INFRA §2–§3): prod is out of reach by construction — no dev credential exists in the management account — and the dev account's SCPs, which nothing in it can remove, take away the levers.

**What's capped, and how:**

- **Compute** — the sum of the dev functions' reserved concurrency: **30 per dev stack**, 60 for the two slots `dev` and `devb` (`cdk/src/config/devAccount.ts` → `DEV_RESERVED_CONCURRENCY`: BFF 18, MCP 9, finance sync 1, reminder poller 1, coach worker 1 on each slot), whatever the account quota. A function runs at most its reservation, so the sum holds even as AWS raises the quota; `stacks.test.ts` fails for any dev function deployed without its table value. (A CDK provider function in a dev stack, such as `ApertureCicdDev`'s OIDC one, is unreserved and outside the sum; only CloudFormation invokes it.) Lambda keeps 100 of the account quota unreserved, so reservations need a quota of at least the sum + 100: the quota was AWS's reduced new-account 10 until 2026-11 (confirmed 2026-11-05 with `get-account-settings`, below; 81 throttles in the 7 days before, every one a devcheck's page-load burst), and 1,000 was requested through Service Quotas on 2026-11-08 and read live that day, while the request still showed `CASE_OPENED` (the Support case for 30 was closed, since 30 can't hold a reservation). Two dev stacks need at least 160. Only main's lane, break-glass and the kill may change a reservation — the freeze denies a dispatch, and a dispatched branch that changes one needs it opened (_Opening the freeze_). Home's cold load is 15 `/api` calls, at most 12 at once (measured 2026-11-13), under the BFF's 18 with room for the harness's ~2; a second client's cold Home load in the same moment can 429. The app has no client-side cap and retries a 429 (`app/src/data/retry.ts`), and a real 429 fails the dev check ([DEV-CHECK.md](DEV-CHECK.md) → _Throttles (429)_). Dev may not raise the quota itself (`servicequotas:Request*` denied); the freeze SCP keeps every function at its deployed memory (512 MB) — main's own deploy excepted (_Two lanes_) — and timeout (15 s; 300 s for finance sync, 90 s for the coach worker), so a kill's in-flight tail is at most those, and denies new functions, Function URLs, permissions and async destinations. No provisioned concurrency, recursion-detection changes or event-source mappings. **Two devchecks at once** (one per slot, DEV-CHECK.md → _Dev slots_), measured 2026-11-13 from REPORT lines (`pnpm bot logs --query`): a full run is ~95–106k Lambda ms and peaks near 810 calls a minute; the reminder pollers and finance sync add ~12–15k ms an hour. A busy two-lane hour — each lane a full run and a full rerun — is ~440k ms (~600k at a conservative 145k a run): 3× under the hourly Duration alarm (1,800,000), 2× under the three-hour one's 1,200,000 an hour, which allows ~11 full runs an hour sustained; two runs' peaks landing in the same minute are ~1,640 calls, 1.8× under the 3,000 a minute alarm (_Kill switch_).
- **Everything else AWS sells** — the allowlist SCP denies every service outside the ~14 dev uses (EC2, Bedrock, SageMaker, SNS…; of SSM only Parameter Store, of ACM only reads), every region but us-west-1 (closes Lambda@Edge), and the paid add-ons of the allowed ones (invalidations, real-time logs, log subscriptions, metric filters and anomaly detectors, KMS keys, exportable certs, S3 replication, acceleration, request metrics, Object Lock and any storage class but Standard, DynamoDB restores, backups, global tables and Contributor Insights).
- **Grants that would outlive a kill** — an SCP binds only the dev account's own principals, so the freeze denies whatever would let another account's principals, an unauthenticated caller, or a service act for dev: bucket policies, ACLs and lifecycle rules, a table resource policy, new roles and role trusts, new buckets and distributions, and the user pool (no self-sign-up, new clients or created users — monthly active users bill).
- **CDK's provider functions** (LogRetention, S3 auto-delete, the OIDC provider) have 15-minute timeouts, so the freeze also denies new code in them (`function:Aperture…`); the app's own functions (`aperture-…`) stay open to code updates — that is what a dev deploy is.
- **DynamoDB** — an on-demand ceiling on dev's table and GSI1 (100 read / 50 write units each), which the freeze keeps (no `UpdateTable`). A dev check's dead rows (~130 a full run) would otherwise run reads into it, so dev's table expires tombstones through TTL ([TECH.md](../arch/TECH.md) §2.3, rule 4); the spec reaches the table through main's lane. A dispatch refuses a branch behind `origin/main`, which keeps templates without it off dev, except a dispatch verified just before the merge and queued behind main's job, or a re-run of an old main deploy: either could turn TTL off, so after such a deploy check with `aws dynamodb describe-time-to-live --profile aperture-dev --region us-west-1 --table-name aperture-dev`. Tombstones written before the stamp shipped never expire, and need one hand purge.
- **The deploy job** — 30 min (`deploy-stage.yml` `timeout-minutes`), in YAML the bot can't edit.
- **Logs and internet egress** — no AWS cap exists for either, so the kill switch bounds them in time.

#### Kill switch

```
dev account (ApertureDevGuard)                 management account (ApertureOrg, us-east-1)
aperture-kill-duration   ≥ 600,000 ms/min ×2 ┐
aperture-kill-duration-hour ≥ 1,800,000 ms/h │
aperture-kill-duration-3h ≥ 3,600,000 ms/3 h │
aperture-kill-invocations ≥ 3,000/min        ├─ ALARM ─▶ rule aperture-kill-forward ─▶ default bus ─▶ rule aperture-dev-kill
aperture-kill-log-bytes  ≥ 100 MB/min        ┘          (role aperture-kill-forwarder)                 ├─▶ Lambda aperture-dev-kill
                                                                                                         │     1. attach SCP aperture-dev-kill (deny-all)
dev budget > $3 actual (8–24 h lag) ─────────────────────▶ topic aperture-dev-budget-kill ─────────────┤     2. every dev function → concurrency 0
                                                                                                         │     3. bff + mcp Function URLs → AWS_IAM
                                                                                                         │     4. dev's CloudFront distributions → disabled
                                                                                                         └─▶ email (raw alarm; also a failed kill, via the Lambda's failure destination)
```

- **Why four moves:** the deny-all SCP stops every API call a dev principal makes (the runner, SDK loops, a schedule's role) — but some compute and egress happens without one. Lambda's own async queue (events queued before the kill retry for up to 6 h) and a public Function URL invoke as the service, so every function goes to concurrency 0; the URLs also switch to `AWS_IAM` (403, and the app goes dark — CloudFront's origin requests aren't signed) in case the throttle fails; and CloudFront serves its cache and reads S3 as a service principal, so the distribution is disabled. All four run through the dev account's break-glass role, which the kill SCP exempts.
- **Latency:** about 2–4 min from a spike (1-min alarm periods, then EventBridge and the Lambda); up to an hour for a slow drain the hourly alarm catches, and up to three for one the rolling three-hour alarm catches (a period under a day is evaluated every minute over a sliding window). Thresholds sit well above a full devcheck; re-tune them from a measured run. Five alarms: with prod's five, the free ten (the free tier is shared across the Organization).
- **Unkill** (user, Mac) — first find out what tripped it (`pnpm bot logs`, the alarm in the email), and redeploy main to dev if a branch is suspect. Wait until nothing will re-kill: if the kill emailed a failure, its retries finish first (about 3 min, ending in the failure email); and all five alarms must read `OK` — a burst that trips the per-minute alarm can leave the hourly and three-hour sums elevated — `aws cloudwatch describe-alarms --profile aperture-dev --region us-west-1 --alarm-name-prefix aperture-kill- --query 'MetricAlarms[].[AlarmName,StateValue]' --output text`. Then detach the SCP and let the kill Lambda reverse moves 2–4 (only a direct invoke with this payload can — a trigger only ever kills; move 2 goes back to each function's own reservation, from the Lambda's `RESERVED_CONCURRENCY`, the same table — so a merge that adds or resizes a dev function needs an ApertureOrg redeploy too): `cd <mac-repo> && aws organizations detach-policy --policy-id <KillPolicyId output of ApertureOrg> --target-id <dev account id> && aws lambda invoke --region us-east-1 --function-name aperture-dev-kill --cli-binary-format raw-in-base64-out --payload '{"action":"restore"}' /dev/stdout` — `aws lambda invoke` exits 0 even when the function failed, so check the output has no `FunctionError`. The dev account's one CDK provider function (`ApertureCicdDev`'s OIDC one, `ApertureCicdDev-…`), never reserved, gets its reservation removed, as before. Any other function with no reservation on record stays at 0 (removing it would lift its cap to the account quota) and the error names it: put it back as break-glass, `aws lambda put-function-concurrency --profile aperture-dev --region us-west-1 --function-name <fn> --reserved-concurrent-executions <n>` — a later deploy won't, since the template hasn't changed. A distribution takes a few minutes to re-enable. A dev stack whose first create failed (`ROLLBACK_COMPLETE`) blocks every later deploy in both lanes: the CDK CLI deletes it without naming a role, which `NameTheStackRole` denies — delete it as break-glass, `aws cloudformation delete-stack --profile aperture-dev --region us-west-1 --stack-name <stack>`. If the kill landed mid-deploy and left a dev stack in `UPDATE_ROLLBACK_FAILED`: the rollback runs as the stack's own role (the CDK execution role), which the SCPs bind — so detach the kill SCP first (and the freeze, if that deploy changed a function's shape), then `aws cloudformation continue-update-rollback --profile aperture-dev --region us-west-1 --stack-name <stack>`. **The budget's $3 kill fires once per month** (a Budgets notification fires once per threshold per period), so after an unkill that month only the alarms remain.
- **Drill** (after any change to either guard stack, and quarterly): `aws cloudwatch set-alarm-state --profile aperture-dev --region us-west-1 --alarm-name aperture-kill-duration --state-value ALARM --state-reason drill`; expect the email, the SCP on the account (`aws organizations list-policies-for-target --target-id <dev account id> --filter SERVICE_CONTROL_POLICY`), all four URLs (`DEV_URL_FUNCTIONS`, two per slot) at `AWS_IAM`, `aws lambda get-function-concurrency --profile aperture-dev --region us-west-1 --function-name aperture-bff-dev` at 0, and both slots' distributions disabled; after the unkill, every dev function back at its own reservation (`for s in dev devb; do for f in bff mcp finance-sync push-dispatch coach-worker; do aws lambda get-function-concurrency --profile aperture-dev --region us-west-1 --function-name aperture-$f-$s --query ReservedConcurrentExecutions --output text; done; done` → 18 9 1 1 1, twice). The first drill also settles one open question: whether Lambda accepts a reservation of 0 below the 100-unreserved floor (the quota: _What's capped_ → Compute). **If it refuses, stop before merging `dev-account`:** moves 3–4 still close the URL and CloudFront paths, but not Lambda's async queue (events queued before a kill would run for up to 6 h), and every later kill would retry and email a failure. The planned fallback is a move that sets each function's async event age to 60 s with no retries (`PutFunctionEventInvokeConfig`, as break-glass). Then unkill and set the alarm back to `OK`. **Monthly**, read the quota: `aws lambda get-account-settings --profile aperture-dev --region us-west-1 --query AccountLimit.ConcurrentExecutions` — expect at least the reservations' sum + 100 (160 for two dev stacks). The cap is the sum (_What's capped_ → Compute), so the quota matters only below that, where a deploy's reservations fail.

**Opening the freeze** — a branch that changes a function's shape (an env var, memory, its reserved concurrency, a new function or URL), the table (not its TTL: `UpdateTimeToLive` isn't frozen), a schedule or a grant (a bucket policy, a new role — but not a changed policy on an existing role: an inline `iam:PutRolePolicy` passes the freeze, proven live 2026-11-01 by `attachment-s3-delete`, run 41353956072) fails its dev deploy with `explicit deny in a service control policy` (CloudFormation's own rollback is refused too — it re-applies the configuration as the same frozen role — so in the frozen lane deploy-stage's _Unstick a refused dev deploy_ step continues it with `cdk rollback --force`, skipping the resource the freeze refused both ways, so it never changed; without it the stack would stick in `UPDATE_ROLLBACK_FAILED` and block both lanes. A run cancelled or timed out mid-deploy skips the step; the next dev deploy fails at once on the stuck stack, and its own step unsticks it. Main's lane never skips: a failed rollback there is a real fault — break-glass `continue-update-rollback`, below) — and so can an `aws-cdk-lib` bump (a dependency PR included) that changes a bucket policy CDK manages, a role trust, or adds a Lambda permission, or adds a CDK provider function (dev's app stacks carry none; a test pins it). So do the user pool's clients and domain (`UpdateUserPoolClient`, `CreateUserPoolClient`, `UpdateUserPoolDomain` sit under the freeze's wildcards): a change to callback URLs — `CLAUDE_CONNECTOR_CALLBACK_URLS` included — scopes or token validity. A merge to `main` needs none of this — main deploys through the freeze-exempt lane (_Dev deploys_ → _Two lanes_); only a dispatch of such a change does. The user detaches the freeze, deploys, and reattaches: `cd <mac-repo> && aws organizations detach-policy --policy-id <freeze id> --target-id <dev OU id>`, then the dispatch — **wait until its run has finished** (a freeze reattached mid-deploy refuses the rollback of a change that already applied, and the unstick step would then skip it, leaving the function in the branch's shape while the stack records the old one) — then `aws organizations attach-policy --policy-id <freeze id> --target-id <dev OU id>` (ids: `aws organizations list-policies --filter SERVICE_CONTROL_POLICY`); a dispatch then runs in the frozen lane, as always. **Read the branch's diff first** — while the freeze is open, that branch's code can change any of those, a reservation included: a changed `ReservedConcurrentExecutions` moves dev's compute cap until main's next deploy or a kill and restore puts it back. And since the reservations merged (2026-11), a branch cut before them has none in its template, so its dispatch tries to remove them and fails on the freeze: rebase it first. A stack delete in dev needs it open too (CloudFormation removes URL configs and permissions), and deleting `ApertureApp-dev` needs its site bucket emptied first (`aws s3 rm s3://<bucket> --recursive --profile aperture-dev` — dev has no auto-delete provider). Changing `ApertureDevGuard` or `ApertureCicdDev` is the same with all three standing SCPs detached (they deny the execution role CloudWatch/EventBridge writes, OIDC-provider changes and — `NoLaneTampering` — any change to a GitHub role), then a drill.

#### Worst case

Per incident, at dev's compute cap of 60 environments — the two dev stacks' reservations, 30 each (_What's capped_ → Compute; the maintainer's call, 2026-11-08) — before the kill lands (~3 min):

- **A buggy or overreaching agent** (normal memory, modest logging, no deliberate egress flood): cents — well inside the $1 target.
- **A deliberately maximal one:** log ingest ~$26 and internet egress ~$76 in theory (at an assumed 5 MB/s of logs and 625 Mbps of egress per environment — real Lambdas manage a fraction), compute under $0.20, DynamoDB cents; plus up to ~$9 of S3 requests (and some egress) from the runner over a full 30-min job, which no alarm watches — per dispatch, and `dev-cutover` puts no rate cap on dispatches.
- **A deliberate slow drain** sitting under the per-minute thresholds (one environment kept busy, or the table held at its cap): above 30 environment-minutes an hour (1,800,000 ms) the hourly alarm trips within the hour — about $1–3 by then — and a drain of 20–30 an hour, which the hourly never sees, trips the rolling three-hour alarm (3,600,000 ms per 3 h) within three hours — about $2–6 by then. **Below that, only the budget catches it**, 8–24 h late: at the same assumed egress rate, just under it is under ~$2/h — still up to ~$50 over a day in theory, for an agent built to hide. In Lambda compute alone that day-long evader (just under 20 an hour — anything nearer 30 the three-hour alarm ends within three hours) is ~$0.25 a day (≈ $0.005 per 10 environment-minutes at 512 MB), so on compute the $3 budget would take ~12 days; it is the assumed log/egress rate that makes the budget a day-scale backstop. How the thresholds got here: the three-hour one went 300,000 → 1,800,000 ms on 2026-11-04 (PT) after parallel lanes' ~314,000 ms in three hours tripped it (a full devcheck cost ~55–60k ms, against 17,707 ms for a whole 2026-11-01 window of deploys, two full devchecks and a phone test); that made the hourly the binding alarm, so the same night the hourly went 600,000 → 1,800,000 and the three-hour to 3,600,000 — a full devcheck costs 70–145k ms (five runs that evening put ~335k ms in 45 min), so only ~4–8 an hour fit under 600,000. Headroom now: the hourly is ≈ 12× a 145k devcheck and ~4× that 45-minute burst; the three-hour ≈ 11× the ~314k window that tripped the old value. Each time the live alarms were raised by hand first (break-glass `put-metric-alarm`), then the code to match; a tighter setting would start false-killing real agent sessions. **The $1 target does not hold against a deliberate flood** — AWS offers no cap on logs or egress, and a VPC without NAT would break Plaid, Google and Anthropic.
- **Persistent after the kill:** ~$0/hr — nothing runs (every function at 0), nothing serves (distributions disabled), and no other account holds a grant (the freeze). Left to delete by hand: S3 objects and SSM parameters (Advanced-tier parameters cost $0.05 a month each and no SCP key can refuse the tier — the dev budget's $1 email and $3 kill catch a pile within a day).
- **If the fast kill itself fails:** the dev budget fires 8–24 h later; the drill is what keeps that from happening.

`deploy-dev.yml` **refuses every dispatch** unless the repository variable `DEV_DEPLOY_ISOLATED` is `true`, which the user set during `dev-cutover` (_Setup_ step 8; the App has no Variables permission, so the bot can't). It is the user's pause switch: `cd <mac-repo> && gh variable set DEV_DEPLOY_ISOLATED --body false` stops every dispatch, `--body true` resumes. `pnpm bot deploy-dev` reports a refused run and releases the lock. While paused, nothing reaches dev but a merge to `main`.
