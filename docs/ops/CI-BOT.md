# CI bot — Claude's GitHub identity

Claude pushes feature branches, deploys a pushed commit to dev and reads dev logs as a **GitHub App, `aperture-cc-bot`**, through `pnpm bot …`. It never opens or merges PRs: **the user opens every PR**, because a squash commit's author is the PR opener and `main` stays the user's (decided 2026-10-29; until the mac-sim bridge gets an allowlisted "open PR" op, the user runs `gh pr create`). `main` needs the user's code-owner approval or admin bypass, and the bot is not a bypass actor. The container's own GitHub token (a read-only PAT, COI-SANDBOX → _GitHub access_) stays as it is, for fetches and reads.

Built 2026-10-13 (ci-bot branch, part of "Zero-Touch PRs"). Its dev deploys (`pnpm bot deploy-dev`) are **off** until dev's CDK bootstrap is isolated (_Dev deploy blast radius_); until then the user pushes `dev` as before, and the `dev-bootstrap` PR turns dispatch on and retires the `dev` push path.

## Commands

Run from a worktree root (`pnpm bot` is a root script: `node scripts/src/bot/cli.ts`, plain Node type stripping, builtins only).

| Command                                                                                                         | Does                                                                                                                                                                                 | Token permissions        |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| `pnpm bot push [--after-rebase]`                                                                                | Pushes the current branch to its own name as the bot. Refuses `main`/`master`/`dev` and detached HEAD. `--after-rebase` = `--force-with-lease` on `origin/<branch>` (the last push). | contents: write          |
| `pnpm bot deploy-dev`                                                                                           | Requires HEAD pushed and containing `origin/main`; takes the dev lock; dispatches `deploy-dev.yml`; waits. On success the lock **stays held** for testing; on failure it's released. | contents, actions: write |
| `pnpm bot lock status\|acquire\|renew\|release`                                                                 | The dev lock (below). Release and renew are holder-only.                                                                                                                             | contents: write          |
| `pnpm bot logs [--since 30m \| --start ISO --end ISO] [--groups bff,mcp,finance-sync] [--filter P] [--query Q]` | Dispatches `fetch-dev-logs.yml`, downloads into `localNotes/devlogs/<key>/`, prints the last 40 lines per group.                                                                     | actions: write           |

Tokens are minted per invocation (JWT → `GET /app/installations` → `POST …/access_tokens` narrowed to `aperture` and the row's permissions), held in memory, and reach `git`/`gh` through env only — a credential helper reading `$APERTURE_BOT_TOKEN`, or `GH_TOKEN`. Never argv, never a file. The JWT needs `Authorization: Bearer`; `gh api` sends `token …`, which GitHub rejects for a JWT (401 "could not be decoded"), so the CLI uses `fetch`.

Workflow changes: the App has no `workflows` permission, so GitHub refuses a bot push that touches `.github/workflows/` — the user pushes such a branch. `pnpm bot deploy-dev` then dispatches it **on its own ref**, so its workflows are what run on dev (once the `dev` environment admits feature branches — _Setup_ step 8). That is how a CI, deploy or Actions-version change gets tried before it reaches `main`, which deploys prod with no pause.

## Dev deploys

`deploy-dev.yml` (dispatch only; on `ref: main`, or on the commit's own branch when it changes `.github/`): job `verify` checks the sha is 40-hex, on a pushed feature branch (not main/master/dev) and contains `origin/main`. Dispatched on main, it refuses a `.github/` change — main's YAML would run, so the change would silently go untested; dispatched on a branch, it requires that branch's head to be the sha. It then classifies the change with the checked-out ref's classifier against **what dev serves now** (`base`: the last successful dispatch's sha when newer than main's last deploy; empty → `origin/main`; unknown → `full`). Job `deploy` calls `deploy-stage.yml` with `ref: <sha>`, which checks it out and exports `APERTURE_BUILD_SHA`. No `check` job: the PR runs CI; dev is for trying things.

**Run-name contract** (with dev-e2e's devcheck): `deploy-dev <40-hex sha> <key>`, key `<branch>-<base36 ms>` (`-r` appended on the one retry after a `cancelled`). A dispatched run's `head_sha` and branch are main's on a main-ref dispatch and the feature's on a branch-ref one — so the devcheck's `pickDeployRun` must not filter by branch; it matches `^deploy-dev ([0-9a-f]{40}) (\S+)$` and the build marker reads `APERTURE_BUILD_SHA`, falling back to `GITHUB_SHA`.

**Whichever deploys last wins.** A merge to `main` deploys dev from main (deploy.yml) over a dispatched branch; a dispatch queued behind main's dev job deploys over main. `deploy-stage-dev` queues them, never runs both. A main deploy's mode comes from main's own diff, so a feature's infra can linger on dev until the next `full` deploy. The devcheck's build-marker check notices any change mid-run; re-run `deploy-dev`.

**What dev serves now** is judged by the dev-stack _job_ (`deploy-dev / deploy` in deploy.yml, `deploy / deploy` in deploy-dev.yml): the newest finished one decides. A main run finishes with prod, long after dev, so run times would mislead. A main deploy counts only when its `Deploy stacks` step ran: an app- or docs-only main merge leaves whatever infra a dispatch put on dev, so the base stays that dispatch (the cost: a few more `full` dispatches after such merges). A dev job still running, one that failed (a possibly half-applied stack), or a deciding job further back than the last 10 runs makes the base `unknown` → `full`. The user's `dev` pushes count too: when one is the newest dev deploy, the base is `unknown`. A dispatch always publishes the frontend (a docs-only `none` becomes `app`), so the build marker always moves to the dispatched sha.

**The lock outlives the deploy:** `deploy-dev` renews it whenever less than 15 minutes remain while it waits, and once more on success, so the devcheck starts with a full 45 minutes. A run that finishes unsuccessfully releases it; a timeout or API error leaves it to expire, since the run may still be deploying.

## Dev lock

`refs/locks/dev` → an annotated tag on the feature sha (it must be pushed) whose message is `{"branch","sha","expiresAt"}`. Acquire = create the ref (a 422 means held). Holder = branch. TTL 45 minutes, `renew` to extend; an expired or unreadable lock is taken over by the next `acquire` (it re-reads the ref and deletes it only if it still points at the tag it judged expired). Residual races: two sessions taking over the same expired lock within that window can both believe they hold it, and a holder's `renew`/`release` (read, then PATCH or DELETE) can clobber a take-over that lands in between — the devcheck's build-marker check catches the result. GitHub's Git refs API has no compare-and-swap.

## Dev logs

`fetch-dev-logs.yml` (dispatch only, `ref: main`) runs in the **`dev-logs`** environment, assumes `aperture-github-logs-dev` and runs `scripts/aws/fetch-dev-logs.mjs`: `filter-log-events` (or Logs Insights with `--query`) per group for one window, up to 20 000 events a group, into an artifact kept 3 days.

- **Dev only, three ways:** the allowlist (`scripts/src/bot/logs-spec.ts`: `bff`, `mcp`, `finance-sync` → `/aws/lambda/aperture-<x>-dev`), checked by the CLI and again on the runner; the role reads only those three groups (`cicd-stack.ts`); the environment admits only `main`'s YAML.
- **Why its own environment, not `dev`:** AWS trusts a job by its environment (`…:environment:<name>`). A job in `dev` could assume the dev **deploy** role too; `dev-logs` gives log reading its own subject that only the read-only role trusts. "Deployment branches: `main`" names which branch's workflow code may run there — not which logs it reads.
- **Window ≤ 6 h; loop guard ≤ 10 fetches an hour** per worktree (`localNotes/devlogs/fetches.jsonl`) — then the CLI stops and says so. Actions minutes are the budget; reading CloudWatch costs next to nothing (Insights bills per GB scanned; dev groups are tiny).
- Prod logs stay the user's to fetch.

**Retention:** the BFF and MCP groups were created by Lambda on first invoke and never expired. `logRetention` on both functions (`app-stack.ts`) now sets dev 14 days / prod 90 days through CDK's `Custom::LogRetention`, which tolerates the existing group. Deprecated but supported in aws-cdk-lib 2.263; `logGroup` would try to create the group and fail (AlreadyExists) — moving to it needs a `cdk import`, a follow-up. finance-sync already owns its group (30 days).

### Dev deploy blast radius — decided 2026-10-13: isolate first

The row above is the real exposure, and it predates the bot: the dev deploy role reaches the account through the shared CDK bootstrap roles, whose CloudFormation execution role is admin. What the bot changes is that nobody runs the deploy by hand any more. **The user's call: isolate dev's bootstrap first.** A separate PR, `dev-bootstrap`, gives dev its own bootstrap qualifier with a scoped execution policy, synthesizes the dev stacks against it, and has the dev role trust only those roles.

Until then `deploy-dev.yml` **refuses every dispatch**: its verify job fails unless the repository variable `DEV_DEPLOY_ISOLATED` is `true`, which the user sets once `dev-bootstrap` is deployed (the App has no Variables permission, so the bot can't). `pnpm bot deploy-dev` reports that failure and releases the lock. Until then the user pushes `dev` as before (the `dev` ruleset keeps the bot off it — _Setup_ step 6); `dev-bootstrap` turns dispatch on and retires that path, in either merge order.
