# Aperture — Infrastructure

The AWS blueprint behind `TECH.md`. All IaC via **CDK**. Two AWS accounts under one Organization (§2). Region: **`us-west-1`** for the data + app stacks. **`us-east-1`** only where AWS requires it: the CloudFront ACM certs (§8), the billing stack (Cost Explorer / anomaly data lives there) and `ApertureOrg` (Organizations, Budgets and the kill switch's event bus, §3).

---

## 1. Shape

```
GitHub Actions ──(OIDC, no static keys)──► cdk deploy + app build/deploy

        ┌──────── CloudFront (per env, HTTPS) ────────┐
        │   default behavior → S3   (React PWA, OAC)  │
        │   /api/*            → Lambda Function URL    │  (public; secret header)
        └──────────────────────────────────────────────┘
              │                              │
            S3 (static)              Lambda BFF (1, multi-route)
                                            │  validates Cognito JWT in-handler
                                            ▼
                                     DynamoDB (single table, on-demand, PITR)
                                            ▲
   Lambda BFF ──async invoke──► finance-sync Lambda ◄── EventBridge Scheduler (3×/day)
        └──HTTPS──► Plaid ◄──HTTPS──┘   (BFF: link token, exchange, remove; sync: accounts, refresh, sync)

   Cognito User Pool (per env, invite-only, PKCE SPA client) ──JWT──► the app
```

## 2. Environments — dev + prod

Two isolated copies of everything, so changes can be tested before touching real data — **in two AWS accounts** (since the dev-account PR, 2026-10-31):

- **Management account** (the original one): prod, and the Organization. **SCPs never apply to a management account**, so prod has no SCP protection; its protection is that no dev credential exists in it — true since the dev-account PR's post-merge teardown redeployed `ApertureCicd` without the old dev roles and removed the old dev resources (2026-11-01; until then the old `aperture-github-deploy-dev` there could still assume the admin bootstrap, so `dev-cutover` checks they're gone first).
- **Dev account** (`aperture-dev`, in the `Dev` OU): dev alone — two slots of it, `dev` and `devb` (since the `dev-slot-b` PR, so two branches can be on dev at once; CI-BOT.md → _Dev slots_) — under the SCPs and kill switch of §3, which are account-wide and so cover both. Bot-dispatched branch code runs here with no human step, so its worst case is bounded by construction — cost model and residuals: [CI-BOT.md](../ops/CI-BOT.md) → _Dev deploy blast radius_. Its compute cap is the sum of its functions' reserved concurrency (30 per dev stack, `cdk/src/config/devAccount.ts`), whatever the account quota; nothing in dev may ask for more quota, and only main's lane, break-glass and the kill may change a reservation. The values and the quota: [CI-BOT.md](../ops/CI-BOT.md) → _Dev deploy blast radius_ → Compute. Break-glass: `OrganizationAccountAccessRole`, assumed from the management account (`--profile aperture-dev`); every SCP deny exempts it.
- Stacks per env: `ApertureData-{dev,devb,prod}` + `ApertureApp-{dev,devb,prod}`, each in its stage's account, each through that account's stock CDK bootstrap (`hnb659fds`) — except main's own dev deploy, which goes through the dev account's second bootstrap (`devmain`), whose execution role the freeze exempts (CI-BOT.md → _Dev deploys_ → _Two lanes_). Each dev lane publishes to its own bootstrap's asset bucket (a shared one would let the bot lane plant what main's lane deploys), so dev's app stack carries no CDK provider function — it owns its log groups and its site bucket has no auto-delete — and the lanes' templates differ only in the `BootstrapVersion` parameter and the asset bucket (`cdk/src/config/lane.ts`, picked by `APERTURE_DEPLOY_LANE`). The deploy role's ARN is what picks the account — there is no separate account setting to drift.
- Isolated resources per env: DynamoDB table (`aperture-dev` / `aperture-prod`), Cognito User Pool, Lambda, S3 bucket, CloudFront distro, SSM parameters, GitHub OIDC provider and roles.

## 3. CDK stacks — split stateful from replaceable

- **`ApertureData-<env>`** — DynamoDB table + Cognito User Pool + the **Files bucket** (task attachments; `RETAIN`, presigned-only, CORS = the stage's app domain — design: `areas/tasks/attachments.md` D5/D9). `removalPolicy: RETAIN`, deployed rarely, protected from teardown. _(Precious: your data + your identity.)_
- **`ApertureApp-<env>`** — Lambda + Function URL + S3 (Site) + CloudFront (+ ACM cert reference, since the domain step, §8). Redeploys freely; nothing precious. The BFF and MCP Lambdas get an object-scoped (`u/*`) `s3:PutObject/GetObject/DeleteObject` grant on the data stack's Files bucket, to sign presigns and delete an attachment's bytes.

Rationale: never let an app redeploy endanger the stateful resources.

Hand-deployed, never by the pipeline (re-run by hand when they change):

- **`ApertureCicd`** (management account) / **`ApertureCicdDev`** (dev account) — each account's GitHub OIDC provider and roles (§9). One class, `cicd-stack.ts`, with `roles: 'prod' | 'dev'`.
- **`ApertureOrg`** (management account, us-east-1; `cdk/src/lib/org-stack.ts`) — the dev account's guardrails: four SCPs, the kill Lambda (`lambdas/src/kill/`), the dev budget. The management account's admin bootstrap — prod's deploy path — is thereby also Organization admin (it could detach SCPs); prod changes still pass the user's PR review. `cdk deploy ApertureOrg -c org=true -c mgmtAccountId=… -c devAccountId=… -c devOuId=…`.
  - **`aperture-dev-allowlist`** — every service outside the ~14 the dev stacks, CDK and CI use is denied (EC2, Bedrock, SNS, EventBridge, CloudWatch writes, ACM requests, SSM beyond Parameter Store, and anything AWS adds later).
  - **`aperture-dev-guardrails`** — us-west-1 only (global services exempt, plus `kms:DescribeKey` / `kms:CreateGrant`: attaching the us-east-1 ACM cert to CloudFront reads and grants on `aws/acm` there under the deploying role — free, and with no key to use them on, since `kms:CreateKey` stays denied); no quota requests, support cases or leaving the org; no provisioned concurrency, recursion-detection changes or event-source mappings; no DynamoDB restores, backups, global tables, reserved capacity or Contributor Insights; no CloudFront invalidations, alias moves or paid add-ons; no IAM users, access keys or federation changes; no paid log, KMS and S3 add-ons, and no S3 storage class but Standard; the break-glass and kill roles untouchable; only the dev-main GitHub role (and break-glass) may assume a `devmain` bootstrap role, and nothing a GitHub role (`OnlyMainAssumesItsLane`); nothing but break-glass may change or pass a `devmain` or `aperture-github-*` role — bar the devmain deploy role passing its own execution role to CloudFormation (`NoLaneTampering`); every stack call names its role, so none inherits a stack's stored one (`NameTheStackRole`); and devmain's bucket, version parameter and toolkit stack are writable only by its publishing role or break-glass (`DevMainBootstrapIntact`).
  - **`aperture-dev-freeze`** — a function's shape (create, configuration, URL, permissions, async destinations, reserved concurrency), the table (create/update/delete, PITR, resource policy), the schedules, the user pool (sign-up, clients and their callback URLs, the domain, users), new code in CDK's 15-minute provider functions, and every grant that would outlive a kill (new buckets and distributions, bucket policies, ACLs and lifecycle rules, new roles and role trusts). Attached after the first deploy into the account. Also exempts the `devmain` bootstrap's execution role — main's own dev deploy. A dispatched or `dev`-pushed branch that changes any of these — or a CDK bump that changes a provider function — needs the freeze opened by hand (CI-BOT.md → _Kill switch_).
  - **`aperture-dev-kill`** — deny-all, unattached until the kill switch fires.
  - Every deny exempts the break-glass role; the standing three also exempt the kill switch's own `aperture-kill-*` roles (its forwarder must reach the management account) — except the three lane guardrails, which exempt only what main's lane needs — and the freeze also exempts the `devmain` execution role. SCPs bind the CloudFormation execution role too, so a deploy can never do what the SCPs deny — however the template asks. The SCP policy type has to be enabled on the Organization's root once (`enable-policy-type`); no Resource Control Policy — the freeze denies the grants an RCP would police.
- **`ApertureDevGuard`** (dev account; `dev-guard-stack.ts`) — the kill switch's alarms and the rule forwarding them to `ApertureOrg`. Deployed before `ApertureOrg` attaches the SCPs (they deny the execution role its CloudWatch and EventBridge writes and its role), and before `ApertureOrg` itself, whose bus policy names its forwarder role; a later change needs the standing SCPs detached first (CI-BOT.md → _Kill switch_).
- **`ApertureBilling`** (management account, us-east-1) — the $5 budget (§11). Unfiltered in a management account, so it now covers the whole Organization's consolidated bill, dev included.

`ApertureDevSandbox` — PR 72's dev-only bootstrap inside the shared account (qualifier `devsandbox`, a permissions boundary on every dev role) — was retired by the dev-account PR: the account boundary does its job, and the SCPs cap even the stock bootstrap's admin execution role.

## 4. Compute & API

- **One multi-route BFF Lambda** per env (all routes in a single handler). Node 22 runtime, esbuild-bundled via CDK.
- **Lambda Function URL**, auth type **`NONE`**, fronted by CloudFront. Not OAC: CloudFront OAC can't SigV4-sign POST bodies to a Function URL. Instead CloudFront stamps a shared **origin-secret header** (`ORIGIN_SECRET`) on every origin request and the handler 403s anything without it, so the raw URL is useless directly. Defense-in-depth only — the in-handler Cognito JWT check is the real auth gate. The MCP Lambda's URL works the same way. (`cdk/src/lib/app-stack.ts` class comment.)
- **Auth:** validate the Cognito JWT **in-handler** (JWKS signature + issuer/expiry), extract `sub` → `userId` scoping every DynamoDB item.
- Config: ~15s timeout, 512 MB, **no warming** (single user — cold starts are fine). Env vars: `TABLE_NAME`, `FILES_BUCKET`, `USER_POOL_ID`, `MCP_CLIENT_ID`, `STAGE`, `ORIGIN_SECRET`, `DEVICE_TOKEN`, `PLAID_ENV`, `FINANCE_SYNC_FN` (+ optional `DEVICE_USER_ID`). The BFF verifier is deliberately **not** bound to one app client (D14) — `MCP_CLIENT_ID` is the claude.ai MCP client, and the BFF **rejects** tokens minted for it (the MCP Lambda does the opposite: it accepts only that client).
- **Writes-object pattern** enforced (single audit point for all side effects; guarantees no writes during smoke tests).
- **Recurrence generation: lazy on read** — when a day loads, materialize any due `taskSeries` occurrences. No cron for recurrence.
- **Four functions:** the BFF, the MCP server (`aperture-mcp-<stage>`, [mcp/](../areas/mcp/index.md)), and the **finance sync** (`aperture-finance-sync-<stage>`, `cdk/src/lib/finance-sync.ts`): 300 s, 512 MB, no Function URL, invoked only asynchronously — by the BFF after a sync request, connect or reconnect, and by **EventBridge Scheduler** at 5:15a / 3:15p / 8:15p LA (the one scheduled job; created only when `DEVICE_USER_ID` is set). It sits alone in schedule group `aperture-finance-<stage>` because Scheduler checks its role's `aws:SourceArn` against the group ARN, never the schedule's; the one-schedule group keeps the role assumable by that job only. Never retried by Lambda; 30-day log group (the BFF and MCP groups: 14 days on dev, 90 on prod, via `logRetention` since 2026-10-13 — they were Lambda-created and never expired; [CI-BOT.md](../ops/CI-BOT.md) → _Dev logs_); reserved concurrency 1 on dev only, a cost cap (a per-item CAS lock is the concurrency control). Its IAM is GetItem/PutItem/Query on the table + Plaid SSM read. `PLAID_ENV` is `production` on prod, else `sandbox`; the BFF may invoke exactly this function. Timing and design: [finances/](../areas/finances/index.md). The **push dispatch** (`aperture-push-dispatch-<stage>`, `cdk/src/lib/push-dispatch.ts`, cloned from finance-sync) is the reminder poller: EventBridge Scheduler `cron(* * * * ? *)` (once a minute, at the schedule's own second, not :00) in its own group `aperture-push-<stage>`, 20 s / 256 MB, no Function URL, never retried (Lambda and Scheduler), timeout < the minute so ticks can't overlap; reserved concurrency 1 on both stages. On dev every function reserves its share (BFF 18, MCP 10, these two 1 each: `cdk/src/config/devAccount.ts`); on prod the poller's is the only one. Registry-driven, not gated on `DEVICE_USER_ID`. IAM: GetItem/PutItem/Query/DeleteItem on the table + GSI1, and the one SSM read of its VAPID private key; the BFF reads only the public one. Design: [tasks/reminders](../areas/tasks/reminders.md).

## 5. Data — DynamoDB

Single table per env (`aperture-<env>`), **on-demand** billing, **PITR on** (35-day continuous backup — the safety net), `RETAIN`. Keys/GSI per `TECH.md §2.4`. One GSI, two key spaces (calibration's done tasks; finance transactions by date). Reads/aggregation in the Lambda.

## 6. Auth — Cognito

- **One User Pool per env.** Self-signup **OFF** (invite-only; you admin-create your own user). MFA optional.
- **App client:** SPA type, PKCE, no secret. Callback URLs = the env's app URL (CloudFront default first; the custom domain from §8 was added when it went live). **`refreshTokenValidity` is 30 days** (Cognito's default; 7 until 2026-11), with token revocation pinned on — it sets how often a password is actually typed; access/ID tokens stay at the 1-hour default. Why, and the renewal behaviour built on it: `TECH.md` §3.
- **Second app client — `aperture-claude-<env>`** — the claude.ai MCP connector (no secret, authorization-code flow, callback URLs = Anthropic's connector constants, **30-day** refresh — why: `areas/mcp/index.md` D13). Plus an **MCP resource server** (identifier `<app-url>/mcp`, one `access` scope). Both live in the **app** stack (not the precious data stack) — the MCP OAuth façade + the credential-not-method fork are in **[areas/mcp/index.md](../areas/mcp/index.md)**.
- **Hosted UI** on a Cognito domain prefix (e.g. `aperture-dev.auth.us-west-1.amazoncognito.com`) — free, independent of the app's custom domain. Google IdP optional. The MCP function reads this host (`COGNITO_DOMAIN`) to build the façade's `/oauth2` endpoints.
- Frontend: `react-oidc-context` + Hosted UI.
- **Dev test user** `rahul3datta+devcheck@gmail.com` — dev pool only, never prod; admin-created (invite suppressed, email verified, no MFA), permanent password in the gitignored `.secrets/devcheck.dev.env`. It signs in through the same Hosted UI and owns its own partition; the dev check uses it ([ops/DEV-CHECK.md](../ops/DEV-CHECK.md)).

## 7. Hosting & CDN

- **S3** (private) + **CloudFront** per env. Default behavior → S3 (OAC); `/api/*` → Function URL origin (origin-secret header, §4). **SPA fallback:** 403/404 → `/index.html` for client-side routing — distribution-wide, so it rewrites an `/api/*` origin 403/404 too (a BFF 404 reaches the browser as a 200 web page). A route a non-browser client reads must not answer 404 — the Shortcut route uses 422 ([tasks/places](../areas/tasks/places.md#4-the-shortcut-route)).
- **`/mcp`** → the second (MCP) Function URL origin, plus three narrowly-scoped `/.well-known/oauth-*` GET behaviors on the same origin (the claude.ai OAuth metadata façade — **never** `/.well-known/*`). `/mcp` uses a **1 s-max-TTL** cache policy (not zero — the mechanism and why are in `areas/mcp/index.md` → _claude.ai — the OAuth façade_ → Decisions) that carries `Authorization` in the cache key, while its origin-request policy forwards the agent-token + MCP headers. Design: **[areas/mcp/index.md](../areas/mcp/index.md)**.
- **Build on the CloudFront default domain first** (`*.cloudfront.net`) — HTTPS + PWA install work immediately, zero DNS. The custom domain was the last step, and is live (§8).
- **Publish discipline** (`scripts/aws/publish-frontend.mjs`, used by CI + local emergency publishes): **two-pass S3 sync** — hashed `assets/*` get `max-age=31536000,immutable`; everything else (`index.html`, `sw.js`, manifest, icons) gets `no-cache,no-store,must-revalidate` so a client never holds a stale shell (old `assets/*` hashes are never deleted — the shell pass excludes them — so in-flight clients keep loading old chunks; the bucket grows ~600 KiB per deploy). **PWA files get explicit `--content-type`** (`manifest.webmanifest` → `application/manifest+json`, `sw.js` → `text/javascript`) because `s3 sync` guesses by extension and an octet-stream manifest silently blocks install. Flux's `.wasm` gets the same treatment (`application/wasm`, still immutable) — Safari's streaming compile refuses anything else — and is uploaded **brotli-encoded** (`Content-Encoding: br`, the decoded size as `x-amz-meta-raw-length`; `scripts/aws/flux-wasm.mjs`) because CloudFront compresses nothing over 10 MB; the build names it `*.br.wasm` so the encoded body never lands under a key an edge already holds uncompressed. `health-check.mjs` asserts type, encoding and raw length at the edge (a missing asset would come back as the SPA fallback's 200 `text/html`). Design: **[areas/flux/index.md](../areas/flux/index.md)** (D63).

- **Each stage's cert lives in its own account** (since the dev-account PR): dev's — and devb's, `devb.aperture.rahuldatta.dev` (`CERT_ARN_DEVB`) — in the dev account's us-east-1, prod's in the management account's. The cert is requested by the break-glass role: the allowlist SCP denies ACM requests to everything else. A CloudFront alternate domain name is globally unique, so moving `dev.aperture.rahuldatta.dev` between accounts meant deleting the old distribution first (about 20–40 min of dev downtime, once).
- **Status (2026-08): LIVE** (re-verified 2026-09-26: `dig NS rahuldatta.dev` → `dns1–4.p03.nsone.net`; `curl -sI aperture.rahuldatta.dev` answers from CloudFront). Planned as the last step, off the critical path, wired right before real daily use. Both stages serve on their custom domains — prod `aperture.rahuldatta.dev`,
  dev `dev.aperture.rahuldatta.dev` — on us-east-1 ACM certs (DNS-validated via Netlify/NS1 DNS, not
  Porkbun: rahuldatta.dev is registered at Porkbun but its nameservers are delegated to Netlify), referenced by ARN through the
  `CERT_ARN_*` GitHub vars. Login round-trips on both (Cognito callbacks registered for each origin).
- **One-time, $0, no recurring work:** create ACM certs in **`us-east-1`** (DNS validation), add the validation CNAMEs at the DNS host (Netlify) once, add the CloudFront alias CNAMEs once. ACM **auto-renews** DNS-validated certs while the CNAME stays — no per-deploy, no per-renewal work.
- **Reference certs by ARN in CDK** (don't have CDK create them) → deploys never touch DNS/certs. The
  ARN comes from `APERTURE_CERT_ARN` (GitHub **var** `CERT_ARN_DEV`/`CERT_ARN_PROD` per stage), read in
  `cdk/src/config/domains.ts` alongside the committed domain names; the app stack takes `domainName` +
  `certificateArn` props and adds the alias + cert to CloudFront only when both are present (else stays
  on the CloudFront default domain, so pre-domain deploys are unaffected).
- **Region note:** the cert lives in **`us-east-1`** (CloudFront's hard requirement) even though the
  stacks deploy to **`us-west-1`** — referencing by ARN makes the split a non-issue.

## 9. CI/CD — GitHub Actions, OIDC

No static credentials — OIDC role assumption. GitHub Flow, simplified:

- Feature branch → PR (three parallel `ci.yml` jobs: `check` = secret scan (gitleaks) + lint + typecheck + non-app tests, `test-app-1`/`test-app-2` = the app suite halved by `vitest --shard`; the same reusable workflow the pipeline runs) → squash to `main`. The secret scan was its own `gitleaks.yml` workflow until `ci-minutes-trim` (2026-11): a one-minute job on every PR and push, now a step of `check` with the same action, full-history checkout and `pull-requests: read` (it lists a PR's commits).
- `main` pipeline: lint/typecheck/test (pnpm + Vitest) → `cdk diff --method=template` → `cdk deploy ApertureData-dev` + `ApertureApp-dev` (`--method=direct`) → smoke dev → build app (Vite, env from CDK outputs) → S3 sync (no CloudFront invalidation — publish bullet below) → health check polls the edge for the new shell → same for prod, **automatically — no approval pause** (see the caveat below).
- **The check is tuned for the 2-vCPU private-repo runner.** Three parallel jobs, so the app suite runs beside lint/typecheck/the other tests, itself split in two by `vitest --shard`. Each shard runs on Vitest's one default worker: app tests share one jsdom instead of one per file, and a second worker measured no faster (2026-10-13: app suite 37.8/46.5/43.6s on two vs 35.5/45.9/42.1s on one). Lint + typecheck results are cached across runs (`actions/cache`, keyed per commit). Every job that installs (the three, and `deploy-stage.yml`) uses the local `.github/actions/setup`: Node from `.nvmrc` via `actions/setup-node` (the image's own Node moved to 24 on 2026-10-30 and the drift guard failed every job) + pnpm via corepack, guarded against drift from `.nvmrc` / `packageManager`, with no pnpm store cache (restoring it cost 4–6s and install took 10–12s either way). The test-side rules live in `product/CONVENTIONS.md` (_Command shape_); why the cache can't false-pass is in the comment above the cache step in `.github/workflows/ci.yml`.
  - **The mailroom fixture suite is gated on PRs** (`ci-check-speed`, 2026-11): `scripts/src/mailroom/runner-fixtures.test.ts`, ~210 s of the ~300 s non-app step, runs in its own step, on a PR only when `scripts/src/fixture-inputs.ts` says one of its inputs changed (its `FIXTURE_INPUTS`: `tools/mailroom/`, `scripts/src/mailroom/` and the files that run them), and on a main push unless a PR run already ran it on that exact tree (_Tree-matched main checks_ below: in full, alone on `fixtures`, not at all on `skip`). A skip is a notice annotation on the run. Trade-off: a break that reaches the suite without touching those paths (a dependency bump, the runner image) isn't caught on its PR but on the main push, where `check` stops the deploy. Saves ~3 billed min per skipped PR run (~90% of runs).
  - **Measured 2026-10-13:** check 105s / 2 billed min (one job, main run 38347127185) → slowest job 54–56s / 3 billed min (dev run 38357193549, 3 attempts; setup + install 14–18s a job). `check` and `test-app-2` finish within a few seconds of each other; the shards are uneven (~17–19s vs ~28–35s of tests) because the file hash put the heaviest files together.
- **Tree-matched main checks** (`ci-minutes-trim`, 2026-11): a main push skips its own `check` when a green PR run already checked the exact same git tree. A PR run tests `refs/pull/N/merge`; when main didn't move before the squash-merge, the squash commit's tree is that merge's tree byte for byte — code and workflow files alike. `ci.yml`'s `check` prints the tree it tests as a `tested-tree` notice (an inline YAML line, so the emitter is reviewed workflow code); deploy.yml's `changes` runs `scripts/src/checked-tree.ts`, which plans `skip`, `fixtures` or `check`. It trusts only the merged PR's head check runs by the `github-actions` app, the newest suite with `ci / check` and both shards green, a `pr.yml` `pull_request` run on that head, exactly one `tested-tree` notice equal to the squash tree, and a green `Secret scan` step. When that PR run skipped the fixture suite, `fixtures` runs the suite alone on main (`ci.yml`'s `fixtures_only`), keeping the guarantee in the bullet above. Anything else — batched merges (main moved), a bot- or other-app run, a failed shard, an API error — is `check`, the full run. A failed `changes` runs the check and deploys nothing; the deploy jobs spell out their `needs` results, since a skipped `check` upstream would fail the implicit `success()`. `deploy-dev.yml`'s `verify` previews the plan for the open PR (CI-BOT.md → _Dev deploys_). Measured from November's runs: about 58% of merges match; a matched merge bills ~5–10 minutes instead of ~18 and reaches prod ~7 minutes sooner. GitHub's "require branches up to date" toggle would make every merge match, at the cost of a rebase per merge — not set.
- **No ntfy** (dropped at `ci-minutes-trim`, 2026-11, the user's call; its `notify` jobs billed a minute every run): a failed main run reaches the merger through GitHub's own Actions notification to the run's actor — the merger needs it on under Settings → Notifications → Actions (email, failed workflows) — and a dispatch's conclusion through the bot to its session. deploy.yml's `quiet-failure` job fails the run in the two cases that notice could miss: `changes` succeeded but `deploy-dev` was skipped with no job failing (an unplanned skipped `check`, or a result the guards don't expect), or any job ended `cancelled` (a deploy job past its timeout may leave the run `cancelled`, not failed). It bills nothing unless it fires (on a run the user cancels it still runs, about a minute, without changing the outcome).
- **The `dev` branch is retired** (`dev-cutover`): until then a user push to `dev` was a one-off dev deploy, and `deploy.yml` triggered on it. The branch is deleted; the `dev` ruleset (CI-BOT.md → _Setup_ step 6) stays to keep it deleted — only the admin bypass can recreate it, and nothing should, because every older commit's `deploy.yml` still deploys a `dev` push.
- **Prod never moves backwards** (since ci-bot, 2026-10-29): deploy-stage's first prod-only step refuses a commit behind prod's last successful deployment (GitHub's deployment record for `environment: prod`; `compare` must say `ahead` or `identical`), so re-running an old successful run can't roll prod back (the bot holds Actions: write). Back-to-back merges still both deploy — the older run is ahead of prod. No rollback by re-run: a revert goes through a PR. Runs from before ci-bot merged carry the old YAML and stay re-runnable, unguarded, for 30 days.
- **Bot-dispatched dev deploys** (`pnpm bot deploy-dev` → `deploy-dev.yml`, on `main` or, for a `.github/`-changing branch, on that branch): built 2026-10-13, **on** since `dev-cutover`, after the dev-account PR moved dev into its own account (§2, §3). The run refuses unless the repository variable `DEV_DEPLOY_ISOLATED` is `true` — the user's pause switch. The only way a branch reaches dev. Details, dev lock and run-name contract: [CI-BOT.md](../ops/CI-BOT.md).
- **Job timeouts** bound how long a job holds AWS credentials: `deploy-stage.yml` 30 min on dev, 60 on prod (a full deploy measures 10–15; a killed prod job would leave CloudFormation mid-update); `deploy-dev.yml`'s verify 5; `fetch-dev-logs.yml` 15. The bot can't edit workflows, so branch code can't lift them.
- **Build marker.** `publish-frontend.mjs` stamps the deployed commit (`APERTURE_BUILD_SHA`, else `GITHUB_SHA`) into `<meta name="aperture-build">` and the Settings footer; `health-check.mjs` asserts the edge serves the marker of the build it just published. The dev check and the Simulator read it to prove which build they test.

- **Deploy-time safety checks:**
  - **Single synth, shared by diff + deploy** — each stage runs `cdk synth … --no-lookups` once to `cdk.out`, then `cdk diff --app cdk.out` and `cdk deploy --app cdk.out` consume that same assembly. No double esbuild bundle, and the diff you read is byte-identical to what deploys. `--no-lookups` fails loudly if an (unexpected) context lookup is ever introduced.
  - **`cdk diff` before every `cdk deploy`** (informational, both stages, `--method=template`: compares the synthesized template with the deployed one via the lookup role). It was `--method=change-set`, chosen so the diff failed under the real deploy role rather than silently falling back to a template diff — but the deploy then built a second, identical change set (5–19 s per stage), and the deploy itself now exercises the deploy role moments later. Given up: CloudFormation's own change-set analysis; property-level "requires replacement" still comes from CDK's resource spec. If a template diff shows every resource of an existing stack as added, distrust it — it couldn't read the deployed template — rather than the stack. Since no prod approval pause is configured, the diff in the run log is the visible record of what each deploy is about to change to infra — and the only thing standing between a bad CDK edit and a real bill. **Read it on the dev run before merging to `main`.** A clean one looks like the 2026-09-07 device-token deploy: `Number of stacks with differences: 1`, two `[+] Added:` env vars, no resources.
  - **Branch up-to-date with main** — `deploy-dev.yml`'s `verify` (and `pnpm bot deploy-dev` before it) refuses a commit that doesn't contain `origin/main`. This is the enforced form of "dev only ever runs code that already contains `main`" — otherwise what you validate on dev isn't what a squash-merge would produce, and a stale branch could redeploy an older cdk app into the dev account. Until `dev-cutover` the same check ran in `deploy.yml`'s `changes` job on a `dev` push; it went with the `dev` trigger. (GitHub's native "require branches up to date before merging" ruleset toggle is a different control — it acts on the PR at merge time, not on a dev deploy, so it couldn't replace this check. It was originally rejected because it needed a designated required status check, which the ruleset lacked then; it has three now, so enabling it is an open, separate decision — not done.)
  - **`cdk deploy --method=direct`** — UpdateStack without a change set: same CloudFormation rollback-on-failure, less per-resource progress in the log; unchanged stacks still no-op and `--outputs-file` is still written.
  - **`concurrency` group per ref**, `cancel-in-progress: false` — serializes deploys so two quick pushes can't race a half-applied stack; never cancels a deploy mid-flight. **Plus a job-level group per stage** in `deploy-stage.yml` (`deploy-stage-<stage>`, also queue-not-cancel): the per-ref group can't stop a `main` push (which deploys dev first) and a bot dispatch from deploying the dev stage at once. Whichever takes the lock last is what dev runs — fine for a scratch stage. The per-ref group caps `main` at one run, and deploy-dev.yml's own group plus `refs/locks/dev` cap dispatches at one, so at most two jobs contend; GitHub's one-pending-per-group rule (a third contender cancels the older pending job, which then reads `cancelled` and fails `quiet-failure`) can't trigger on the stage group today. It does trigger on the per-ref group: when merges cluster, the older pending runs are cancelled with no jobs (2026-11-05: three of five merges). That is harmless because classification doesn't use the previous push.
  - **Publish + health check** — `publish-frontend.mjs` creates **no CloudFront invalidation** (since the dev-account PR; it had already stopped waiting for one — the CLI waiter cost a flat 20–22 s per stage). Every file outside `assets/` is uploaded `no-store` and `assets/` names are content-hashed, so the edge serves a new build within the 1 s min TTL anyway (checked on dev's live headers, 2026-10-31), and paths past 1,000 a month bill per path — a cost lever, so neither GitHub role may create one. `health-check.mjs` reads the `/assets/*` refs from the `app/dist/index.html` it just built and polls `/` (backoff 1 → 8 s, ~60 s budget) until the edge serves all of them — proof the edge serves _this_ build — then runs the endpoint checks. It converges in a second or two because the shell is `no-store` with the default behaviour's 1 s min TTL, and the 403/404 SPA-fallback responses have `ttl: 0`. No cache-buster: the default behaviour ignores query strings. `sw.js` and the manifest are excluded from the shell sync and uploaded once each by their pinned-Content-Type `cp`.

## 11. Cost

Effectively free at single-user scale: DynamoDB / Lambda / Cognito within always-free tiers; S3 + CloudFront in cents; Function URLs add no per-request cost. **No Route 53** (DNS is at Netlify/NS1; the domain is registered at Porkbun — §8). Only real line item: S3/CloudFront, pennies. The finance sync (3 scheduled runs a day, ~5–20 s each), the push dispatch (one ~0.3 s tick a minute, ~$0.04/mo of DynamoDB; worst case a stuck tick ≈ $0.15/day, [tasks/reminders](../areas/tasks/reminders.md#5-security-and-cost)), EventBridge Scheduler and the alarms sit inside the free tiers — prod's five plus the dev account's five kill alarms make the free ten (the push dispatch adds no alarm of its own: no fixed monthly cost, so the account-wide Lambda Errors alarm covers it) (the free tier is shared across the Organization's consolidated bill — AWS Billing docs, _Consolidated billing_); Plaid Trial is $0 with a hard cap of 10 linked bank logins. The Organization, the SCPs, the kill Lambda and SNS email are free; the dev budget is the second of two free budgets. Dev's table carries an on-demand ceiling (100 read / 50 write units, table and GSI1) that the freeze SCP keeps in place, and expires tombstones through TTL, whose deletes use no write capacity and cost nothing; prod's has none. The dev account's worst case under a rogue branch: CI-BOT.md → _Dev deploy blast radius_.
