# Aperture — Infrastructure

The AWS blueprint behind `TECH.md`. All IaC via **CDK**. Two AWS accounts under one Organization (§2). Region: **`us-west-1`** for the data + app stacks. **`us-east-1`** only where AWS requires it: the CloudFront ACM certs (§8), the billing stack (Cost Explorer / anomaly data lives there) and `ApertureOrg` (Organizations, Budgets and the kill switch's event bus, §3).

---

## 1. Shape

```
GitHub Actions ──(OIDC, no static keys)──► cdk deploy + app build/deploy

        ┌──────── CloudFront (per env, HTTPS) ────────┐
        │   default behavior → S3   (React PWA, OAC)  │
        │   /api/*            → Lambda Function URL    │  (public; secret header)
        └──────────────────────────────────────────────┘
              │                              │
            S3 (static)              Lambda BFF (1, multi-route)
                                            │  validates Cognito JWT in-handler
                                            ▼
                                     DynamoDB (single table, on-demand, PITR)
                                            ▲
   Lambda BFF ──async invoke──► finance-sync Lambda ◄── EventBridge Scheduler (3×/day)
        └──HTTPS──► Plaid ◄──HTTPS──┘   (BFF: link token, exchange, remove; sync: accounts, refresh, sync)
   Lambda BFF / MCP ──async invoke──► coach-worker Lambda   (the LeetCode coach's AI pick, ≤ 1 a day)

   Cognito User Pool (per env, invite-only, PKCE SPA client) ──JWT──► the app
```

Not drawn: the **MCP Lambda** (its own Function URL behind CloudFront's `/mcp` and `/.well-known/` OAuth/OIDC metadata behaviours — §4, [mcp/](../areas/mcp/index.md)), the **push-dispatch Lambda** on its once-a-minute Scheduler tick (§4, [tasks/reminders](../areas/tasks/reminders.md)), and the **Files bucket**, which the browser reaches by presigned URL (§3, [tasks/attachments](../areas/tasks/attachments.md)).

## 2. Environments — dev + prod

Two isolated copies of everything, so changes can be tested before touching real data — **in two AWS accounts** (since the dev-account PR, 2026-10-31):

- **Management account** (the original one): prod, and the Organization. **SCPs never apply to a management account**, so prod has no SCP protection; its protection is that no dev credential exists in it — true since the dev-account PR's post-merge teardown redeployed `ApertureCicd` without the old dev roles and removed the old dev resources (2026-11-01; until then the old `aperture-github-deploy-dev` there could still assume the admin bootstrap, so `dev-cutover` checks they're gone first).
- **Dev account** (`aperture-dev`, in the `Dev` OU): dev alone — two slots of it, `dev` and `devb` (since the `dev-slot-b` PR, so two branches can be on dev at once; CI-BOT.md → _Dev slots_) — under the SCPs and kill switch of §3, which are account-wide and so cover both. Bot-dispatched branch code runs here with no human step, so its worst case is bounded by construction — cost model and residuals: [CI-BOT.md](../ops/CI-BOT.md) → _Dev deploy blast radius_. Its compute cap is the sum of its functions' reserved concurrency (30 per dev stack, `cdk/src/config/devAccount.ts`), whatever the account quota; nothing in dev may ask for more quota, and only main's lane, break-glass and the kill may change a reservation. The values and the quota: [CI-BOT.md](../ops/CI-BOT.md) → _Dev deploy blast radius_ → Compute. Break-glass: `OrganizationAccountAccessRole`, assumed from the management account (`--profile aperture-dev`); every SCP deny exempts it.
- Stacks per env: `ApertureData-{dev,devb,prod}` + `ApertureApp-{dev,devb,prod}`, each in its stage's account, each through that account's stock CDK bootstrap (`hnb659fds`) — except main's own dev deploy, which goes through the dev account's second bootstrap (`devmain`), whose execution role the freeze exempts (CI-BOT.md → _Dev deploys_ → _Two lanes_). Each dev lane publishes to its own bootstrap's asset bucket (a shared one would let the bot lane plant what main's lane deploys), so dev's app stack carries no CDK provider function — it owns its log groups and its site bucket has no auto-delete — and the lanes' templates differ only in the `BootstrapVersion` parameter and the asset bucket (`cdk/src/config/lane.ts`, picked by `APERTURE_DEPLOY_LANE`). The deploy role's ARN is what picks the account — there is no separate account setting to drift.
- Isolated resources per env: DynamoDB table (`aperture-dev` / `aperture-devb` / `aperture-prod`), Cognito User Pool, Lambda, S3 bucket, CloudFront distro, SSM parameters. The GitHub OIDC provider and roles are per **account** — slot `devb` shares dev's (§9).

## 3. CDK stacks — split stateful from replaceable

- **`ApertureData-<env>`** — DynamoDB table + Cognito User Pool + the **Files bucket** (task attachments; `RETAIN`, presigned-only, CORS = the stage's app domain — design: `areas/tasks/attachments.md` D5/D9). `removalPolicy: RETAIN`, deployed rarely, protected from teardown. _(Precious: your data + your identity.)_
- **`ApertureApp-<env>`** — Lambda + Function URL + S3 (Site) + CloudFront (+ ACM cert reference, since the domain step, §8). Redeploys freely; nothing precious. The BFF and MCP Lambdas get an object-scoped (`u/*`) `s3:PutObject/GetObject/DeleteObject` grant on the data stack's Files bucket, to sign presigns and delete an attachment's bytes.

Rationale: never let an app redeploy endanger the stateful resources.

Hand-deployed, never by the pipeline (re-run by hand when they change):

- **`ApertureCicd`** (management account) / **`ApertureCicdDev`** (dev account) — each account's GitHub OIDC provider and roles (§9). One class, `cicd-stack.ts`, with `roles: 'prod' | 'dev'`.
- **`ApertureOrg`** (management account, us-east-1; `cdk/src/lib/org-stack.ts`) — the dev account's guardrails: four SCPs, the kill Lambda (`lambdas/src/kill/`), the dev budget. The management account's admin bootstrap — prod's deploy path — is thereby also Organization admin (it could detach SCPs); prod changes still pass the user's PR review. `cdk deploy ApertureOrg -c org=true -c mgmtAccountId=… -c devAccountId=… -c devOuId=…`.
  - **`aperture-dev-allowlist`** — every service outside the 13 the dev stacks, CDK and CI use (SSM as Parameter Store only), plus reads of ACM, CloudWatch, Service Quotas, Organizations and Account, is denied: EC2, Bedrock, SNS, EventBridge, CloudWatch writes, ACM requests, SSM beyond Parameter Store, and anything AWS adds later (`org-stack.ts` → `allowlistPolicy`).
  - **`aperture-dev-guardrails`** — us-west-1 only (global services exempt, plus `kms:DescribeKey` / `kms:CreateGrant`: attaching the us-east-1 ACM cert to CloudFront reads and grants on `aws/acm` there under the deploying role — free, and with no key to use them on, since `kms:CreateKey` stays denied); no quota requests, support cases or leaving the org; no provisioned concurrency, recursion-detection changes or event-source mappings; no DynamoDB restores, backups, global tables, reserved capacity or Contributor Insights; no CloudFront invalidations, alias moves or paid add-ons; no IAM users, access keys or federation changes; no paid log, KMS and S3 add-ons, and no S3 storage class but Standard; the break-glass and kill roles untouchable; only the dev-main GitHub role (and break-glass) may assume a `devmain` bootstrap role, and nothing a GitHub role (`OnlyMainAssumesItsLane`); nothing but break-glass may change or pass a `devmain` or `aperture-github-*` role — bar the devmain deploy role passing its own execution role to CloudFormation (`NoLaneTampering`); every stack call names its role, so none inherits a stack's stored one (`NameTheStackRole`); and devmain's bucket, version parameter and toolkit stack are writable only by its publishing role or break-glass (`DevMainBootstrapIntact`).
  - **`aperture-dev-freeze`** — a function's shape (create, configuration, URL, permissions, async destinations, reserved concurrency), the table (create/update/delete, PITR, resource policy), the schedules, the user pool (sign-up, clients and their callback URLs, the domain, users), new code in CDK's 15-minute provider functions, and every grant that would outlive a kill (new buckets and distributions, bucket policies, ACLs and lifecycle rules, new roles and role trusts). Attached after the first deploy into the account. Also exempts the `devmain` bootstrap's execution role — main's own dev deploy. A dispatched branch that changes any of these — or a CDK bump that changes a provider function — needs the freeze opened by hand (CI-BOT.md → _Kill switch_).
  - **`aperture-dev-kill`** — deny-all, unattached until the kill switch fires.
  - Every deny exempts the break-glass role; the standing three also exempt the kill switch's own `aperture-kill-*` roles (its forwarder must reach the management account) — except the three lane guardrails, which exempt only what main's lane needs — and the freeze also exempts the `devmain` execution role. SCPs bind the CloudFormation execution role too, so a deploy can never do what the SCPs deny — however the template asks. The SCP policy type has to be enabled on the Organization's root once (`enable-policy-type`); no Resource Control Policy — the freeze denies the grants an RCP would police.
- **`ApertureDevGuard`** (dev account; `dev-guard-stack.ts`) — the kill switch's alarms and the rule forwarding them to `ApertureOrg`. Deployed before `ApertureOrg` attaches the SCPs (they deny the execution role its CloudWatch and EventBridge writes and its role), and before `ApertureOrg` itself, whose bus policy names its forwarder role; a later change needs the standing SCPs detached first (CI-BOT.md → _Kill switch_).
- **`ApertureBilling`** (management account, us-east-1) — the $5/month budget, emailing at $1 actual and at $5 forecast. Unfiltered in a management account, so it now covers the whole Organization's consolidated bill, dev included.

`ApertureDevSandbox` — PR 72's dev-only bootstrap inside the shared account (qualifier `devsandbox`, a permissions boundary on every dev role) — was retired by the dev-account PR: the account boundary does its job, and the SCPs cap even the stock bootstrap's admin execution role.

## 4. Compute & API

- **One multi-route BFF Lambda** per env (all routes in a single handler). Node 22 runtime, esbuild-bundled via CDK.
- **Lambda Function URL**, auth type **`NONE`**, fronted by CloudFront. Not OAC: CloudFront OAC can't SigV4-sign POST bodies to a Function URL. Instead CloudFront stamps a shared **origin-secret header** (`ORIGIN_SECRET`) on every origin request and the handler 403s anything without it, so the raw URL is useless directly. Defense-in-depth only — the in-handler Cognito JWT check is the real auth gate. The MCP Lambda's URL works the same way. (`cdk/src/lib/app-stack.ts` class comment.)
- **Auth:** validate the Cognito JWT **in-handler** (JWKS signature + issuer/expiry), extract `sub` → `userId` scoping every DynamoDB item.
- Config: ~15s timeout, 512 MB, **no warming** (single user — cold starts are fine). Env vars: `TABLE_NAME`, `FILES_BUCKET`, `USER_POOL_ID`, `MCP_CLIENT_ID`, `STAGE`, `ORIGIN_SECRET`, `DEVICE_TOKEN`, `PLAID_ENV`, `FINANCE_SYNC_FN`, `COACH_WORKER_FN` (+ optional `DEVICE_USER_ID`, and `APP_URL` — the Google OAuth return base — only with a custom domain). The BFF verifier is deliberately **not** bound to one app client (D14) — `MCP_CLIENT_ID` is the claude.ai MCP client, and the BFF **rejects** tokens minted for it (the MCP Lambda does the opposite: it accepts only that client).
- **Writes-object pattern** enforced — the rule: [CONVENTIONS](../product/CONVENTIONS.md#bff-writes-one-writes-object).
- **Argument shapes at the RPC boundary** (`lambdas/src/rpc/argSpecs.ts`). `handleRpc` checks every call's arguments against its method's spec before it builds, reads or writes anything. That covers `/api`, `/mcp`, the local edge and the contract suite.
  - **What it checks:** the JSON type at full depth, required presence, arity (an extra argument is refused), unknown keys (refused by name, never dropped) and generic size bounds. The bounds are ids 128, names 200, file names 1024, prose 20 000, batches 2000, 100 000 for a log entry or an idea a capture line becomes, and 40 000 for a task title. A task title is lower because the task row can also hold its synced event's "Parent · Part" title. Where a title is copied with words added (a split's `… (cont.)`, a calendar block), the cap leaves room for them. A null counts as a value: it's refused wherever the type isn't nullable, optional slots included. A wrong shape is a `ShapeError`, a 400 naming the problem, never a 500. Nothing nested is stored as sent.
  - **What it leaves to the domain:** domain meaning stays with the domain rule and its message: enum membership, day-key formats, ranges. An enum with no domain rule behind it is checked here instead: idea status, period override, competency tags.
  - **Plaid's Link metadata:** `exchangePlaidPublicToken`'s accounts are a third party's objects, read and never stored, so their extra fields pass (`verification_status`, and whatever Plaid adds next).
  - **Owned inputs:** where a normalizer already rebuilds an input, it keeps the input with its own messages. That's the review (`normalizeSittingReview`), the push subscription (`parsePushInput`), a Flux set, a place, and settings' `fluxSets`. A Flux set that isn't an object is refused at the boundary (`flux set must be an object`), because `fluxSetError` reads its fields unguarded. The review and the push subscription still get a top-level key allowlist. The two extension ingest methods are checked for arity only.
  - **Lockstep:** the table `satisfies` a type mapped from `ApiClient`, so a new method, a changed arity or a new input field without a check fails typecheck.
  - **Body caps:** a non-ingest body over 1 MiB is a 413; ingest keeps its 300 KB.
- **Failure statuses: one mapping, two paths** (`lambdas/src/rpc/failure.ts` → `failureStatus(err, 'ingest' | 'rpc')`). Ingest is the extension's two methods; rpc is everything else.

  | Failure                                                  | ingest    | rpc       |
  | -------------------------------------------------------- | --------- | --------- |
  | `Unauthorized…` / `Unknown method`                       | 401 / 404 | 401 / 404 |
  | `ShapeError`, or our own plain-`Error` refusal           | 400       | 400       |
  | `ConflictError` (a lost CAS race)                        | 409       | 400       |
  | DynamoDB throttle                                        | 429       | 500       |
  | AWS 4xx                                                  | 400       | 500       |
  | AWS 5xx, a builtin fault (TypeError…), a non-Error throw | 500       | 500       |
  | another custom subclass (EventGoneError…)                | 500       | 400       |
  - **Shown text:** a 500 always reads `Internal error`, and any AWS error's text reads `Request refused`. AWS text can carry table ARNs and account ids, so neither path shows it.
  - **Never 429 on rpc:** the app retries a 429 as a call that never ran, which a throttle mid-write can't promise.
  - **Ingest:** the extension's outbox retries 409, 429 and 5xx (`extension/README.md` → _Statuses_).
  - **MCP:** tool errors go through the same `shownMessage`.

- **Recurrence generation: lazy on read** — when a day loads, materialize any due `taskSeries` occurrences. No cron for recurrence.
- **Five functions:** the BFF, the MCP server (`aperture-mcp-<stage>`, [mcp/](../areas/mcp/index.md)), and the **finance sync** (`aperture-finance-sync-<stage>`, `cdk/src/lib/finance-sync.ts`): 300 s, 512 MB, no Function URL, invoked only asynchronously — by the BFF after a sync request, connect or reconnect, and by **EventBridge Scheduler** at 5:15a / 3:15p / 8:15p LA (the one scheduled job; created only when `DEVICE_USER_ID` is set). It sits alone in schedule group `aperture-finance-<stage>` because Scheduler checks its role's `aws:SourceArn` against the group ARN, never the schedule's; the one-schedule group keeps the role assumable by that job only. Never retried by Lambda; 30-day log group (the BFF and MCP groups' retention — 90 days on prod via `logRetention` since 2026-10-13, stack-owned 14-day groups on dev — is [CI-BOT.md](../ops/CI-BOT.md) → _Dev logs_); reserved concurrency 1 on dev only, a cost cap (a per-item CAS lock is the concurrency control). Its IAM is GetItem/PutItem/Query on the table + Plaid SSM read. `PLAID_ENV` is `production` on prod, else `sandbox`; the BFF's invoke grant on it is its exact ARN. Timing and design: [finances/](../areas/finances/index.md). The **push dispatch** (`aperture-push-dispatch-<stage>`, `cdk/src/lib/push-dispatch.ts`, cloned from finance-sync) is the reminder poller: EventBridge Scheduler `cron(* * * * ? *)` (once a minute, at the schedule's own second, not :00) in its own group `aperture-push-<stage>`, 20 s / 256 MB, no Function URL, never retried (Lambda and Scheduler), timeout < the minute so ticks can't overlap; reserved concurrency 1 on both stages. On dev every function reserves its share (BFF 18, MCP 9, these two and the coach worker 1 each: `cdk/src/config/devAccount.ts`); on prod the poller's is the only one. Registry-driven, not gated on `DEVICE_USER_ID`. IAM: GetItem/PutItem/Query/DeleteItem on the table + GSI1, and the one SSM read of its VAPID private key; the BFF reads only the public one. Design: [tasks/reminders](../areas/tasks/reminders.md). The **coach worker** (`aperture-coach-worker-<stage>`, `cdk/src/lib/coach-worker.ts`, entry `lambdas/src/coachWorker.ts`) runs the LeetCode coach's AI pick, at most once a day a user, so the model call stays out of the request path and away from finance-sync's Plaid grants: 90 s (≤ 20 s queued + a 60 s model call + writes; the caller's stale-claim read is 120 s, above it), 512 MB, no Function URL, no schedule, invoked only asynchronously (`InvocationType: 'Event'`) by the BFF and the MCP function, each of which carries `COACH_WORKER_FN` and may invoke exactly its ARN. Never retried by Lambda, an event dropped after 1 min; 30-day log group; reserved concurrency 1 on dev, none on prod. Its own role (no `AWSLambdaBasicExecutionRole`, as the poller's): write to its own log group, GetItem/PutItem/Query on the table + GSI1 (writes only via conditional puts), and `ssm:GetParameter` on `/aperture/<stage>/anthropic/api_key` alone; nothing Plaid, S3 or Google. No alarm of its own (§11). Design: [recruiting/coach](../areas/recruiting/coach.md).

Single table per env (`aperture-<env>`), **on-demand** billing, **PITR on** (35-day continuous backup — the safety net), `RETAIN`. Keys/GSI per `TECH.md §2.4`. One GSI, three key spaces (TECH §2.4). TTL on `expiresAt` (TECH §2.3). Reads/aggregation in the Lambda.

## 6. Auth — Cognito

- **One User Pool per env.** Self-signup **OFF** (invite-only; you admin-create your own user). MFA off.
- **App client:** SPA type, PKCE, no secret. Callback URLs = the env's app URL (CloudFront default first; the custom domain from §8 was added when it went live). **`refreshTokenValidity` is 30 days** (Cognito's default; 7 until 2026-11), with token revocation pinned on — it sets how often a password is actually typed; access/ID tokens stay at the 1-hour default. Why, and the renewal behaviour built on it: `TECH.md` §3.
- **Second app client — `aperture-claude-<env>`** — the claude.ai MCP connector (no secret, authorization-code flow, callback URLs = Anthropic's connector constants, **30-day** refresh — why: `areas/mcp/index.md` D13). Plus an **MCP resource server** (identifier `<app-url>/mcp`, one `access` scope). Both live in the **app** stack (not the precious data stack) — the MCP OAuth façade + the credential-not-method fork are in **[areas/mcp/index.md](../areas/mcp/index.md)**.
- **Hosted UI** on a Cognito domain prefix (`aperture-<stage>-<account>.auth.<region>.amazoncognito.com`, created in the data stack; `-c cognitoPrefix=…` overrides the prefix) — free, independent of the app's custom domain. No Google IdP is configured. The MCP function reads this host (`COGNITO_DOMAIN`) to build the façade's `/oauth2` endpoints.
- Frontend: `react-oidc-context` + Hosted UI.
- **Dev test user** `identifiers.json` → `email.devTestUser` (on the dev subdomain; needs no mailbox) — dev pool only, never prod; admin-created (invite suppressed, email verified, no MFA), permanent password in the gitignored `.secrets/devcheck.dev.env`. It signs in through the same Hosted UI and owns its own partition; the dev check uses it ([ops/DEV-CHECK.md](../ops/DEV-CHECK.md)).

## 7. Hosting & CDN

- **S3** (private) + **CloudFront** per env. Default behavior → S3 (OAC); `/api/*` → Function URL origin (origin-secret header, §4). **SPA fallback:** 403/404 → `/index.html` for client-side routing — distribution-wide, so it rewrites an `/api/*` origin 403/404 too (a BFF 404 reaches the browser as a 200 web page). A route a non-browser client reads must not answer 404 — the Shortcut route uses 422 ([tasks/places](../areas/tasks/places.md#4-the-shortcut-route)).
- **`/mcp`** → the second (MCP) Function URL origin, plus three narrowly-scoped `/.well-known/oauth-*` GET behaviors on the same origin (the claude.ai OAuth metadata façade — **never** `/.well-known/*`). `/mcp` uses a **1 s-max-TTL** cache policy (not zero — the mechanism and why are in `areas/mcp/index.md` → _claude.ai — the OAuth façade_ → Decisions) that carries `Authorization` in the cache key, while its origin-request policy forwards the agent-token + MCP headers. Design: **[areas/mcp/index.md](../areas/mcp/index.md)**.
- **Build on the CloudFront default domain first** (`*.cloudfront.net`) — HTTPS + PWA install work immediately, zero DNS. The custom domain was the last step, and is live (§8).
- **Publish discipline** (`scripts/aws/publish-frontend.mjs`, used by CI + local emergency publishes): **two-pass S3 sync** — hashed `assets/*` get `max-age=31536000,immutable`; everything else (`index.html`, `sw.js`, manifest, icons) gets `no-cache,no-store,must-revalidate` so a client never holds a stale shell (old `assets/*` hashes are never deleted — the shell pass excludes them — so in-flight clients keep loading old chunks; the bucket grows ~600 KiB per deploy). **PWA files get explicit `--content-type`** (`manifest.webmanifest` → `application/manifest+json`, `sw.js` → `text/javascript`) because `s3 sync` guesses by extension and an octet-stream manifest silently blocks install. Flux's `.wasm` gets the same treatment (`application/wasm`, still immutable) — Safari's streaming compile refuses anything else — and is uploaded **brotli-encoded** (`Content-Encoding: br`, the decoded size as `x-amz-meta-raw-length`; `scripts/aws/flux-wasm.mjs`) because CloudFront compresses nothing over 10 MB; the build names it `*.br.wasm` so the encoded body never lands under a key an edge already holds uncompressed. `health-check.mjs` asserts type, encoding and raw length at the edge (a missing asset would come back as the SPA fallback's 200 `text/html`). Design: **[areas/flux/index.md](../areas/flux/index.md)** (D63).

## 8. Custom domain — LIVE

- **Each stage's cert lives in its own account** (since the dev-account PR): dev's — and devb's, `devb.aperture.rahuldatta.dev` (`CERT_ARN_DEVB`) — in the dev account's us-east-1, prod's in the management account's. The cert is requested by the break-glass role: the allowlist SCP denies ACM requests to everything else. A CloudFront alternate domain name is globally unique, so moving `dev.aperture.rahuldatta.dev` between accounts meant deleting the old distribution first (about 20–40 min of dev downtime, once).
- **Status (2026-08): LIVE** (re-verified 2026-09-26: `dig NS rahuldatta.dev` → `dns1–4.p03.nsone.net`; `curl -sI aperture.rahuldatta.dev` answers from CloudFront). Planned as the last step, off the critical path, wired right before real daily use. Both stages serve on their custom domains — prod `aperture.rahuldatta.dev`,
  dev `dev.aperture.rahuldatta.dev` — on us-east-1 ACM certs (DNS-validated via Netlify/NS1 DNS, not
  Porkbun: rahuldatta.dev is registered at Porkbun but its nameservers are delegated to Netlify), referenced by ARN through the
  `CERT_ARN_*` GitHub vars. Login round-trips on both (Cognito callbacks registered for each origin).
- **One-time, $0, no recurring work:** create ACM certs in **`us-east-1`** (DNS validation), add the validation CNAMEs at the DNS host (Netlify) once, add the CloudFront alias CNAMEs once. ACM **auto-renews** DNS-validated certs while the CNAME stays — no per-deploy, no per-renewal work.
- **Reference certs by ARN in CDK** (don't have CDK create them) → deploys never touch DNS/certs. The
  ARN comes from `APERTURE_CERT_ARN` (GitHub **var** `CERT_ARN_DEV`/`CERT_ARN_PROD` per stage), read in
  `cdk/src/config/domains.ts` alongside the committed domain names; the app stack takes `domainName` +
  `certificateArn` props and adds the alias + cert to CloudFront only when both are present (else stays
  on the CloudFront default domain, so pre-domain deploys are unaffected).
- **Region note:** the cert lives in **`us-east-1`** (CloudFront's hard requirement) even though the
  stacks deploy to **`us-west-1`** — referencing by ARN makes the split a non-issue.

## 9. CI/CD — GitHub Actions, OIDC

No static credentials — OIDC role assumption. GitHub Flow, simplified:

- Feature branch → PR (three parallel `ci.yml` jobs: `check` = secret scan (gitleaks) + lint + typecheck + non-app tests, `test-app-1`/`test-app-2` = the app suite halved by `vitest --shard`; the same reusable workflow the pipeline runs) → squash to `main`. The secret scan was its own `gitleaks.yml` workflow until `ci-minutes-trim` (2026-11): a one-minute job on every PR and push, now a step of `check` with the same action, full-history checkout and `pull-requests: read` (it lists a PR's commits).
- **Branch runs** (`branch-ci`, 2026-11): `branch.yml` runs the same `ci.yml` on every push to a branch other than `main` and `dev`, before any PR exists, so a lane's full suite can run here once per push instead of on the shared container (the local affected-tests gate that relies on it is the `faster-lanes` follow-up). Its checks are `branch / …` (the job id `branch`, pinned by the test: a `ci` job would post the required check names on a head that isn't the merge), never required, and `checked-tree.ts` reads only `pr.yml` runs, so the PR's required `ci / …` checks and main's tree match are unchanged. A push run always runs the mailroom fixture suite (the fixture-inputs gate is PR-only). A newer push cancels the older run; once a PR is open, a push starts both this and the PR run. Read-only, no secrets, no AWS; `workflow-triggers.test.ts` pins its one `branches-ignore: [main, dev]` filter.
- `main` pipeline: lint/typecheck/test (pnpm + Vitest), alongside a wait while the dev slot's lock is held (`wait-dev`, at most an hour, never a gate: CI-BOT.md → _Dev deploys_ → _A merge waits for the lock_) → `cdk diff --method=template` → `cdk deploy ApertureData-dev` + `ApertureApp-dev` (`--method=direct`) → smoke dev → build app (Vite, env from CDK outputs) → S3 sync (no CloudFront invalidation — publish bullet below) → health check polls the edge for the new shell → same for prod, **automatically — no approval pause** (see the caveat below). Slot `devb` is redeployed by its own `deploy-devb` job, behind its own `wait-devb`, in parallel with dev and never gating prod, only when the push changes what devb runs (`mode_devb == full`; CI-BOT.md → _Dev slots_).

- **Public repo** (public since 2026-11-14, with its real history; prepared by `public-prep`). What a stranger can run:
  - **A fork's pull request fails, never skips.** Every job that runs steps opens with the same `Fork guard` step: anything but a `push`, a `workflow_dispatch` or a same-repo `pull_request` exits 1, before checkout. Failing matters: a job skipped by `if:` reports Success, and a skipped required check passes. `scripts/src/workflow-fork-guard.test.ts` pins the step in every job of every workflow (a file added later included), runs its script under each event, and pins the rest of the posture: triggers only `push`, `pull_request`, `workflow_dispatch`, `workflow_call` (never `pull_request_target` or `workflow_run`); `runs-on: ubuntu-latest` only, no `container`, `services` or `defaults`; nothing a `pull_request` run reaches (`pr.yml`, `ci.yml`, the setup action) mentions secrets, `id-token` or an environment; no `github.event.*`, `github.head_ref` or whole-`github` read outside the guard's `env:`; no job `if:` on who triggered it, no `BASH_ENV`; local actions only `composite`; no write scope but `id-token`; third-party actions from an owner/repo allowlist (versions stay Dependabot's).
  - **The guard is not the boundary.** A fork's `pull_request` run uses the fork's copy of these files, so it can drop the guard (and report green checks on the PR head: merging still needs the code-owner's approval). What holds is GitHub's: such a run gets no secrets and a read-only token, so no `id-token: write` and no OIDC token (inferred from the read-only token; GitHub's OIDC page doesn't say it outright). Behind that, three walls. First, the environments' branch policies: `prod`, `dev-main` and `dev-logs` admit `main` only, and `dev` admits `main` plus the `.github/` branches admitted by name. GitHub matches them against the run's `GITHUB_REF`, which for a `pull_request` run is `refs/pull/N/merge`, so none matches, and a fork's branch named like a protected one is refused outright (docs: _Deployments and environments_). Second, the roles' trust: each admits one named environment of this repo, and `cdk/src/cicd.test.ts` walks every GitHub-federated role for both subject forms. Third, `ApertureCicdStack` refuses a `githubRepo`/`githubSubject` outside GitHub's own owner/repo charset, so there is no `*`, `?` or `${…}` that `StringLike` would read as a pattern.

## 10. Secrets

- No static AWS creds anywhere (Cognito public keys are public).
- **Each stage's parameters live in its own account** (dev's in the dev account since the dev-account PR; the operator-written values were copied across once, the per-user tokens were not — reconnect Google and relink Plaid on dev).
- **Third-party credentials live in SSM Parameter Store** (SecureString, Standard tier, the default `aws/ssm` key — no KMS statement needed): Google under `/aperture/<stage>/google/*` ([calendar/](../areas/calendar/index.md)); Plaid under `/aperture/<stage>/plaid/` — `client_id` + `secret` written once by the operator, `items/<itemId>/access_token` written/deleted by the BFF and read by the sync; the MCP function gets none of Plaid ([finances/ → Operator checklist](../areas/finances/index.md#12-operator-checklist)); the reminders' VAPID keys at `/aperture/<stage>/push/vapid_private_key` (SecureString, read by the push dispatch only) and `vapid_public_key` (String, read by the BFF only), written once by the operator from `pnpm vapid-keys` ([tasks/reminders](../areas/tasks/reminders.md#6-setup-and-rotation)); the Claude API key at `/aperture/<stage>/anthropic/api_key`, written once by the operator and readable (that parameter only) by the BFF and the MCP function ([tasks/quick-add](../areas/tasks/quick-add.md#operator-step-once-per-stage)).
- **Origin secret** — CloudFront→Lambda origin lockdown. A plain Lambda env var, sourced from `APERTURE_ORIGIN_SECRET` (CI) or a gitignored `cdk/.secrets/` file. Anti-abuse only; the JWT is the real gate.
- **Device token** — auth for the extension's LeetCode ingest endpoint. **Same class and same pattern as the origin secret** (single-user, one write method, tiny blast radius) → a plain env var from `APERTURE_DEVICE_TOKEN` / a gitignored file, deliberately **not** Secrets Manager. Paired with `APERTURE_DEVICE_USER_ID` (no credential, but account-specific → uncommitted, and a GitHub secret so public logs print `***`). What happens when either is unset in CI, plus the operator checklist: **[recruiting/ → Operator setup](../areas/recruiting/index.md#operator-setup)**.
- **Where CI gets the three env-var credentials** — `cdk/src/config/ciSecrets.ts` (`stageSecret`): the GitHub secret `<KIND>_<STAGE>` — prod's in the `prod` environment, dev's repo-level (§9) — else, outside CI only, a gitignored file generated once per stage. Empty in CI throws, naming the secret: a misnamed secret can never rotate a token.
- **Agent token** — the MCP server's static credential for Claude Code (`AGENT_TOKEN_DEV` — shared by both dev slots — and `AGENT_TOKEN_PROD`; the third of the three env-var credentials above); the auth fork it sits on: [mcp/ → Auth](../areas/mcp/index.md#auth--a-static-agent-token-disambiguated-by-credential).
- **Place token** — auth for the iPhone Shortcut's one read (`GET /api/places/<slug>/tasks`, [tasks/places](../areas/tasks/places.md#4-the-shortcut-route)). Unlike the device token it is **not** an env var: minted and rotated by the user in Settings, stored only as a SHA-256 lookup row in DynamoDB, so there's no operator step and the dev check's test user can hold one.
- The model API key: _planned_ for Secrets Manager here; **built 2026-10-12 as the SSM SecureString above** (quick add — same pattern and SDK client as Plaid, free; read on first use and held for the warm container). Never in env vars or CDK config.

## 11. Cost

Effectively free at single-user scale: DynamoDB / Lambda / Cognito within always-free tiers; S3 + CloudFront in cents; Function URLs add no per-request cost. **No Route 53** (DNS is at Netlify/NS1; the domain is registered at Porkbun — §8). Only real line item: S3/CloudFront, pennies. The finance sync (3 scheduled runs a day, ~5–20 s each), the coach worker (≤ 1 invoke a day a user, ≤ 90 s × 0.5 GB), the push dispatch (one ~0.3 s tick a minute, ~$0.04/mo of DynamoDB; worst case a stuck tick ≈ $0.15/day, [tasks/reminders](../areas/tasks/reminders.md#5-security-and-cost)), EventBridge Scheduler and the alarms sit inside the free tiers — prod's five plus the dev account's five kill alarms make the free ten (the push dispatch and the coach worker add no alarm of their own: no fixed monthly cost, so the account-wide Lambda Errors alarm covers them, a timeout included) (the free tier is shared across the Organization's consolidated bill — AWS Billing docs, _Consolidated billing_); Plaid Trial is $0 with a hard cap of 10 linked bank logins. The Organization, the SCPs, the kill Lambda and SNS email are free; the dev budget is the second of two free budgets. Dev's table carries an on-demand ceiling (100 read / 50 write units, table and GSI1) that the freeze SCP keeps in place, and expires tombstones through TTL, whose deletes use no write capacity and cost nothing; prod's has none. The dev account's worst case under a rogue branch: CI-BOT.md → _Dev deploy blast radius_.
