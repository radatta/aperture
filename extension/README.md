# Aperture LeetCode (MV3 — Safari)

A personal Safari extension for **sittings**: one go at one LeetCode problem, a rep of your LeetCode Roll in Aperture (`docs/areas/recruiting/index.md` → _Sittings_). On a problem page it puts up one **Start** button. Start clicks LeetCode's own editor reset, its "Are you sure" confirm and its timer, and opens the sitting. From then until you mark the rep Done in Aperture, it sends what LeetCode itself sends: your code as you type, every Run and Submit with its full result, your notes, LeetCode's timer and its replay stream. It authenticates with a **device token** you set in the options page; it never touches or transmits your LeetCode credentials.

> **Automation never reaches the real leetcode.com.** The tests run this code in jsdom and, in the E2E, in headless Chromium on a fake LeetCode page served at `leetcode.com` by a Playwright route, sending to a local server (_Tests_, below). Loading it on the real site is the user's.

## Build it for Safari (daily driver)

Safari needs the extension wrapped in a macOS app, signed with a **free Apple ID Personal Team**. Why that's enough, the per-stage setup, and expiry: `docs/areas/recruiting/index.md` → _Deployment & install_.

1. Convert, from the repo root (needs full Xcode, not just the Command Line Tools):
   - prod: `xcrun safari-web-extension-packager extension --macos-only --copy-resources --project-location ~/Desktop/ApertureSafari --app-name "Aperture LeetCode" --bundle-identifier dev.rahuldatta.ApertureLeetCode`
   - dev: the same **without** `--copy-resources` (the project then reads this folder live, so a rebuild picks up edits), with `~/Desktop/ApertureSafariDev`, `"Aperture LeetCode Dev"`, `dev.rahuldatta.ApertureLeetCodeDev`.
   - Ignore the `world` / `open_in_tab` "not supported" warnings (recruiting doc → _Safari: free signing_).
2. In Xcode, both targets → **Signing & Capabilities** → Automatically manage signing, Team = **(Personal Team)**.
3. **Expect "Embedded binary's bundle identifier is not prefixed with the parent app's bundle identifier" on the first ⌘R** — it hit both fresh prod builds. Fix: in each target's **General** tab, make the extension's Bundle Identifier the app's plus `.Extension` (exact case), make `extensionBundleIdentifier` in `Shared (App)/ViewController.swift` equal it, then ⇧⌘K and ⌘R. Same rule if you change a bundle ID.
4. **⌘R**, then copy the built app to `/Applications`, open that copy once, and delete the project's DerivedData folder (`~/Library/Developer/Xcode/DerivedData/Aperture_LeetCode-*` — spaces become underscores; `…Dev-*` for dev) — otherwise Safari lists the extension twice. **Every rebuild ends with this step**: the installed copy is frozen at the moment it was copied.
5. Safari → Settings → Extensions: enable each build **in one profile only**. Prod ("Aperture LeetCode") goes in a dedicated **Recruiting** profile, where the LeetCode tab group lives. Dev ("Aperture LeetCode Dev") stays ticked for good in the "Aperture Dev" profile; a temporary extension is loaded only there, and replaces it while loaded (untick the dev app meanwhile, so the profile keeps one capture path). The personal profile has neither. In each, allow `leetcode.com` and the API origin, then set the origin and device token there (_Configure_).

**Versions.** `manifest.json`'s `version` (semver-ish, `x.y.z`) names the build: Options shows it, the exported debug log leads with it, and every Start carries it, so the sitting records which build Safari opened it with (a resume, or a same-day reopen of an idle-closed sitting, keeps that first build) and the app's Settings → LeetCode says when that is behind the version the app was built from (_Configure_). Any change to what ships — `manifest.json`, `options.html`, `src/`, `icons/` — bumps it (a fix the patch number, a feature the minor); a test, README or package-config change doesn't. `test/version.test.ts`, in the gate, fails a branch that changed what ships without raising it above its base's (on a PR in CI, main; locally, the merge base with `origin/main`). Two branches bumping to the same number both pass on their own: the second to merge bumps again on its rebase.

After changing anything here: the prod project (made with `--copy-resources`) holds a **copy** of this folder, so re-copy the files into its extension target's `Resources/` first (on the 2026-10 prod project: `Aperture LeetCode/Aperture LeetCode Extension/Resources/`; find it with `find <project dir> -name manifest.json`, and check it holds `manifest.json` before an `rsync --delete` into it); the dev project reads it live. Its `src` and `icons` are folder references, so new files under them are built in. Then rebuild and redo step 4. The dev project reaches this folder by relative paths: when `~/Desktop` moved one level down, into a renamed Desktop folder, they broke, and one more `../` in them fixed it.

**If Safari then says "Unable to find … in the extension's resources" for every file** (seen 2026-11-10): it still points at the build in DerivedData that step 4 deleted. Quit Safari, open the `/Applications` copy once, and register its extension: `pluginkit -a "/Applications/Aperture LeetCode.app/Contents/PlugIns/Aperture LeetCode Extension.appex"`. `pluginkit -mAvvv -p com.apple.Safari.web-extension` lists what macOS knows and from which path.

**Dev icon.** Both builds read the same `manifest.json` (prod icons). The dev project swaps in `icons/dev/` with a **Run Script** phase on its Extension target, after Copy Bundle Resources, "Based on dependency analysis" unticked, and the target's `ENABLE_USER_SCRIPT_SANDBOXING = NO`:

```sh
set -eu
d="${TARGET_BUILD_DIR}/${UNLOCALIZED_RESOURCES_FOLDER_PATH}/icons"
cp -f "$d"/dev/icon-*.png "$d"/
```

This needs `icons` to be a blue **folder reference** in Xcode (the packager's default); a yellow group flattens it and the two `icon-48.png` collide. The Dock/Applications icon is the app's `Assets.xcassets/AppIcon` — drag the matching PNGs in once.

## Configure

Open the extension's **options** page — Safari → Settings → Extensions → the extension → Settings (options are per Safari profile and start blank in each; the per-stage origins, and the command that reads back the device token: `docs/areas/recruiting/index.md` → _Deployment & install_ → _What ever invalidates the setup_) — and set:

- **API origin** — scheme + host of your Aperture backend, e.g. `https://aperture.example.com`. `https` only (`http` for `localhost` / `127.0.0.1`), since the token rides on every request.
- **Device token** — your Aperture device token.

**Save** asks for permission to reach that origin (`<origin>/*`) — inside the click, which Safari requires — then stores both in `storage.local` and resumes a paused outbox. Decline it and nothing sends until you allow it.

The page also shows:

- **Last send** — the outbox's state, its last HTTP status and message, how many batches are queued or failed, and why each failed one was refused. **Retry now** puts failed batches back in line and ends every wait; **Clear failed** drops them (asks first).
- **Version** — the build this is (_Build it for Safari_ → Versions). After a Start, the app's Settings → LeetCode reads "Extension: installed X, latest Y — rebuild needed" when Safari's copy is behind.
- **Coach** — one switch, on unless unticked: the resubmit note (_The sitting_, step 9). Opening Options removes the retired trace card's two switches from storage.
- **Debug mode** — _Debug mode_, below.
- **Selectors** — overrides for where LeetCode's controls are, as JSON over the defaults in `src/lib/selectors.js`: `editorReset`, `resetConfirm`, `dialog`, `timerOpen`, `timerStart`, `timerReset`, `timerResetConfirm`, `lang`, `submit` — each a CSS selector. `null` on a click key (`editorReset`, `resetConfirm`, the four `timer*`) turns that step off, and on `submit` turns the resubmit note off; `dialog` and `lang` aren't steps, so leave them set. Open LeetCode tabs pick a change up at once — no rebuild, which matters for the prod Xcode build. The shipped defaults are below (_LeetCode's controls_).

## The sitting, from LeetCode's side

1. **A problem page** (`/problems/<slug>/…`) puts up a full-screen overlay: the problem, the language, **Start** and **Just looking**.
2. **Start** runs four steps, each checked before the next — Aperture first, so a Start it refuses (another sitting open, no roll, a bad token, the origin or token unset) never touches the editor. The overlay's buttons act only on a real click (`isTrusted`); a LeetCode script's `click()` does nothing.
   1. `lcSittingStart` → the sitting is open (and bound, so a reload from here on resumes);
   2. click LeetCode's editor reset → a dialog appears;
   3. click its confirm → the dialog goes;
   4. (re)start LeetCode's timer, read from `QD_TIMER_STATE`: running or paused → its Reset (`timerReset`); then, if LeetCode asks (its pop-up's Reset, `timerResetConfirm` — the toolbar logged 2026-11-14 resets straight to idle, no pop-up) → idle; then Start (`timerStart`: the pop-up's, still showing after a reset, or the toolbar's own; else the idle opener, `timerOpen`, first), in whichever mode LeetCode last used → it reads running, started just now — and the overlay gives way to a badge: `Aperture · 12m · synced 3s ago`. At most four clicks; a Retry picks up wherever a half-done try left it.
3. **A step that fails** says which, in words ("Couldn't find LeetCode's reset button (editorReset)", "LeetCode's timer didn't start", the server's own message — a missing control is named with its key). Aperture refused: **Retry** (the send again — nothing was clicked) or **Just looking**. A click failed after Aperture said yes: **Retry** (that click) or **Continue without a clear** — the sitting is open either way, so Just looking isn't offered. A step turned off in Options (`null`) is _not configured_ and says so; Continue still keeps the sitting. Leave it there and the sitting stays open, uncleared: a reload resumes it.
4. **Just looking** dismisses the overlay without touching anything, and isn't asked again for that problem until the browser session ends (`storage.session`) — but a pill, `Aperture · Start a sitting`, sits where the badge would (bottom right), and a click on it (the overlay's real-click rule) forgets the dismissal and prompts again; a sitting opened for that problem in another tab meanwhile resumes instead. It shows only on the dismissed problem, never in a tab whose sitting is open (a binding Aperture already ended prompts); stuck hand-offs' warning takes its place while they last. Nothing is captured for a problem with no sitting.
5. **A reload, or a second tab, mid-sitting** resumes with no overlay and no clicks (one Start call per sitting per page load — later visits in the same load trust the binding, so a page flipping the address can't turn into a stream of calls): the per-problem binding (`storage.local['sitting:<slug>']`) repeats the Start with the same `clientSittingId`, which A1 answers with the open sitting. Only Aperture saying the sitting is over (an ended sitting, `SITTING_ENDED_ERROR`, or a Start over a day old) clears the binding; a 401, a 404 or no answer keeps it, so a token change mid-solve never re-prompts you one click from a reset — the outbox holds the events and the badge says why.
6. **Moving to another problem** (LeetCode is a single-page app; the isolated world watches its own `location`: a 500 ms poll, a trusted popstate, or any page message that arrives once the address names another problem — the address read here, never the message's; the poll compares against the path of the last nav whichever noticed it, so going straight back is never missed) prompts again. A Start there while the first sitting is open is refused by Aperture — "Another sitting is still open — end it in Aperture first. Then Retry." The extension can't end a sitting itself: its token only starts sittings and adds events.
7. **The sitting ends in Aperture**, at Done (or Drop) on the rep — an Accepted submit never ends it. The next send learns it (`status` in the events reply, or `SITTING_ENDED_ERROR`), the badge says "Sitting ended in Aperture", the binding clears, and the next visit prompts again. Coming back to the tab (focus, or the tab shown again; at most every 15 s) re-sends LeetCode's timer reading, so a Done marked in Aperture shows within seconds — a send, not a repeat Start, since those count against the day's Start attempts.
8. **The problem doc** — LeetCode's `questionDetail.question`: title, difficulty, tags, the statement (`content`) and the companies (`companyTagStatsV2`). A fresh load doesn't fetch it — the page server-renders it into `__NEXT_DATA__` (`props.pageProps.dehydratedState.queries`, keyed `["questionDetail", {titleSlug}]`; debug log 8, 2026-11-10) — and LeetCode fetches it after a submit, and for the next problem before you click Next (other navigations unconfirmed). So the extension reads the page's copy at `DOMContentLoaded` (again at Start if it has none; a tag over 1,048,576 characters is skipped), kept only when it names the problem the document was loaded for: after a navigation the tag still holds the first problem's, so that problem goes without the page's copy. The page's copy is names and text only — never a question id (the hint check, the binding's id); the one id it may give is the display number (`frontendId`, up to six digits, when no fetched doc has one) — and a fetched doc wins over it. Any doc is first cleaned to what A1 stores (`lib/wire.js` `cleanProblem`, A1's `payloadError` rule: nothing nested past 20 deep, no unstorable number, and an own `__proto__` key — those values dropped, everything else kept), so a doc can never make A1 refuse the Start. A Start carries the doc whole under 64 KB, else only the eight fields read (`lib/wire.js` `PROBLEM_FIELDS`, 2.5–3.6 KB on real docs of 17–22 KB), else none; without a doc, the title, difficulty and tags come from the page. A doc that comes after the Start went is sent once the sitting is active — when it arrives, or when the sitting gets there — in a repeat Start; A1 fills it in. In Safari LeetCode fetches the doc over a blob XHR, which the page world reads as text (_Safari behaviour_ → GraphQL bodies). A fetched doc is kept by its own slug, wherever it was fetched — the next problem's comes from the page you're on, before the Next click (debug log 9) — at most eight, the oldest off screen going first (`doc.keep`; `lib/relay.js` `keepsDoc`), and used only while the address names that problem; so a problem reached by Next starts with its doc.

9. **The resubmit note** (`lib/coach.js`). A real Submit click (`isTrusted`, on a button or `[role=button]` matching `submit` — never a click in our own hosts — caught at the window in the capture phase) within 60 s of a judged submit whose raw `status_code` wasn't 10 (Accepted) shows "trace the failing input before you resubmit" on the badge for 8 s, and logs `nudge-shown` with the gap (from the verdict's arrival); one note per failed verdict. It never blocks, holds or delays the click; the extension never clicks Submit. A page script's `click()`, a keyboard Submit (⌘↵), `submit` null or matching nothing: no note. Each is a `coach` event (`CoachEventPayload`), with `config` once a sitting as it goes active (`{kind: 'config', nudge}`, flagged on the binding as `coach.config`, so a reload or a second tab never sends it twice). Options turns the note off. **The trace card is retired (2.2.0)**: it held the first Submit for three hand-traced inputs; the maintainer traces in a code comment, as in an interview, and whether a sitting was traced is the server's call from the code. The extension no longer sends `trace`, `trace-skip` or `untraced-submit`, and Aperture no longer folds them: the card's build's (manifest 2.0.0) are stored as unknown kinds (`docs/areas/recruiting/index.md` → _Coach events_). A binding from before 2.2.0 keeps the card's `coach.trace`, `held` and `traceAt`, which nothing reads.

## Wire contract

Both calls go to the BFF as RPCs, from the background only:

```
POST <apiOrigin>/api/lcSittingStart       { "args": [ SittingStartInput ] }
POST <apiOrigin>/api/lcSittingEvents      { "args": [ { sittingId, events: SittingEventInput[] } ] }
x-aperture-authorization: Bearer <deviceToken>
content-type: application/json
```

The shapes, caps and error strings are `packages/shared/src/sittings.ts`; the extension mirrors what it must (`x-aperture-authorization` is `rpc.ts` `AUTH_HEADER`; `test/background.test.ts` checks the copies against the shared package, and the unit tests run the shared normalizers over what the extension makes).

- **Start** — `{clientSittingId (a ULID the extension mints), problemSlug, problemTitle, questionId, frontendId, difficulty, topicTags, lang, startedAt (the click), tzOffsetMinutes, lcSolveSessionId (LeetCode's qd_solve_session id), problem (questionDetail.question, from the page or LeetCode's own fetch — step 8), extensionVersion (the manifest's, stamped by the background — _Versions_; null if the browser won't say)}`. A repeat with the same id resumes; the reply is `{sitting, resumed}`.
- **Events** — at most 50 per call and 256 KB, each `{id (ULID), type, at, payload}` or a replay chunk `{id, type: 'replay', at, clientSessionId, events (text)}`:

| LeetCode traffic                                                                                           | event           | payload                                                        |
| ---------------------------------------------------------------------------------------------------------- | --------------- | -------------------------------------------------------------- |
| GraphQL `updateSyncedCode` (`{code, lang, questionId}`) — the full code as you type; one per 30 s ¹        | `snapshot`      | `{code, questionId, lang}`                                     |
| `POST /problems/<slug>/submit/` + its final `/submissions/detail/<id>/v2/check/`                           | `submit`        | `{submissionId, slug, request, result}` — at the submit's time |
| `POST /problems/<slug>/interpret_solution/` + its final `/submissions/detail/runcode_…/check/` (no `/v2/`) | `run`           | `{interpretId, slug, request, result}`                         |
| GraphQL `submissionDetails`                                                                                | `submitDetails` | `{submissionId, details}`                                      |
| GraphQL `updateNote`                                                                                       | `note`          | `{slug, content}`                                              |
| GraphQL `PracticeReplayUploadEvents`                                                                       | `replay`        | its `events` text, split along the array past 60 KB            |
| localStorage `QD_TIMER_STATE`, read every 2 s on change                                                    | `timer`         | `{state, heartbeat}`                                           |
| The extension's resubmit note and its once-a-sitting config (step 9; the server takes them since C0)       | `coach`         | `CoachEventPayload` (`packages/shared/src/types.ts`), ≤ 4 KB   |

¹ `lib/batch.js`: at most one snapshot per 30 s window, the latest code when the window closes (trailing), so live code is at most 30 s behind and a long sitting stays well under A1's per-sitting event cap; the pending one also goes ahead of a run or submit, and on hide or navigation. Other events batch for 3 s; a run or submit goes at once. The first snapshot after Start therefore lands up to 30 s later.

A run or submit LeetCode never judges is sent after two minutes with `result: {pending: true}`. GraphQL `syncedCode` (the saved code on load) only supplies the `questionId`; `questionDetail` only feeds Start (step 8).

**Statuses** (`lambdas/src/rpc/failure.ts` → `failureStatus(…, 'ingest')`; a wrongly shaped call is a 400 like any refusal, and an AWS refusal's text reads `Request refused`): 200 **with the events reply** is sent — CloudFront answers an `/api` 403 or 404 with the app's `index.html` as a 200 (`cdk` `errorResponses`), so any other 200 is retried as "isn't its API"; **409, 429, 5xx and an unreachable server retry** with backoff (5 s, 30 s, 1, 2, then every 5 min, each send timing out at 30 s), in order — a waiting batch holds the ones behind it; **401 pauses** everything until Save in Options; **413 and a 400** split the batch in two until the refused event is alone (a 400 for the sitting's capture cap doesn't split); **`SITTING_ENDED_ERROR`** drops the batch — how a sitting ends past Aperture's ten-minute grace after Done (inside it, a late batch answers 200 with the ended `status`, its events stamped after Done skipped), not a failure; **any other refusal is kept as failed** and shown — in the badge and in Options, never dropped silently. A run or submit over the server's per-event cap is trimmed to its verdict (LeetCode's long outputs first, then the typed code, which the snapshots carry) rather than lost; a full queue (2,000 entries / 5 MB) sheds its oldest snapshot-only batches, then other raw bulk (replay, submitDetails), never a run, submit or note.

## How it works

Three contexts, as the maintainer's forgery rules require (`docs/areas/recruiting/index.md` → _Design decisions_): the page's world can be spoofed by any script on leetcode.com, so it is only ever a source of evidence.

```
leetcode.com page (MAIN world)          extension side of the page (ISOLATED)        background
page/tag.js, inject-main.js             lib/*, debug.js, overlay.js, content.js       lib/outbox.js, background.js
  watches fetch + XHR ──raw text,──▶     relay → wire parse → admit → batches ──msg──▶  outbox → POST to Aperture
  (passive; receives nothing) tagged     overlay, Start's clicks, binding    ◀─reply─  Start answered directly
```

- **`src/inject-main.js`** (MAIN, `document_start`) patches `window.fetch` and `XMLHttpRequest` to _observe_ LeetCode's own traffic — it never blocks or alters a request, makes none of its own, and nothing ever flows back to it. It parses nothing: each message is the raw URL (read once, and that same string goes to the real fetch or open), request text, response text and times. An XHR's response is its `responseText`, or, for `responseType` `'blob'` (Safari's GraphQL), the Blob's text, read through the originals; any other type goes without it. Each send has its own token and a `once` listener, so a reused XHR never pairs one request with another's response; a listener woken by an earlier request's `loadend` (the page re-sent from its `load` handler) waits, by `readyState`, for its own. It loads `lib/tag.js` as a copy in `src/page/`, because Chrome runs a file listed in both worlds only once, in the first (seen 2026-11-08); `pnpm -F @aperture/extension sync-page` refreshes it, and `libs.test.ts` fails when it drifts. The lib is removed from the page's globals once read.
- **The relay.** At `document_start` the page world mints a 32-byte nonce and hands it to the isolated world in a hello; the isolated world acks in the same tick, after which the page world never repeats it. `lib/relay.js` `accept` takes a message only if its tag (HMAC-SHA256 over the body, keyed by the nonce) verifies, its sequence number is new and it is raw text of the right shape; the isolated world then parses it itself (`lib/wire.js`), and `admit` takes each item only if it is for the problem in the tab's address (read by the isolated world — though a page script can change it with `pushState`) and, for events, the extension itself opened a sitting for that problem. Each message also carries the page its request was made from (`location.pathname` at the request — a page script can change it only by navigating): an item made on another page (the last problem's, arriving after a nav) is never this one's. A problem doc is the exception to that, not to the address rule: it names its own problem, so it is kept by that slug wherever it was fetched, and used only while the address names it (step 8) — a script that can fake it before the nav could fake it after. One more exception: a run or submit made on its own problem's page and judged after you left — for another problem or for none — goes to that problem's open sitting (the one the extension bound there), never to the one on screen. Anything else is dropped (counted in the debug log), as is a message over 6 MB or a backlog over 500. The page has no message that Starts anything: only the overlay, in the isolated world, can.
- **What the tag stops, and what it doesn't.** It stops a script on leetcode.com from minting a message or replaying one it heard: it can't sign without the key, a repeated sequence number is dropped, and the key never passes through anything the page can reach — the page world's crypto and promise calls are originals bound at load, called through `Reflect.apply`, and `then` is pinned to `undefined` on what those promises settle with (`Response`, `CryptoKey`, `ArrayBuffer`; a blob's text is a string, which settles with no `then` lookup), so the browser's own promise resolution can't run a page-installed `then`. It does not make the page's traffic true. A patch made _after_ our capture can't make what we record differ from what LeetCode itself got: a `Response` counts only if the browser fetched it from leetcode.com (its own `type` and final URL — so a page-built one, or a `<base href>` sending a request elsewhere, is ignored; an XHR likewise by its `responseURL`, and its body only through the pinned `response` getter, Blob `size` getter — which also proves it a real Blob — and `Blob.prototype.text`), the message is strings and numbers in null-prototype objects (no page `toJSON` applies), and all parsing happens in the isolated world (`replay.test.ts` patches `Response`, `Promise`, `JSON`, `Array` and `Object.prototype`, then `Blob`, `FileReader` and the XHR's `response`, builds Responses, and checks nothing changes). A problem doc is used only for the problem in the address, and a hint's question id only when none is known and no doc disagrees. **Accepted residual:** a script that patched `fetch`, `XMLHttpRequest` or the built-ins _before_ our script ran — including when Safari runs our isolated script after the page's (then page listeners can also run ahead of ours, and the handshake can be heard) — or that drives LeetCode's real editor or writes its timer state (Start's timer step then passes without LeetCode's timer restarted: an `idle` state skips the reset, a fresh running one passes the check while LeetCode's own clock keeps its count — a `timer` event is evidence, not authority), fakes traffic LeetCode itself receives, keeps an event from us (a `loadend` listener ahead of ours) or points the address at the open sitting's problem from another one, produces or loses messages for the one open sitting; the server's caps are the boundary. The debug log records the page's `readyState` at both scripts' start, so the Safari debug session shows whether ours ran first.
- **`src/content.js`** (ISOLATED) runs the overlay's state machine (`lib/overlay-state.js`, painted by `overlay.js` in closed shadow roots on `<html>`, outside React's `#__next` — no page script can read the overlay's text or Aperture's words; what it can see is whether the overlay and the badge show — the badge host also carries the pill on a dismissed problem — so whether a sitting is active or a problem was dismissed. A button acts only on a real click on an overlay that is really showing: the host a direct child of `<html>`, its style ours, nothing on it or `<html>` fading, hiding or moving it — checked at the click; the hosts are put back and kept last among `<html>`'s children every 500 ms. A page element in the browser's top layer, painted over the overlay and letting clicks through, is residual), Start's steps, the binding (written as patches merged into what storage holds, so two tabs on one sitting don't undo each other's writes, and adopted from the other tab's — its change event, or the 5 s reread), the timer read, the parse (`lib/wire.js` over the relay's raw text), and the hand-off (`lib/batch.js`: 3 s batches, a snapshot per 30 s, a run or submit at once, a flush on `pagehide`, hide and navigation). Safari sometimes refuses a hand-off with "Invalid call to runtime.sendMessage(). Tab not found." with nothing reloaded (_Safari behaviour_ → Tab not found): each one is retried in order (after 0.25, 1, 3 and 10 s; a try with no answer in 15 s counts as refused; on `pagehide` or hide the first try starts at once, ahead of the queue). After the last try the events are kept in the page — a reload would lose them — and tried again every 30 s, on coming back to the tab and after any hand-off that lands; the badge says "events waiting to reach the extension — retrying, keep this tab open", and only says to reload when the extension itself is gone (reloaded or updated). A batch handed over twice is safe: the server writes each event id once. The debug log records each refusal (`enqueue.fail`) and a retry that got through (`enqueue.retried`). The overlay names the problem from LeetCode's doc (step 8), else the tab title only once it names this problem (after Next it still names the last one for a moment), else the slug, and repaints when the doc or the title comes; until the page names it, a Start sends no difficulty or tags rather than the last problem's.
- **`src/background.js`** owns the device token and every POST. Start is answered directly; events go through the outbox (`lib/outbox.js`, persisted as `storage.local.outbox`, capped at 2,000 batches / 5 MB — over it, the oldest snapshot-only batches go first, never a run or submit). It re-arms itself with a timer and an alarm, so a retry survives the background being unloaded. It writes `status` (the outbox) and `sync:<slug>` (the sitting's last reply) for the badge and Options, and answers only messages from the extension itself — `{ok: true}` once an enqueue is stored, and the content script counts anything else as refused. Safari doesn't always pass these writes on to the page as storage changes (_Safari behaviour_ → onChanged), so while a sitting is open the content script also re-reads them every 5 s.

**Storage keys** — `local`: `apiOrigin`, `deviceToken`, `selectors`, `coachNudge` (absent = on; Options removes the retired `coachTrace` and `coachHold`), `debug`, `debugLog`, `outbox`, `status`, `sitting:<slug>` (its `coach`: step 9), `sync:<slug>`; `session`: `dismissed:<slug>` (set by Just looking, removed by the pill).

## Debug mode

For finding LeetCode's controls (the table above). Options → **Debug mode** on, then reload the LeetCode tab. It records, in `storage.local.debugLog` (last 2,000 entries): what you click (tag, text, `data-*`/`aria-*` attributes, a short HTML excerpt, a CSS path), every dialog that opens and its buttons, changes to `QD_TIMER_STATE`, `QD_TIMER_HEARTBEAT`, `global_lang` and `qd_solve_session:*`, the clocks on screen every 2 s, `__NEXT_DATA__`'s query keys and what the problem-doc read found (`pageDoc`: the tag's length in characters, whether it named this problem, its field count, whether it fit, how many unstorable values were dropped), each late fill (`fill`), whether Safari took the scrim's blur (`scrim`: `CSS.supports` and the computed values), the handshake (with `document.readyState` when the isolated script ran — whether Safari's `document_start` is early enough), the version the page loaded under (`oc.reg`'s `v`), every relay drop and overlay step (the timer step's `timer` entry: the state it read, and whether it `reset` (`confirmed` when LeetCode asked), `opened` and `started`, and the status and mode it ended in, `statusAfter` and `modeAfter`), each pill click (`pill`: whether it was a real click and passed the overlay's checks), each nav (`nav`: the slug, `by` what noticed it — `poll`, `popstate`, `message`, `init`, or a `reread`/`pill` of the same problem — whether a binding was there, and whether it was dismissed) — and, when a Start step fails, every editor button, labelled button and labelled `[role=button]` on the page (an icon's `<svg>` named too). Never code, request bodies or tokens: the wire entries are sizes, GraphQL operation names and the page world's word on how it read the response (`how`: `fetch:ok`, `fetch:skip`, `fetch:no-clone`, `fetch:no-text`, `fetch:read-fail`, `xhr:ok`, `xhr:skip`, `xhr:status-<n>`, `xhr:type-<type>`, `xhr:no-text`; for a blob XHR `xhr:blob-ok`, `xhr:blob-none` (no Blob), `xhr:blob-big` (over 1 MB, not read), `xhr:blob-empty`, `xhr:blob-no-text` (no `Blob.prototype.text`), `xhr:blob-read-fail`; `:big` past 1 MB), each fetched problem doc kept (`doc.keep`: whether it is the problem on screen, how many are kept, the slug evicted for it), and credential-looking storage keys are redacted.

The session (≈5 minutes, on a problem you've solved): Just looking; hover each icon in the editor toolbar, click the reset, then its confirm; open the timer, start it, wait, pause, resume, reset; switch to the stopwatch and do the same; type a line; Run once; Next problem and back. Then Options → **Export debug log** (or **Copy JSON** — Safari may open a download in a tab; its first entry, `export`, names the version), and the selectors come from it.

## Safari behaviour

**The rule: research before fixing.** jsdom and Chromium can't see Safari's quirks, and each guessed fix has cost one of the maintainer's manual Safari passes (2026-11-10: three, one per guess). So before changing code for something Safari does: read WebKit's source, search for it, and ship a probe of the mechanism; then hand over a pass.

- **WebKit's source** — a sparse, shallow clone of just the extension code: `git clone --depth 1 --filter=blob:none --sparse https://github.com/WebKit/WebKit.git && cd WebKit && git sparse-checkout set Source/WebKit/UIProcess/Extensions Source/WebKit/WebProcess/Extensions Source/WebKit/Shared/Extensions`. For XHR and Blob, add `Source/WebCore/xml Source/WebCore/fileapi Source/WebCore/bindings/js`. Record the commit (`git log -1 --format=%H`) beside every file:line you cite: trunk moves, and the Safari on the Mac may be older than it.
- **A probe** is a `debug.log(type, {...})` (`src/debug.js`; recorded only in Debug mode) that logs the mechanism, not the symptom — was the listener registered, which events arrived, why a read failed — as sizes, flags and fixed words, never content. The model is `content.js`'s `oc.reg` / `oc` / `pageshow`: the page's `readyState` when its `storage.onChanged` listener was added, every change it then heard (its own debug-log writes only counted), and whether it came back from the back/forward cache.
- **The pass protocol.** Research done and probes in, then: say if the code is pre-review; no dev deploys while the maintainer tests on dev; every Mac command a single line with `find`-found paths and a guard (`ls …/manifest.json &&`) before anything destructive; Debug mode on; a short scripted pass, then Options → **Export debug log**. After it, read the log for every state they could have seen — a state stuck where it shouldn't be is a bug.

## Tests

- **Unit and jsdom** — `pnpm --filter @aperture/extension test` (in the gate): the pure libs against the shared package's own normalizers; `test/replay.test.ts` runs the real page-world script in jsdom over both transports, XHRs as text and as Safari's blobs (`load.ts` `fakeXHR`); `test/overlay.test.ts` runs both worlds' scripts over the fake LeetCode page (`test/fixtures/`), reading the closed roots through an `attachShadow` wrapper and clicking through jsdom's internals with `isTrusted` set (`test/load.ts`, test-side only); its fake clock steps 10 ms at a time, each only once no relay webcrypto call is in flight, so crypto takes no fake time (F242: a slow threadpool let the clock run seconds ahead); `test/background.test.ts` runs the real background in a vm; `test/options.test.ts` runs the real Options page (`options.html` and the scripts it lists) in jsdom; `test/version.test.ts` is the version gate (_Versions_).
- **Stress, for a test that assumes timing** (opt-in, not in the gate) — `EXT_CRYPTO_JITTER_MS=90 pnpm --filter @aperture/extension exec vitest run test/overlay.test.ts` settles each relay crypto call 0–90 real ms late, at random: the order of completions and anything assuming a call lands within one real turn. `EXT_CRYPTO_LATENCY_MS=50` adds 0–50 _fake_ ms per call instead, so crypto races the scripts' own timers (the poll, the batch windows), as it does in a browser. Either prints its `EXT_CRYPTO_SEED`, which replays the same delays. Proving the stress still bites: with `io` cut to one `turn()` (main's harness before F242), `EXT_CRYPTO_JITTER_MS=90` fails six tests.
- **E2E** — `scripts/src/lc-e2e/extension.test.ts` (in `pnpm --filter @aperture/scripts test`; skipped where `~/pw` has no Playwright, as on CI): the real extension in headless Chromium (a copy with a service-worker background, `chrome-build.ts` — Chrome's MV3 refuses `background.scripts` — plus, in that copy only, the `scripting` permission and a script that keeps the closed roots in the isolated world, which the test reads through `chrome.scripting` and clicks at their real coordinates), on the fake page, against A1's real BFF run locally as the test user — and the fake page's GraphQL over real blob XHRs (`__fakeOpts.blobGql`), read by the page with `FileReader`; and Just looking's pill, clicked at its real coordinates.
- **What none of them prove:** Safari, and LeetCode's real DOM. Nor, by default, crypto racing a timer: the overlay suite gives a sign or verify no fake time, while Safari likely runs HMAC on a work queue and answers a task later (inferred, WebKit's `CryptoAlgorithmHMAC` not yet read) — `EXT_CRYPTO_LATENCY_MS` is the jsdom probe for it. Those are the `lc-extension` dev-check scenario's _Needs you_ rows: real Safari sittings that prove the shipped selectors (the debug session, 2026-11-10, found them), and one real sitting against dev.
